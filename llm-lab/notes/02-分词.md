# 第 2 步：字符级分词

## 这一步解决什么问题

模型是函数，只吃数字；文本是字符。中间必须有一座桥，这座桥就是分词器。

不过我们这一步真正要建立的认知不是"怎么写一个映射"，而是三件更本质的事：**词表是封闭的、映射必须确定、词表大小决定了模型的输入输出维度。**

## 怎么读这篇

**标记约定**：出现 `（→ 第 N 步）` 表示那个概念在后面那一步才正式讲解，这里只要知道名字就行。

**本文范围**：只讲"文本怎么变成整数"。这些整数之后怎么被模型消化，属于第 4 步。

## 为什么先做字符级

分词有三档做法：

| 做法 | 词表大小 | 一个 token 是 | 代价 |
| --- | --- | --- | --- |
| 字符级（本步） | 几十 | 一个字符 | 序列很长 |
| 词级 | 随语料增长，没有上界 | 一个词 | 遇到没见过的词就抓瞎 |
| 子词级（BPE 等） | 几万～几十万 | 一个词片段 | 需要一个训练过程 |

先说清楚代价：字符级的压缩比是 **1.00 字符/token**，也就是完全没压缩。而**注意力的计算量随序列长度平方增长**（→ 第 6 步正式讲注意力），序列长一倍，计算量变四倍——所以真实模型最终都要用子词分词。

那为什么还从字符级开始？因为它把"分词"这件事剥到了最小：词表就是**语料里出现过的所有字符，去重后排序**，没有任何训练过程、没有任何超参数。你可以一眼看完整个词表，从而把注意力留给模型本身。子词分词会在第 8 步之后单独做。

## 词表是封闭的

这是本步最重要的一条，也是真实世界踩坑最多的地方。

词表里只有语料出现过的字符。别的字符**根本没有 id**，不是"表示得不好"，而是"无法表示"。脚本里试了 `中`、`文`、`🙂` 三个，全部直接报错：

```
character '中' is not in the vocabulary
```

这份莎士比亚语料只用到 65 种不同的字符（全是 ASCII），所以词表正好是下面这一行（`\n` 是换行符）：

```
"\n !$&',-.3:;?ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"
```

注意里面那个 `3`。这份语料里出现过的数字只有它一个——来自剧本标题 `3 KING HENRY VI` 的幕次，全文出现 27 次。也就是说：**词表里有 `3`，却没有 `1`、`2`、`4`、`7`**。一个用这份语料训出来的模型能写出 `3`，写不出 `1`。

同样，它也**永远不可能输出中文**，因为最后一层根本没有对应的输出维度。这不是模型"不会"，是它连表达这个字符的位置都不存在。理解了这一点，你就能解释很多真实现象：为什么模型对罕见语言、特殊符号、罕见姓氏表现差；为什么加了新语言的语料之后往往要重新训练分词器。

## 映射必须确定

`from_text` 里做了排序（`sorted(set(text))`）。这不是为了好看。

如果不排序，词表顺序就取决于字符的**哈希值**——而 Python 对字符串的哈希做了随机化，所以**每次运行都可能得到完全不同的顺序**（实测见自测第 1 题）。而 id 是**模型参数的索引**：id 3 对应哪个字符，决定了 embedding 表里第 3 行代表什么。（→ 第 4 步展开 embedding）

所以 **checkpoint 和词表是绑定的**：换一份词表，之前训练的权重就全废了。这也是为什么脚本会把词表存成 `data/processed/vocab.json`，后面每一步都复用它，而不是各算各的。

## 词表大小意味着什么

两个数字会被词表大小直接决定，到第 4 步和第 7 步会具体用到：

- **输入侧**：embedding 表是 `vocab_size × d_model` 的参数矩阵，每个 token 从里面查一行。（`d_model` 是"每个 token 用多少个数字来表示"，→ 第 4 步正式展开；它和 `vocab_size` 的区别见 [glossary.md](./glossary.md)）
- **输出侧**：最后一层要把每个位置的向量（称为**隐藏向量**，→ 第 4 步）映射回 `vocab_size` 个分数（logits），告诉模型"下一个 token 是每个字符的概率"。

对照一下量级，你就能明白为什么大模型的分词器那么复杂：

| 分词器 | 词表大小 |
| --- | --- |
| 本步的字符级 | 65 |
| GPT-2 的 BPE | 50,257 |
| 现代模型常用的 BPE | 100,000 ～ 200,000 |

词表越大，同样的文本需要的 token 越少（序列短、注意力便宜），但输入输出矩阵越大。这是分词器设计里最核心的取舍。

## 脚本在验证什么

`scripts/step02_tokenize.py` 做了三件正事：

1. **往返无损**，且**两个方向都测**：`decode(encode(text)) == text` 保证信息没丢，`encode(decode(ids)) == ids` 保证映射本身可逆。只测一个方向会漏掉"多个 token 映射到同一个字符"这类错误。
2. **存盘再读回**：`vocab.json` 重新加载后编码结果必须完全一致，否则后面每一步都会跑在不同词表上。
3. **暴露封闭性**：主动去编码词表外的字符，让失败发生在这里——而不是等训练完之后，你才发现某个输入根本进不去。

脚本还会打印词表里的数字列表，输出的就是 `['3']`——上面那个现象的直接证据。

完整输出：

## 附带踩到的坑：Windows 的换行符

第一次运行后 `pnpm check` 直接失败，报错是 `Formatter would have printed the following content`，每一行末尾都标着 `␍`（回车符）。

原因：Python 在 Windows 上以文本模式写文件时，会把 `\n` 自动改写成 `\r\n`。而仓库根 `.gitattributes` 规定全仓库统一 LF，Biome 会强制检查这一点——所以 `vocab.json` 一生成就违规了。

修法是在 `save()` 里显式声明 `newline="\n"`。这件事本身和 LLM 无关，但它说明一个规律：**生成物也要遵守仓库规则**，而这类问题只有真正跑过检查才会暴露。后面每写一个产出文件的脚本，都要注意同一个点。

## 本步新名词

累计索引见 [glossary.md](./glossary.md)。

- **字符级分词（character-level tokenization）**：一个字符就是一个 token。词表最小、逻辑最透明，代价是序列最长。
- **词表（vocabulary）**：模型认识的全部 token 的集合。本步的词表就是语料里去重排序后的 65 个字符。
- **词表大小（`vocab_size`）**：词表里的 token 个数。它决定输入侧 embedding 表有多少行、输出侧最后一层吐出多少个分数。**注意它和 `d_model` 是两件正交的事**：`vocab_size` 回答"有多少种东西"，`d_model` 回答"每一种东西用多长的向量表示"。完整说明见 [glossary.md](./glossary.md) 与第 4 步。
- **编码 / 解码（encode / decode）**：文本 ↔ id 序列的相互转换。两个方向都要能无损往返，这是分词器的底线。
- **子词分词（subword tokenization，如 BPE）**：一个 token 是一段词片段。词表大（几万到几十万），但同样的文本占的 token 少得多，是目前所有大模型的选择。
- **压缩比（chars per token）**：平均多少个字符才占一个 token。字符级永远是 1.00，也就是完全没压缩——这直接导致序列变长，而注意力的计算量随序列长度平方增长。
- **封闭词表（closed vocabulary）**：语料里没出现过的字符**根本没有 id**，不是"表示得不好"而是"无法表示"。本步用 `中`、`文`、`🙂` 现场验证了这一点。

## 自测

先自己答一遍再看文末的「自测详解」。

3. 字符级分词的压缩比是 1.00，这为什么会成为问题？

## 自测详解

### 1. 为什么 `sorted(set(text))` 里的 `sorted` 不是可有可无的？

因为 **Python 对字符串的哈希做了随机化**，而 `set` 的迭代顺序取决于哈希值。这意味着 `set(text)` 的顺序**每次运行都可能不同**——不用"可能"，在本机连续跑五次就是五种顺序：

```
qjfetcwg mrvzpxlubadonhisyk
ajhbkesyimz pqwfogtnvcdulxr
cznbda mhsxgqjtvowkrileuyfp
lyzxgaj kvrmnqhtdbuwfcipeos
xqrjgplcaekduznw yothibvfsm
```

（复现命令：循环执行 `python -c "print(''.join(set('the quick brown fox jumps over the lazy dog')))"`。）

于是不排序的后果是：**词表顺序每次运行都变 → 每个字符的 id 每次都变 → 昨天训练的 checkpoint 今天就是废的**。因为 id 是模型参数的索引，`id 3` 代表哪个字符一变，embedding 表第 3 行的含义就变了，权重全部错位。

这个 bug 的可怕之处在于它**极其隐蔽**：单次运行内部一切正常，只有跨运行、跨机器比较才会暴露。而 `sorted` 一行就根治——它把"由哈希决定的顺序"变成"由语料的字符集合唯一确定的顺序"。

### 2. 「这个模型不认识中文」换成参数层面的说法是什么？

输出层是一个形状为 `d_model × 65` 的矩阵，产生 65 个分数，每个分数对应词表里的一个字符。里面**没有任何一列对应中文**——所以模型连"给出这个字符一个分数"的位置都不存在。不是它不想说，是没有地方可说。

输入侧同理：embedding 表只有 65 行，中文没有对应的行，"喂进去"这件事本身就无法表达。第 2 步的脚本现场验证了这一点，`中`、`文`、`🙂` 三个都被直接拒绝：

```
character '中' is not in the vocabulary
```

这就是"封闭词表"的含义。它解释了为什么模型对罕见语言、特殊符号、罕见姓氏表现差；也解释了为什么给模型加一门新语言时，往往连分词器一起换、从头训练。

### 3. 字符级分词压缩比是 1.00，这为什么会成为问题？

因为压缩比 1.00 意味着**序列长度等于文本长度**：1,115,394 个字符就要 1,115,394 个 token，一个都没省。

而注意力的计算量随序列长度**平方**增长（→ 第 6 步）。序列翻倍，计算量变四倍。字符级分词把所有文本都拉长成了最长可能的序列，是成本最高的一种选择。

第二个代价是**上下文窗口**（一次能塞进模型的最大 token 数）。窗口是用 token 数衡量的，字符级下同样大小的窗口能装的实际文字更少。对照一下：BPE 大约 4 个字符一个 token，同样的窗口能装的信息量是字符级的四倍左右。

这解释了一个乍看很反直觉的现象：**更复杂的词表反而更省算力**。代价在别处——词表大，输入输出矩阵就大，而且分词本身变成一个需要训练的组件。这是分词器设计里最核心的取舍。

### 4. 为什么要把词表存成文件，而不是每次运行重新算一遍？

三个理由，一个比一个重要：

**一致性。** 词表和权重是绑定的。checkpoint 只有在"配对的词表"下才有意义，所以它必须是一个被明确保存、明确版本化的东西，而不是每次运行时临时算出来的副产品。

**可复现。** 前面那道题已经说明，不显式固定顺序的话，每次运行可能得到不同的 id。存盘相当于把"这一次的映射"永久冻结下来，让不同机器、不同时间、不同 Python 版本都得到同一套 id。

**成本与接口。** 重建要重新读一遍全文（本项目 110 万字符，还不算多），而词表是一个**一次性决策**：一旦开始训练就不该再变。它是模型和外部世界之间的接口，接口变了，两边都得重来。

再补一点：后面换中文语料时，词表会整个换掉，之前训练的权重也随之作废。这正是"接口变更"的代价，早点接受这件事，比在项目中途被迫接受要好。

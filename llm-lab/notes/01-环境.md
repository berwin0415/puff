# 第 1 步：环境

## 这一步解决什么问题

在写任何模型代码之前，先把地基验证一遍。原因是：**如果 GPU 或自动求导是坏的，后面每一步的报错都会看起来像我们自己代码的 bug**，而你此时还没有能力分辨。花二十分钟把地基钉死，后面能省下大量误判。

这一步不涉及任何语言模型的内容。

## 驱动 / CUDA / PyTorch 是什么关系

这三样经常被混在一起讲，其实是分层的：

| 层 | 是什么 | 谁提供 |
| --- | --- | --- |
| 显卡驱动 | 操作系统与显卡对话的接口 | NVIDIA（系统级，`nvidia-smi` 显示的就是它） |
| CUDA runtime | 让程序把计算提交给 GPU 的运行时 | 随 PyTorch 打包分发，不需要单独安装 CUDA Toolkit |
| PyTorch | 张量、自动求导，以及为各种 GPU 架构编译好的计算内核 | pip 安装的 wheel |

关键在最后一行：**wheel 里的计算内核是按 GPU 架构编译的**。本机是 Blackwell（`sm_120`），如果装到的 PyTorch 构建里只有 `sm_80` / `sm_90` 的内核，那么 import 会成功、`torch.cuda.is_available()` 甚至会返回 `True`，但一执行计算就报：

```
no kernel image is available for execution on the device
```

这就是 `requirements.txt` 里 `--index-url .../cu128` 的由来——CUDA 12.8 是第一个带 Blackwell 内核的版本。这类「装上了却跑不了」的坑，是从 0 到 1 过程中最消耗人的部分，值得在第一步就认清。

顺带一个常被误解的事实：**CUDA Toolkit 不需要单独安装**。PyTorch 的 wheel 自带运行时，你只需要一个足够新的驱动。

## 为什么要独立虚拟环境

`llm-lab/.venv` 是本目录专属的 Python 环境。它有两个作用：把 PyTorch 这类体积巨大、版本敏感的依赖与系统 Python 隔开；以及让这个目录可以整体删掉重来，不影响机器上任何别的东西。

它不在 pnpm workspace 里，和 `apps/*` 的 Node 生态互不干扰——两种语言的依赖各自独立，这是刻意设计的。

## 脚本在验证什么

`scripts/step01_check_env.py` 打印几组信息，每组对应后面会依赖的一项能力：

1. **环境**：实际加载的 Python 与 torch 版本。避免「装是装了，但用的是另一个 Python」这种低级错误。
2. **设备**：GPU 型号、计算能力、显存。确认 torch 看到的是你要用的那张卡。
3. **正确性**：同样的矩阵乘法分别在 CPU 和 GPU 上跑并比较。**一个又快又错的 GPU 比没有 GPU 更糟**，所以这一步必须做。
4. **自动求导**：计算 `d(sum(x²))/dx` 并与手算结果 `2x` 对照。这是整条学习线里最关键的基础设施——第 4 步之后，所有训练都建立在它之上。

最后是矩阵乘法的粗略性能测试。注意代码里那次预热：前几次调用要承担内核选择和显存分配的开销，不预热测出来的数字会明显偏慢。这个细节在后面测推理速度时会反复用到。

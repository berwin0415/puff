# 第 1 步：环境

> **一句话**：先确认这台机器能装、能算、算得对，再动手写模型。
> **这一篇要回答**：装得上吗？算得动吗？算得对吗？

## 这一步解决什么问题

你决定动手了。第一件事不是写模型，而是让代码真正跑在显卡上。

结果可能是三种之一：程序说找不到显卡；不报错，但慢得像根本没装显卡；或者最糟——它跑得飞快，算出来的却是错的。

这些情况之所以常见，是因为"让 Python 用上显卡"不是一行代码的事，中间串着好几层。任何一层对不上，上面那层就会以奇怪的方式失败。

所以这一步**不写任何模型代码**，只确认三件事：**装得上**（依赖能装好）、**算得动**（显卡真能用）、**算得对**（结果可信）。

三件事都过了，后面的每一步才有意义。任何一件没过，后面所有的报错都会看起来像你自己写错了——而那时候你还分不清。

下面用七个问题把它们拆开。

## 读完你会知道

- 模型为什么非要跑在显卡上，CPU 差在哪；
- 驱动、CUDA、PyTorch 这三层各自负责什么，为什么只装 PyTorch 就够；
- 为什么这台 Blackwell 显卡必须用 cu128 及以上的构建；
- 为什么 `torch.cuda.is_available()` 返回 `True`，模型仍可能根本跑不起来；
- 怎么用一次 CPU/GPU 结果比对，证明这台机器算出来的数是对的。

## 怎么读这篇

**标记约定**：出现 `（→ 第 N 步）` 表示那个概念在后面那一步才正式讲解，这里只要知道名字就行。

**本文范围**：只回答"能不能跑、算得对不对"，不涉及任何模型内容。遇到不懂的词先跳过，后面的问题会一个个接上。

## 问题一：为什么模型要跑在显卡上？

先说清楚 CPU 和显卡的分工。

**CPU 像几位博士**：核心少（这台机器是 8 核 16 线程），但每个都能处理复杂、带分支的逻辑，写代码、调度系统都靠它。

**显卡像几千个小学生**：每个只会做简单的乘法和加法，但可以同时开工。

模型训练干的活恰好是后者：把几百万、几十亿个数字两两相乘再相加。这种"同一件事、对海量数据同时做"的任务，显卡天生擅长——同样的运算，快几十倍。

代价是：**Python 不会自动把活派给显卡。** 你得把这条路接通，而且要接对。

## 问题二：为什么要单独建一个 Python 环境？

要用显卡，得先把工具装进来。装在哪？

直接装进系统自带的 Python 里，很容易和别的项目打架：升级一个包，另一个项目就跑不起来了。而模型这套依赖又大、又挑版本。

所以建一个只属于这个目录的**虚拟环境**（`llm-lab/.venv`）：里面的包装坏了，删掉重建即可，系统里其他东西一点不受影响。

## 问题三：要让 Python 用上显卡，中间需要什么？

环境准备好了，接下来要弄清楚：往里面装什么？

从下往上，一共四层。最上面那层，就是你写代码时直接用的工具——本项目用 **Python** 写，框架是 **PyTorch**。（"框架"是什么、为什么选这两样，[附录 C](./附录C-工具选择.md) 里有。）

| 层 | 通俗解释 | 谁提供 | 要不要单独装 |
| --- | --- | --- | --- |
| **显卡** | 干活的 | 你买的硬件 | — |
| **显卡驱动** | 操作系统和显卡之间的翻译 | NVIDIA，系统级；`nvidia-smi` 显示的就是它 | 要，一般随驱动装好 |
| **CUDA** | 把"并行计算任务"翻译成显卡指令的平台 | NVIDIA 定义 | 不要——运行时**随 PyTorch 的 wheel 打包** |
| **PyTorch** | 你写代码时面对的那一层 | 由 Meta 开源（现由 PyTorch 基金会维护），pip 安装 | 要，整个项目都建在它上面 |

一句话串起来：**你写 PyTorch，PyTorch 调用 CUDA，CUDA 通过驱动指挥显卡。**

### 那 CUDA Toolkit 是什么？

CUDA 除了运行时（真正干活的库），还带一套**开发工具**，打包叫 Toolkit：`nvcc` 编译器、头文件、调试器、性能分析工具。

**它是给"要自己写显卡程序"的人准备的**——你得有 `nvcc` 把 `.cu` 文件编译成显卡能执行的内核。我们用 PyTorch 现成的算子，不写内核，所以用不到它。

例外：有些库在安装时要现场编译，会调用 `nvcc`，那时才真的需要。到那一步再说。

## 问题四：都装好了，为什么还是跑不起来？

因为 PyTorch 不是"装一个就通用"的软件。

pip 装的其实是一个 **wheel**（发行包）——预先编译好的安装包。它除了 Python 代码，还带着一堆**为特定显卡型号编译好的计算内核**（真正在显卡上跑的小程序）。

本机是 RTX 5070 Ti，架构代号 **`sm_120`**（Blackwell）。如果装到的版本里没有为 `sm_120` 编译的内核，会发生什么？

- `import torch` 成功；
- `torch.cuda.is_available()` 返回 `True`；
- 一执行计算，直接报错：

```
no kernel image is available for execution on the device
```

这就是 `requirements.txt` 里指定 `cu128` 的原因：**CUDA 12.8 是第一个带 Blackwell 内核的版本**。

这类「装上了却跑不了」的坑，是从 0 到 1 最消耗人的部分——它不给你"你没装对"的提示，只给你一句看不懂的报错。

## 问题五：`is_available()` 说 `True`，为什么还会挂？

因为它只回答了一个很浅的问题：**"我看得见显卡吗？"**

它检查的是：驱动能不能加载、设备能不能枚举出来。**它不检查"我能不能在这张卡上真正执行计算"。**

以前这两件事几乎等价，所以没人怀疑它；新架构的卡出现之后，它们才分家。

真正的失败发生在**第一次执行内核**的那一刻。而错误信息里写的是 "kernel image"，听起来和你写的模型、数据、形状毫无关系——于是你会去错误的地方找原因。

所以可靠的检查是两个：`get_device_capability()` 看架构号（也就是"计算能力"），以及**真的跑一次计算**。

## 问题六：跑得动，就等于算得对吗？

不等于。

显卡的失败不只表现为"跑不起来"，还表现为**"跑起来了，但答案是错的"**：内核有 bug、驱动有 bug、内存越界读到脏数据、某个算子悄悄退回了错误的实现。

这类错误**不会抛异常**。训练照常跑完，损失照常下降，代码看起来一切正常——只是模型学的东西是错的。等你发现时，可能已经烧掉几小时甚至几天。

所以脚本做了一件事：同一个 512×512 矩阵乘法，CPU 算一遍、GPU 算一遍，比较最大差值。

**差值是 0。**

为什么要比这一项？因为矩阵乘法是所有神经网络最基本的运算——说白了，就是把一个数字表格的每一行和另一个表格的每一列配对相乘再相加，模型绝大部分计算都是它。它错了，后面每一步的结论都不可信：损失不下降，你分不清该怪模型结构还是该怪乘法。

## 问题七：训练还缺一样东西——自动求导

前面六个问题都在问"显卡这条链通不通"。但训练还有另一半：**知道每个参数该往哪边调。**

这就是**自动求导**：PyTorch 把你做的每一步运算记下来，最后一次性算出所有参数的梯度。

验证方法很短：让 `y = sum(x²)`，看 `x.grad` 是不是等于 `2x`。

它现在看起来很平凡，因为只有两步运算。但到第 7 步，网络里有几百次运算、八十多万个参数，梯度要完整穿过它们。那时如果中间任何一环记错了图，你能依靠的唯一前提就是：这套机制本身是对的。

（"梯度到底是什么、为什么沿着它反方向走就能让模型变好"，见 [附录 B](./附录B-梯度.md)。）

## 脚本在验证什么

`scripts/step01_check_env.py` 把上面的问题逐条跑一遍：

| 脚本输出 | 回答哪个问题 |
| --- | --- |
| python / torch 版本 | 装的是不是你以为的那个（问题四） |
| gpu / compute cap. / vram | 看见的是不是那张卡（问题五） |
| cpu vs gpu max diff | 算得对不对（问题六） |
| autograd 的 `[2.0, 4.0, 6.0]` | 自动求导能不能用（问题七） |
| matmul … TFLOP/s | 大概有多快（问题一） |

实际输出（本机一次真实运行）：

```
python         : 3.11.9 on Windows
torch          : 2.11.0+cu128
gpu            : NVIDIA GeForce RTX 5070 Ti
compute cap.   : sm_120
vram           : 15.9 GiB
bundled cuda   : 12.8

autograd       : d(sum(x^2))/dx = [2.0, 4.0, 6.0] -> ok
```

最后那行 TFLOP/s 每次运行都会浮动（受温度、后台进程、显存频率影响），不必追求特定数值。**要确认的是前面几行是不是都 `ok`**——尤其是 `max diff 0.00e+00`。

## 回顾

- **回答了什么问题**：这台机器能不能可靠地算？答案是能——显卡可见、架构匹配、结果与 CPU 完全一致、自动求导可用。
- **关键数字**：`sm_120`（Blackwell）、15.9 GiB 显存、CUDA 12.8 运行时、CPU 与 GPU 差值 `0.00e+00`。
- **在总览图上的位置**：这一步不在数据流里，它是让整张图能跑起来的前提。

## 本步新名词

累计索引见 [glossary.md](./glossary.md)。标注 `→ 第 N 步` 的，是这里只需知道名字、后面才展开的。

- **虚拟环境（virtual environment）**：与系统 Python 隔离的独立依赖空间。本项目的在 `llm-lab/.venv`，删掉重建不会影响机器上任何别的东西。
- **显卡驱动（driver）**：操作系统与显卡之间的翻译，由 NVIDIA 提供。
- **CUDA**：NVIDIA 的 GPU 通用计算平台——一套并行计算接口，加上配套的运行时库。**运行时随 PyTorch 的 wheel 一起分发**，所以不需要单独安装 CUDA Toolkit。
- **PyTorch**：本项目使用的深度学习框架。它提供张量、自动求导、神经网络层，并负责把计算翻译成 CUDA 调用。写模型时你只跟它打交道，不直接写 CUDA 代码。
- **计算能力（compute capability，写作 `sm_120`）**：GPU 的架构版本号。它决定 PyTorch 的 wheel 里有没有为你的卡编译好内核——5070 Ti 是 `sm_120`，所以必须 cu128 及以上。
- **内核（kernel）**：在 GPU 上实际执行的一小段程序。驱动、CUDA、内核版本对不上时，报错就是 `no kernel image is available`。
- **发行包（wheel）**：Python 的预编译安装包。PyTorch 为不同平台和 CUDA 版本分别发布 wheel，所以"装哪个 wheel"是必须先决定的事。
- **显存（VRAM）**：显卡自带的内存。模型参数和中间结果都放在这里，本机有 15.9 GiB。
- **自动求导（autograd）**：PyTorch 记录你做的每一步运算，从而在调用 `backward()` 时自动算出梯度。（→ 第 4 步正式展开；附录 B 讲清了梯度本身是什么）

## 自测详解

答案要点在这里，完整解释在正文对应的小节。

### 1. 驱动够新，为什么就不需要单独安装 CUDA Toolkit？

因为需要的只有前两层：驱动（系统级，要装）、CUDA runtime（**PyTorch 的 wheel 自带了**，不要装）。Toolkit 是**给"要自己写显卡程序"的人准备的**开发工具链——`nvcc`、头文件、profiler。我们用现成算子，不写内核。

还要分清版本关系：驱动是唯一的硬约束，它决定这台机器支持的 CUDA 上限；runtime 必须 ≤ 这个上限；Toolkit 只影响编译，不影响能否运行。

本机 `nvidia-smi` 报告 `CUDA UMD Version: 13.4`，而 PyTorch 内置的是 12.8 runtime——12.8 ≤ 13.4，所以能跑。注意驱动版本号和 CUDA 版本号是两套彼此独立的编号，`617.14` 和 `13.4` 之间没有算术关系，只能查 NVIDIA 的对应表。

### 2. 没有 `sm_120` 内核时，`torch.cuda.is_available()` 返回什么？为什么容易误判？

返回 **`True`**。它只检查两件事——能不能加载驱动、能不能枚举到 GPU 设备，**完全不检查"能不能在这个设备上执行计算"**。

真正的失败发生在**第一次实际执行 GPU 内核时**：`no kernel image is available for execution on the device`。

误判是这样发生的：所有人写代码的第一句都是 `torch.cuda.is_available()`，它返回 `True`，"环境没问题"这个判断就被钉死了。接下来一运行报错，而错误里提到的是 "kernel image"——听着和"我写的模型、数据、形状"毫无关系，于是开始怀疑人生。

还有个细节解释了为什么不同人遇到的现象不一样：wheel 里如果带了 PTX（一种中间表示），驱动可以现场为你的新架构编译内核，于是变成"能跑，但是慢"，或者在某些算子上报错、另一些上正常。

### 3. 为什么必须验证 GPU 与 CPU 的结果一致，而不只看它跑得快不快？

因为 GPU 的失败不只表现为"跑不起来"，还表现为**"跑起来了，但答案是错的"**：新架构上的内核有 bug、驱动有 bug、内存越界读到脏数据、某个算子悄悄 fallback 到错误的实现路径。

这类错误**不会抛异常**。训练会正常跑完，损失会正常下降，代码看起来一切正常——只是模型学的东西是错的。等你发现时可能已经烧掉几小时甚至几天。

而矩阵乘法是所有神经网络最基本的运算。它错了，后面每一步的结论都不可信。脚本花几秒钟做一次 512×512 的比对，换来排除掉一整类静默错误，这笔账在任何情况下都划算。

### 4. `x.grad` 为什么恰好等于 `2x`？

先算数学：

```
y = sum(x²) = x₁² + x₂² + x₃²
∂y/∂x₁ = 2x₁      （其他项与 x₁ 无关，偏导为 0）
∂y/∂x₂ = 2x₂
∂y/∂x₃ = 2x₃
```

所以梯度是 `2x`。输入 `[1, 2, 3]` 对应输出 `[2, 4, 6]`，脚本打印的就是这个。

但**这道题真正的意义不在求导**，而在于验证一套机制：自动求导把每一步运算记成一张图，`backward()` 再沿图反向把梯度算回来。我们验证的是"记录 + 反向"在本机、本版本上工作正常。

它现在看起来平凡，因为这里只有两步运算。但到第 7 步，网络里有几百次运算、八十多万个参数，梯度要完整穿过它们。那时如果中间任何一环记错了图，你能依靠的唯一前提就是：这套机制本身是对的。（→ 第 4 步写训练循环、第 6 步把梯度送进注意力层时，会真正用到它）

`x.grad` 的六条实测行为在 `scripts/step01_grad_demo.py` 里；"梯度到底是什么、为什么沿着它下降就能训练"见 [附录 B](./附录B-梯度.md)。

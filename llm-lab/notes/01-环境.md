# 第 1 步：环境

## 这一步解决什么问题

在写任何模型代码之前，先把地基验证一遍。原因是：**如果 GPU 或自动求导是坏的，后面每一步的报错都会看起来像我们自己代码的 bug**，而你此时还没有能力分辨。花二十分钟把地基钉死，后面能省下大量误判。

这一步不涉及任何语言模型的内容。

## 驱动 / CUDA / PyTorch：三个层次

这三个东西经常被混在一起讲，其实是分层的。

### 谁提供什么

| 层 | 是什么 | 谁提供 | 我们要不要单独装 |
| --- | --- | --- | --- |
| 显卡驱动 | 操作系统与显卡对话的接口 | NVIDIA（系统级，`nvidia-smi` 显示的就是它） | 要，一般随驱动一起装好 |
| CUDA runtime | 让程序把计算提交给 GPU 的运行时 | **随 PyTorch 的 wheel 打包分发** | 不要 |
| CUDA Toolkit | 开发工具链：`nvcc` 编译器、头文件、调试器、profiler | 需要单独装，可多版本共存 | 不要 |

**Toolkit 是给"要自己写 CUDA 内核"的人准备的**——你得有 `nvcc` 把 `.cu` 文件编译成 GPU 程序。我们用 PyTorch 现成的算子，不写内核，所以用不到它。

例外情况：有些库要在安装时现场编译内核，它们会调用 `nvcc`，那时才真的需要 Toolkit。到那一步再说。

### 约束是单向的

| | 版本由谁决定 | 约束关系 |
| --- | --- | --- |
| 显卡驱动 | 你装的驱动 | **决定这台机器支持的 CUDA 上限** |
| CUDA runtime | 随 PyTorch 的 wheel | 必须 ≤ 驱动支持的上限 |
| CUDA Toolkit | 你装的版本 | **只影响"编译"，不影响"能不能跑"** |

三条规则：

1. **驱动是唯一的硬约束。** 本机 `nvidia-smi` 报告 `CUDA UMD Version: 13.4`，即这个驱动最高支持 CUDA 13.4。PyTorch 内置的是 12.8 runtime，12.8 ≤ 13.4，所以能跑。
2. **驱动比 Toolkit 新永远安全，反过来不一定。** 如果装了 CUDA 13 的 Toolkit 而驱动只支持到 12.4，编译能通过，一运行报 `CUDA driver version is insufficient for CUDA runtime version`——错误出现在运行时而不是安装时，很难第一时间联想到驱动。
3. **同一大版本内不要求严格匹配。** CUDA 11 之后引入了小版本兼容：用 12.0 编译的程序能跑在支持 12.4 的驱动上，不必版本号完全一致。跨大版本（12 → 13）不适用。

一个经典误解：`nvidia-smi` 那一行是"**这个驱动最高能支持到哪个 CUDA 版本**"，不是"本机装了哪个 CUDA"。驱动版本号和 CUDA 版本号是两套彼此独立的编号，`616.64` 和 `13.4` 之间没有算术关系，只能查 NVIDIA 的对应表。新版 `nvidia-smi` 已把它改名为 `CUDA UMD Version`（UMD = User Mode Driver），名字更准确，但仍然容易被误读。

### 为什么"装上了却跑不了"

**wheel 里的计算内核是按 GPU 架构编译的。** 本机是 Blackwell（`sm_120`），如果装到的构建里只有 `sm_80` / `sm_90` 的内核，那么 import 会成功、`torch.cuda.is_available()` 甚至会返回 `True`，但一执行计算就报：

```
no kernel image is available for execution on the device
```

这就是 `requirements.txt` 里 `--index-url .../cu128` 的由来——CUDA 12.8 是第一个带 Blackwell 内核的版本。这类「装上了却跑不了」的坑，是从 0 到 1 过程中最消耗人的部分，值得在第一步就认清。误判是怎么发生的，见自测第 2 题的详解。

## 为什么要独立虚拟环境

`llm-lab/.venv` 是本目录专属的 Python 环境。它有两个作用：把 PyTorch 这类体积巨大、版本敏感的依赖与系统 Python 隔开；以及让这个目录可以整体删掉重来，不影响机器上任何别的东西。

它不在 pnpm workspace 里，和 `apps/*` 的 Node 生态互不干扰——两种语言的依赖各自独立，这是刻意设计的。

## 脚本在验证什么

`scripts/step01_check_env.py` 打印几组信息，每组对应后面会依赖的一项能力：

1. **环境**：实际加载的 Python 与 torch 版本。避免「装是装了，但用的是另一个 Python」这种低级错误。
2. **设备**：GPU 型号、计算能力、显存。确认 torch 看到的是你要用的那张卡。
3. **正确性**：同样的矩阵乘法（→ 第 4 步起每天用）分别在 CPU 和 GPU 上跑并比较。**一个又快又错的 GPU 比没有 GPU 更糟**，所以这一步必须做。
4. **自动求导**（→ 第 4 步正式展开）：计算 `d(sum(x²))/dx` 并与手算结果 `2x` 对照。这是整条学习线里最关键的基础设施——第 4 步之后，所有训练都建立在它之上。

最后是矩阵乘法的粗略性能测试。注意代码里那次预热：前几次调用要承担内核选择和显存分配的开销，不预热测出来的数字会明显偏慢。这个细节在后面测推理速度时会反复用到。

## 本步新名词

累计索引见 [glossary.md](./glossary.md)。标注 `→ 第 N 步` 的，是这里只需知道名字、后面才展开的。

- **虚拟环境（virtual environment）**：与系统 Python 隔离的独立依赖空间。本项目的在 `llm-lab/.venv`，删掉重建不会影响机器上任何别的东西。
- **显卡驱动（driver）**：操作系统与显卡对话的接口，由 NVIDIA 提供，是三层里最底层的一层。
- **CUDA**：把计算提交给 NVIDIA GPU 的运行时。**它随 PyTorch 的 wheel 一起分发**，所以不需要单独安装 CUDA Toolkit。
- **计算能力（compute capability，写作 `sm_120`）**：GPU 的架构版本号。它决定 PyTorch 的 wheel 里有没有为你的卡编译好内核——5070 Ti 是 `sm_120`，所以必须 cu128 及以上。
- **内核（kernel）**：在 GPU 上实际执行的一小段程序。驱动、CUDA、内核版本对不上时，报错就是 `no kernel image is available`。
- **发行包（wheel）**：Python 的预编译安装包。PyTorch 为不同平台和 CUDA 版本分别发布 wheel，所以"装哪个 wheel"是必须先决定的事。
- **张量（tensor）**：多维数组，深度学习里的基本数据结构。可以理解成 NumPy 的数组，外加能在 GPU 上运算、能自动记录梯度。（→ 第 4 步起每天用）
- **自动求导（autograd）**：PyTorch 记录你做的每一步运算，从而在调用 `backward()` 时自动算出梯度。（→ 第 4 步正式展开；先说清"梯度是什么"的是 [01b-梯度.md](./01b-梯度.md)）
- **叶子张量（leaf tensor）**：直接创建的、梯度会被保留的张量；中间算出来的张量默认不留梯度。（→ 第 4 步）

## 自测

先自己答一遍再看文末的「自测详解」。

1. 驱动够新，为什么就不需要单独安装 CUDA Toolkit？
2. 如果 PyTorch 里没有 `sm_120` 的内核，`torch.cuda.is_available()` 会返回什么？为什么这种现象特别容易让人误判？
3. 为什么必须验证 GPU 与 CPU 的结果一致，而不能只看它跑得快不快？
4. `x.grad` 为什么恰好等于 `2x`？

## 自测详解

答案要点在这里，完整解释在正文对应小节。

### 1. 驱动够新，为什么就不需要单独安装 CUDA Toolkit？

因为需要的只有前两层：驱动（系统级，要装）、CUDA runtime（**PyTorch 的 wheel 自带了**，不要装）。Toolkit 是**给"要自己写 CUDA 内核"的人准备的**开发工具链——`nvcc`、头文件、profiler。我们用现成算子，不写内核。

还要分清版本关系：驱动是唯一的硬约束，它决定这台机器支持的 CUDA 上限；runtime 必须 ≤ 这个上限；Toolkit 只影响编译，不影响能否运行。三者的完整对照见正文「约束是单向的」。

### 2. 没有 `sm_120` 内核时，`torch.cuda.is_available()` 返回什么？为什么容易误判？

返回 **`True`**。它只检查两件事——能不能加载驱动、能不能枚举到 GPU 设备，**完全不检查"能不能在这个设备上执行计算"**。这两件事以前基本等价，所以没人怀疑它；新架构的卡出现时，它们才分家。

真正的失败发生在**第一次实际执行 GPU 内核时**：`no kernel image is available for execution on the device`。

误判是这样发生的：所有人写代码的第一句都是 `torch.cuda.is_available()`，它返回 `True`，"环境没问题"这个判断就被钉死了。接下来一运行报错，而错误里提到的是 "kernel image"——听着和"我写的模型、数据、形状"毫无关系，于是开始怀疑人生。

所以可靠的检查是两件事：`torch.cuda.get_device_capability()` 确认架构号，以及**真的跑一次计算**。后者正是 `step01_check_env.py` 里 CPU/GPU 比对存在的理由。

还有个细节解释了为什么不同人遇到的现象不一样：wheel 里如果带了 PTX（一种中间表示），驱动可以现场为你的新架构编译内核，于是变成"能跑，但是慢"，或者在某些算子上报错、另一些上正常。同一个架构的卡，装不同的 wheel，表现可能完全不同。

### 3. 为什么必须验证 GPU 与 CPU 结果一致，而不只看它跑得快不快？

因为 GPU 的失败不只表现为"跑不起来"，还表现为**"跑起来了，但答案是错的"**：新架构上的内核有 bug、驱动有 bug、内存越界读到脏数据、某个算子悄悄 fallback 到错误的实现路径。

这类错误**不会抛异常**。训练会正常跑完，loss（→ 第 3 步）会正常下降，代码看起来一切正常——只是模型学的东西是错的。等你发现时可能已经烧掉几小时甚至几天，而且还会去错误的地方找原因。

而矩阵乘法是所有神经网络最基本的运算。它错了，后面每一步的结论都不可信：loss 不下降你不知道该怪模型结构还是该怪乘法。脚本花几秒钟做一次 512×512 的比对，换来排除掉一整类静默错误，这笔账在任何情况下都划算。

### 4. `x.grad` 为什么恰好等于 `2x`？

先算数学：

```
y = sum(x²) = x₁² + x₂² + x₃²
∂y/∂x₁ = 2x₁      （其他项与 x₁ 无关，偏导为 0）
∂y/∂x₂ = 2x₂
∂y/∂x₃ = 2x₃
```

所以梯度是 `2x`。输入 `[1, 2, 3]` 对应输出 `[2, 4, 6]`，脚本打印的就是这个。

但**这道题真正的意义不在求导**，而在于验证一套机制：autograd 把每一步运算记成一张图，`backward()` 再沿图反向把梯度算回来。我们验证的是"**记录 + 反向**"在本机、本版本上工作正常。

它现在看起来平凡，因为这里只有两步运算。但第 4 步之后，网络里有几百次运算、几百万个参数，梯度要完整穿过它们。那时如果中间任何一环记错了图，你能依靠的唯一前提就是：这套机制本身是对的。（→ 第 4 步写训练循环、第 6 步把梯度送进注意力层时，会真正用到它）

`x.grad` 的六条实测行为在 `scripts/step01_grad_demo.py` 里；"梯度到底是什么、为什么沿着它下降就能训练"见 [01b-梯度.md](./01b-梯度.md)。

# 1. 背景与我们要解决的问题

## 一个明确的起点：把已有客户端的能力带到云端

我们已有基于 DeepSeek Harness 的客户端，希望研究它上云需要做哪些工作。客户端能运行，说明已经有可以复用的基础；但云端要持续服务用户，任务的启动方式、数据保存、访问控制和资源管理都需要重新检查。

例如，用户关闭页面之后，任务是否继续？执行程序被回收后，进度存在哪里？两个人同时使用时，工具和文件怎样分开？这些问题决定了上云需要建设哪些服务，也决定了哪些客户端代码可以继续用。

因此，这次调研的一项具体目标，是把“客户端上云”拆成一份有依据的工作清单：已有能力能复用到哪一步，运行环境变化后要改什么，产品还要补什么。

## 从个人使用，走向持续运行的服务

一个需要替用户办事的云端助手，通常要经历一串动作：理解要求、查询资料、调用业务服务、操作网页、保存结果。中间可能要等待，也可能遇到网络故障；用户离开后，任务和结果还得保留。

模型负责理解和判断，围绕模型的运行系统则要负责：允许它使用哪些工具、如何保存进度、什么时候停止、出了错怎么继续，以及如何把过程告诉用户。这次比较的开源框架，就是这套运行系统的不同起点。

DeepSeek Harness 是已有客户端的基础，需要研究它在云端的接法。同时，更广泛的框架探索可以帮助我们理解云端运行有哪些实现方式，各自适合什么需求，需要承担哪些建设和维护工作。

## 现有云端业务还提供了三个观察角度

现有云端业务基于 OpenClaw，使用反馈主要集中在以下方面。这些反馈也帮助我们确定，客户端上云时哪些问题值得提前验证：

**第一，部分过程不好看清。** 任务为什么卡住、执行到了哪里、哪一步改变了业务数据，需要更容易查到。只知道最后“成功”或“失败”，不足以支持排查和运营。

**第二，业务定制较费力。** 通用助手接入具体业务后，会增加工具、状态和规则。例如，下单后必须再次确认订单，某类操作必须禁止，任务结束后还要保存业务凭据。我们希望知道，这些要求能否通过清晰的扩展接口实现，后续升级又要维护多少东西。

**第三，用户增长带来了实例和资源成本增长。** 现有做法按用户启动对应的助手实例来隔离。我们希望研究，能否保留每个用户的独立数据，同时按实际工作量分配计算资源。

这些反馈用于提出问题，原因需要分别验证：过程不好看清可能涉及展示和接入方式，实例数量也与部署方式有关。本轮用官方开源 OpenClaw 搭建独立实验环境，观察相关能力和接入方式；实验结果不直接说明现有云端业务采用了什么实现，也不把使用反馈直接当成框架本身的缺陷。

## 探索更多框架在云端能做到什么

除了已有客户端和云端业务，我们还希望了解更多 Agent 框架的云端能力，为后续业务积累技术选择。这项探索需要独立回答：框架提供了哪些可直接使用的能力，在哪类任务中有价值，做成云端服务还缺什么。

例如，较完整的运行系统可能省去部分任务管理工作；允许自己定义执行步骤的框架，可能更适合业务流程较明确的场景；轻量框架接入简单任务可能方便，但恢复、隔离和资源管理需要另行建设。这些都是要通过实验核实的取舍，不能只凭功能列表判断。

因此，调研也要为每条路线留下能力和适用范围的记录。当前只完成初筛的候选，可以先明确已知能力与待验证问题；当未来业务需要它的特点时，再决定是否深入。

## 把三类需求落到共同的云端能力上

| 要检查的环节 | 云端服务需要明确或补齐什么 | 实验要回答什么 |
| --- | --- | --- |
| 任务运行 | 提供可以在后台启动、持续执行和结束任务的入口 | 在独立的后台环境中，选定运行方式能否完成同一段业务？ |
| 工具与浏览器 | 逐项检查桌面程序、本机路径和登录环境等依赖，确定服务端接法 | 在独立运行环境里，助手还能否查询、操作网页和提交结果？ |
| 进度与文件 | 将任务进度、业务记录和工作文件保存到执行程序之外 | 程序关闭或突然退出后，新程序能否继续，且不重复提交订单？ |
| 用户接入与控制 | 将用户身份绑定任务，提供进度查询、暂停、继续和取消 | 自己的任务能否正常控制，别人的任务和文件能否隔开？ |
| 业务规则与过程展示 | 接入工具、执行限制和过程记录，明确各自的维护位置 | 新规则是否真正生效，出了问题能否查清具体步骤？ |
| 资源分配与回收 | 按实际任务安排执行资源，处理空闲、唤醒和回收 | 能否减少等待期间的占用，代价是多少启动时间和额外工作？ |

这组能力既用于盘点客户端上云工作，也用于比较现有云端方案和其他框架。具体到每条路线，要区分框架已经提供的能力、接入时需要调整的部分，以及产品还要补建的服务。它不表示现有客户端或任何候选缺少表中全部能力。

这里要区分研究目标和受测对象：客户端上云是我们要解决的问题，实际运行的是官方开源 DeepSeek Harness 加实验接入代码；OpenClaw 同样从官方开源版本构建。自有产品的修改、配置和依赖还需要另行对照，不能直接继承实验的通过或失败结论。

这些目标彼此有关。例如，想把执行程序关掉省资源，就必须先保存进度；想从进度继续，就必须知道哪些订单已经提交，否则可能重复下单。只有能解释这些关系，资源优化才不会以业务正确性为代价。

## 这次调研要支持什么决定

本轮希望形成三项产出：现有 DeepSeek Harness 客户端的上云工作清单、OpenClaw 云端业务相关问题的验证与改善方向，以及更多框架的云端能力、适用条件和补建工作记录。

具体业务和研发时间会影响选择。近期可以集中验证最有价值的问题，同时保留其他路线已有证据与缺口，供后续需求变化时参考。这样既能推动眼前的上云与改造，也能积累更广泛的技术判断。

实验范围围绕通用助手展开：调用工具、操作网页、处理业务，普通的授权内操作自动执行，明确禁止的操作直接拒绝。任务恢复重点是进度、业务记录和工作文件；网页可以重新打开、重新登录，不要求原样恢复每个标签页。

有了这些目标，下一步就能设计一段共同任务，再逐步增加变化，观察不同方案在哪里省事、在哪里需要我们补代码。

# 实验方法：比较的对象、控制条件与验收口径

资料截点：**2026-10-21 11:49:45（Asia/Shanghai）**。本篇依据该截点保存的计划、配置、代码及验证报告撰写，解释实验怎样产生结论；不重新运行候选、不重新评分原始证据。各路线结果见 [实验结果](02-results.md)，判断与取舍见 [分析](03-analysis.md)，未覆盖范围及下一步见 [限制与后续验证](04-limitations-and-next.md)。

## 1. 研究问题与结论适用范围

本仓库研究的是：在业务尚未最终确定、研发时间有限的条件下，哪条开源 Agent Harness 路线值得继续投入，能够支持工具、浏览器、可观察的执行过程、业务定制，以及释放计算资源后的任务继续。它同时比较“继续改造现有 OpenClaw”“迁移到另一套 Harness”“使用 SDK 补齐产品运行管理”的建设边界。

这里的 Harness 包含模型与工具循环、执行状态、控制接口、持久化与恢复机制。一个框架能够调用模型，并不意味着产品后端身份、云端任务管理和实例回收也已经具备。实验因此分别记录候选自带能力、官方配套、业务接入和公共实验设施，避免把实验控制器实现的功能归给框架。

用户已经说明现有业务按用户启动 Agent 实例，但没有确认完整的现网版本、配额、回收策略和账单。本实验中的“每用户常驻且不回收”是显式对照假设，Hogee 源码仅作技术参考。当前没有具体业务权重，因此实验支持有条件的投入建议，不计算综合名次，也不直接宣称迁移后的现网节省比例。

来源：[研究计划](../../../../RESEARCH_PLAN.md)、[需求](../../../../REQUIREMENTS.md)、[比较报告](../../../validation/comparison.md)。

## 2. 候选筛选是分阶段研究，不是八路线同等深度比赛

| 阶段 | 范围与目的 | 形成什么证据 |
| --- | --- | --- |
| 来源与初筛 | DeepSeek Harness、OpenClaw、Deep Agents + LangGraph、Pi Agent Core、Google ADK、OpenAI Agents SDK、Codex SDK、OpenHands，共八条路线 | 核对开源范围、固定源码与依赖、合适的运行入口；同镜像两个全新容器的真实工具任务及累计请求限额 |
| 同题详细验证 | DSH、OpenClaw、Deep Agents、Agents SDK | 五类正式任务使用 101/202/303；另测诊断、取消与最小原生状态冷读；保存成功、失败和接线修正 |
| 生命周期专项 | DSH、Deep Agents | 各自单独冻结暂停、故障等入口，先做同变体基线，再检验真实暂停与突然退出；其他路线保留未测边界 |
| 最终输入补充 | DSH、Deep Agents 的五类基本任务补 404/505 | 增加输入覆盖，但按候选和判定材料分组；不是把所有阶段拼成一次同镜像大批次 |
| 产品边界与成本探索 | 当前实际接入 Deep Agents | I24 模拟产品后端下的双用户控制；I25 独立 resident 入口下的常驻/按需比较 |

选择四条详细路线的理由分别是用户优先关注 DSH、现有业务对照 OpenClaw、持久图执行代表 Deep Agents、轻量应用 SDK 代表 Agents SDK。I21 再选择 DSH 与 Deep Agents 做专项，依据已取得的结果与原生恢复接入路径。Pi、ADK、Codex、OpenHands 没有进入同等深度验证，表示本轮投入暂缓，不能转述为不支持相关能力。

本研究是逐步收窄范围的工程实验。越到后续，材料与实现越具体，不能把初筛 SDK、详细入口、Goal 入口和 resident 入口视作同一个未经变化的处理条件。来源：[初筛](../../../validation/screening.md)、[专项选择](../../../validation/selection.md)、[实施计划](../../../../IMPLEMENTATION_PLAN.md)。

## 3. 实验单位、数据与可比性

### 3.1 一条 run 或一条恢复链才是基本单位

普通单任务的实验单位包括候选、入口/profile、源码和接入摘要、候选/bench/services 镜像完整 ID、任务定义哈希、模型、seed、scope、预算和资源配额。任务 scope 为 `experiment_id / variant / user_id / session_id`。相同名称或浮动镜像标签不足以认定两轮材料相同。

恢复实验使用一条逻辑 chain：A、B 是同一任务的不同 attempt，改变容器 ID 和输出目录，但保留原 scope、原生状态、工作区、业务账本与模型预算。B 不能重新 prepare 场景、获得新预算或重新提交原 prompt。相反，无故障基线、故障变体、不同 seed 和不同写模式使用独立目录与账本，防止前一轮的状态帮助后一轮通过。

### 3.2 seed 固定业务数据，不固定模型输出

商品数据由 `seed XOR SHA256(user_id + "\0" + session_id)` 派生随机源生成。商品总数为 `17 + seed % 9`，类别在 office、kitchen、garden、travel 中循环，价格为 100–5000 整数分，库存为 1–20。验证种子 101/202/303 对应 19/21/23 条商品，最终补充 404/505 对应 25/18 条。

相同 seed 与用户/会话产生同样的商品；不同 variant 可以保留相同输入而隔离副作用；不同用户/会话的价格库存发生变化，有助于暴露串数据。种子并不固定模型采样、网络时延、调度和页面交互次数。每个种子一次运行不是多次随机重复，不能从三组或五组输入推断总体成功率。

候选只获得任务要求和允许的工具、页面信息，不获得标准答案。验收器使用同一确定性数据生成器重新筛选、排序并计算金额；“独立验收”是指不相信模型最终回答或候选自报结果，不意味着另有一套完全独立的数据生成实现。来源：[数据生成器](../../../../fixtures/data/generate.py)、[公共判分](../../../../runner/grading.py)。

### 3.3 实际统一的条件与允许的差异

| 条件 | 实际口径 | 解释边界 |
| --- | --- | --- |
| 执行环境 | 候选、工具、浏览器、业务服务与验收都在本机 Linux arm64 Docker；宿主只编排与观测 | 不借宿主 Node/Python 依赖执行候选；这也不等于强制每用户一个容器 |
| 模型 | 已选远程 `deepseek-v4-flash`，实际 API 别名单列；不换模型或用协议转换掩盖不兼容 | 原生 API 轨道、框架默认提示与工具包装仍可能不同 |
| 预算 | 通常每逻辑任务 300 秒活跃时间、20 次代理请求、最多两次 SDK 重试 | 恢复累计；SDK turn/Goal round 不是 API 请求次数；本地注入也占额度 |
| 输出上限 | 支持的详细入口请求 4096 输出 token | 不支持硬上限的候选明确记录，不能声称所有初筛入口控制完全相同 |
| 普通/敏感策略 | 普通 scope 内写入自动执行；敏感操作执行前直接拒绝，无审批等待 | 不建设完整生产规则分类或审批系统 |
| 任务与工具 | 相同目标、筛选规则、业务状态、工具语义、站点和结果标准 | 允许原生工具、MCP、SDK、薄桥接不同；不给个别候选一键完成全流程的优势 |
| 资源 | 总额度不超过 6 GiB/3 CPU；详细单 Worker 通常 2 GiB/1 CPU | I24/I25 为容纳两活跃任务改用每 Worker 2 GiB/0.75 CPU，并单独做新入口基线 |

这是一项“同目标、同约束下的整套接法比较”。框架提示、状态语义、官方插件、工具包装与协议差异无法全部消除，它们是方案实际表现的一部分。报告需要记录这些差异，而不能仅凭同一个模型名就说所有实验条件完全相同。来源：[全局配置](../../../../configs/experiment.yaml)、[详细矩阵](../../../validation/detailed.md)、[多用户配额](../../../validation/multi-user-design.md)。

## 4. 九项任务怎样检验能力

### 4.1 固定镜像运行：排除一次性环境成功

runtime 要求从固定镜像新建容器，真实调用选定模型与一个业务查询工具；删除后再次从同一镜像创建不同 ID 的容器复现。记录来源、依赖锁、架构、镜像、配置摘要及挂载，正式代码和依赖必须在镜像中。这证明可复现运行，不证明新容器能够接回未完成任务。[任务定义](../../../../configs/tasks/runtime.yaml)。

### 4.2 工具任务：用可核对的多步业务做共同底座

Agent 读取 `request.json`，每次查询最多 5 条，直到看完商品目录；选择 office/garden、单价不高于 3500 分、库存至少 2 的商品，按单价升序、编号升序取至多 3 件，每件买 2 个。operation ID 由固定前缀和商品编号组成，最后输出包含完整 scope、选择顺序、数量、价格、金额与总额的 JSON。

正确商品和金额只是一部分要求。“查全分页且每页不超过 5 条”本身也是任务契约。因此，报告和三笔写入正确，但只读了部分目录或请求每页 100 条，仍判完整业务失败。这能检验约束保留与工具使用过程，也说明当前任务的通过率不能简化成“选购最终结果正确率”。[任务定义](../../../../configs/tasks/tools.yaml)、[预期计算与工具判分](../../../../runner/grading.py)。

### 4.3 浏览器任务：让模型真正逐步操作页面

目标是登录本地账号，跨页找到 `item-{seed}-08`，读取页面库存，购买 `min(5, 库存)`，填写指定 operation ID，提交、查看回执并下载 CSV。只暴露导航、页面读取、点击、填写等基础动作，禁止业务 HTTP 写入工具或预写全流程脚本替代页面操作。

验收同时看独立账本、CSV 中真实回执、网站服务端动作，以及原始浏览器工具调用。要求登录、多页、表单、提交、回执、下载，不能仅凭截图、正确文件名或“浏览器工具接通”通过。任务不要求暂停后恢复网页现场。[任务定义](../../../../configs/tasks/browser.yaml)。

### 4.4 暂停恢复：受控安全点与真实资源释放

同一专项入口先做不暂停基线，再执行 101/202/303 的暂停链。可信宿主观察到真实任务活动和业务进展后，才发送外部暂停请求；候选收束到安全点、保存原生进度、正常关闭，确认旧 Worker 退出并删除。等待至少 600 秒，期间持续观测工具/模型静默和所有保留服务；随后同镜像新 Worker 从原状态继续，累计仍受 20 次请求和 300 秒活跃时间约束。等待时间不算活跃预算，恢复冷启动算入。

两种候选的安全点不同：

- **DSH** 使用官方持久 Goal、driver 与 checkpoint 插件，在公开 pre-step 边界处理暂停；保留真实 blocked turn、paused/disarmed Goal、空 inbox 与成功 flush 证据。B 恢复原 Session/Goal 后，由官方 driver 继续目标，不重发 prompt。已验证最小范围为无并发 followup/steer/inject、claimed 输入为空的单任务边界；不是恢复任意内存指令位置。
- **Deep Agents** 使用 `RunControl.request_drain`，当前 superstep 完成后实际产生 `GraphDrained`，同步保存 checkpoint 并关闭 SQLite saver。B 先核对保存点及当前 head，再用原 thread/namespace、`None` 输入继续；执行时不带 checkpoint ID，避免把历史重放当成续跑。保存的下一节点可以存在，已在途的模型/工具调用必须收束。

最终除 tools 业务判分，还核对 A 已完成的 operation ID 在 B 没有再次派发 write。最终账本没有重复不能单独通过，因为服务端幂等可能掩盖重发。专项输出原生暂停/继续、完整业务、资源/预算三类结论，全部满足才是完整链通过。截点已有六条真实链：两路线原生恢复各 3/3，DSH 完整业务 3/3，Deep Agents 完整业务 1/3；不能继续把 I22 写成未开始。[设计](../../../validation/pause-recovery-design.md)、[已执行报告](../../../validation/pause-recovery.md)。

### 4.5 故障恢复：把“没写”和“写了但没收到”分开

故障专项以同一 tools 任务为基础，交叉四类故障与两种写模式：

| 故障 | 可信注入窗口 | 要排除的错误解释 |
| --- | --- | --- |
| model_timeout | 计数代理第 1 次请求返回本地 504，不转发远程 | 重试应计入原预算；注入 504 不是一次远程收费请求，也不等于真实网络空闲超时 |
| fail_once | 指定 operation 的提交前返回一次 503 | 请求已经发生但未提交，不应把它算成成功写入 |
| kill_before_write | 真实写前栅栏处，确认活动后强杀 A，删除后绑定 B | 不先 flush 制造受控暂停；137 作为注入异常退出保留，不称健康关闭 |
| drop_receipt_once | 服务端事务已提交，随后断开响应 | 客户端失败不代表业务未发生；盲目重试可能在非幂等服务中重复写 |

fault 和写模式由管理员准备，Agent 无权选择。故障消费次数持久化，重复准备不能把已消费故障重新装回。同一故障链 A/B 共用原状态/预算，其他格完全隔离。判定同时记录请求数、真实 write_count、回执查询、原生恢复、过程与最终处理方式；自动完成、明确失败、需要人工确认分开报告。

每路线完整安排为：两模式 seed101 正常基线 2 格、seed101 非幂等四故障冒烟 4 格、四故障×两模式×三种子的正式 24 格、补 202/303 正常基线 4 格，以及最终 kill/drop×两模式×404/505 的 8 格。截点两路线冒烟均已结束，DSH 正式有效完成 1/24，第二格因资源采样完整性停止；不能将这格归为候选能力失败。[任务定义](../../../../configs/tasks/fault-recovery.yaml)、[执行协议与结果](../../../validation/fault-recovery-execution.md)、[最新汇总](../../../validation/comparison.md)。

### 4.6 流程透明与执行控制：效果与证据都要存在

普通写入成功是正例，敏感请求被执行层直接拒绝是反例，避免“全部拒绝”也得高分。敏感场景要求真实触发 `sensitive_export` 的执行拒绝、无副作用、不等待审批；如果模型自行拒绝而没有调用，说明安全效果存在但没有覆盖执行规则测试路径，不能改说越权，也不能算执行层已经验证。

缺文件工具错误、代理首次 504、真实运行中取消分别测试。取消依候选公开接口及原生语义判定，保留在途请求与已提交效果，确认生效后不能新派发写入。协作 drain、立即取消、整 Gateway 停机不是同一种能力；“能看到日志”也尚未证明定位故障更省人工时间。[任务定义](../../../../configs/tasks/control-policy.yaml)、[详细判分](../../../../runner/detailed.py)。

### 4.7 业务定制：加工具、业务状态和执行规则

普通扩展任务仍购买每件 2 个，但要求每次写后显式调用新增 `query_order_status`，读取真实 receipt/write_count，并把 operation 与确认状态保存在候选原生持久状态中。验收核对新增调用、原生状态引用及其文件内容与真实账本，而不让接入层代替 Agent 完成后续流程。

数量规则上限设为 3，另一个任务明确要求购买 4 个且不能改小：应在 HTTP 写入前被真实规则拒绝。它与 quantity=2 普通任务配对，防止把所有写入阻断也算定制成功。冷读还要删除旧 Worker、用新容器无模型读取原状态；冷读只证明存储可重建，不能代替未完成任务续跑。

同时记录公开接口、内部导入、官方配套、接入代码和维护面。文件行数、自动构建时长不等于人工投入；未实际升级就不报告升级通过。[任务定义](../../../../configs/tasks/business-extension.yaml)、[工程清单](../../../validation/engineering-inventory.md)。

### 4.8 产品后端与作用域：授权必须来自可信身份

I24 的模拟后端从 HTTP Authorization 得到 A/B 身份，查 task owner 后才路由到固定 Worker；客户端不能靠 body 中的 user ID、路径或信号目标改变归属。每用户主任务分别完成读取、暂停、换容器恢复与重连；独立取消子任务检验取消，避免把主任务取消后重发伪装成连续执行。

六类越权探针是 state、events、artifacts、pause、resume、cancel。A 指向真实 B 任务应拒绝且无 B 内容，B 的独立前后快照不受影响；自己的同类操作必须正常。resume 越权要在 B 已被本人合法暂停后测试。为排除 B 自然进展导致的快照变化，可在真实只读工具等待窗口比较；这个窗口不替代有效并发证据。并发另要求双方真实模型/工具进展重叠，重连要求真实旧连接关闭、新连接认证及同一原任务归属。

截点 Deep Agents 新 removal101 轮的边界、重叠、重连和资源生命周期已通过，A 主任务及两取消通过，B 主任务业务失败，整轮仍 false；202 仍在运行。该结果属于独立模拟后端、独立 Worker 和固定 multi-user 入口，尚未证明已有产品租户后端、浏览器使用期隔离或同 Worker 跨用户复用。[原任务](../../../../configs/tasks/scope.yaml)、[真实接线协议](../../../validation/multi-user-design.md)。

### 4.9 实例成本：固定工作量比较常驻与按需

计划保留 2/5/10 个用户状态，始终只有两个真实活跃任务，在同一总配额内比较每用户保留真实候选对象与只保留状态、按需启动回收。不能用空壳容器当常驻，也不能少执行或串行排队来获得低内存。

当前 Deep Agents resident 探索每进程绑定一个用户，不实现同进程跨用户复用。常驻保留真实 graph、模型客户端、工具桥和 saver；按需正常关闭并删除 Worker。完整流程含初始 60 秒空闲、两真实任务重叠、结束后 60 秒空闲、原业务 checkpoint 保留/新容器冷读、两个新的唤醒任务，以及干净故障任务中只杀 A、观察 B 后续进展。这里的唤醒是新任务，故障 A 不恢复，不能与 I22/I23 原任务恢复混为一谈。

两策略使用相同候选、bench、services、seed101 与 pair ID，各五个可评分业务 3/5，整轮仍失败。生命周期和资源有效观察可以保留，但正式业务门槛、resident 入口自身的 I24、真实产品后端和更多规模尚未完成，保持 `formal_i25_eligible=false`、`i25_complete=false`、`savings_percent=null`。N=5/10 常驻因冻结配额超限在 Docker 启动前拒绝，`observed_RSS=null`；不是实测 OOM 或框架容量上限。[原任务](../../../../configs/tasks/instance-cost.yaml)、[成本流程与结果](../../../validation/instance-cost-flow.md)、[resident 边界](../../../validation/resident-runtime.md)。

## 5. 独立验收怎样避免“看起来成功”

原生结果、业务正确性和实验完整性是三个分开的判断：

| 层次 | 需要什么 | 不足以替代它的材料 |
| --- | --- | --- |
| 业务结果 | 独立种子重算、完整报告/CSV、真实账本、分页和写入审计、scope | 最终回答称完成、正确文件名、只看最后一笔写入 |
| 原生行为 | 实际执行事件、持久状态、公开控制 API、真实开始/结束与恢复链 | 外层 paused/completed 标签、只存聊天记录、只看接口存在 |
| 实验完整性 | 冻结来源、工具审计配对、真实注入、原预算、Docker 状态、资源采样与清理 | 评分文件写了 passed、容器 exit code 单值、缺测补零 |

公共 tools 判分是所有检查取 AND，不通过平均分抵消漏项。审计要求 call_id 唯一且 start/finish 配对；完整账本计数与 scope 一致；实际请求和写入能与工具事件对应。browser 增加网站路径和原始工具动作；扩展与控制任务增加真实规则、状态来源与原生证据。

专项还校验评分进程本身：正确完整容器 ID、镜像、配额、PID=0、无 OOM/异常状态，退出值与原判定一致。受控业务失败可以是一次有效实验；缺日志、错误材料、采样超限、评分过程异常等完整性失败应停止并归因。测试中故意 kill 的 137、正常服务关闭、候选自然结束也分别记录。费用闭合只说明付费进程/路由结束，不能自动改判业务成功或全 trial 清理健康。

判定器先用正反样例校准，再运行真实候选。合成测试通过不能计作候选能力。发现评分器误解固定原生格式时，可使用新固定 bench 对原材料断网、只读追加复核，保留旧 verdict 与哈希，不重写历史、不重复计算模型用量；DSH 的 GoalSpec/GoalView 与会话头默认字段已有这种处理。来源：[公共判分](../../../../runner/grading.py)、[详细判分](../../../../runner/detailed.py)、[暂停复核记录](../../../validation/pause-recovery.md)、[资源预算口径](../../../validation/resource-budget.md)。

## 6. 资源、请求与费用怎样计算

### 6.1 配额验收与实际占用是两种数

每阶段先冻结完整容器清单，再用归属标签发现实际容器逐一比对；所有运行 Worker、工具、代理、Fixture、后端或观察器、短时 bench 都计入总配额。Docker 配额 0 表示无限，不能当作零成本。I24 两 Worker 活跃阶段为 5.5 GiB/3 CPU，离线评分在执行容器停止后运行；I25 观察容器占用预留给后端的档位，但不提供真实身份服务。

实际占用从原始 Docker 样本汇总，目标每 2 秒一次，真实间隔、缺测和错误保留。Docker PIDs 含线程，不直接称进程数；真实进程清单另存。样本均值、峰值不是时间加权平均、CPU 秒、内存时间积分或云账单。暂停六链已观察到等待期 Worker 为 0，但 Fixture、工具、代理和监测仍占内存；不能说暂停总成本为零。

I25 两用户配对的内存是整套实验容器样本均值，包含 Fixture 和观察器，不含宿主/VM、真实产品后端及生产存储费。请求至首次原生活动包含实验服务/容器准备，没有产品队列，不等于 API 端到端延迟。当前不能计算空闲用户从 2 增至 5/10 的实测内存斜率，也不能用配额预拒绝代替 RSS 数据。

来源：[资源预算](../../../validation/resource-budget.md)、[暂停资源摘要说明](../../../validation/pause-recovery.md)、[成本探索](../../../validation/instance-cost-flow.md)。

### 6.2 请求占额、远程调用、token 和金额分别记

代理在请求转发前持久 reserve 一次额度。重试、失败和恢复仍计入同一逻辑任务的 20 次；注入 504 会 reserve 但不转发远程，内网模拟请求也不是远程模型消耗。`client_disconnected` 或只有 `reserved` 的记录保留未知，不补成远程成功，也不当成零费用。401/额度耗尽429在 reserve 前拒绝，当前 calls 表不能给出这些实际拒绝次数。

比较成功任务用量前，先固定任务、候选变体/镜像、模型、输入、预算和资源组，然后计算：

```text
每成功业务任务请求用量 = 本组全部尝试的实际远程模型请求数 / 本组完整成功业务任务数
每成功业务任务费用 = 本组全部尝试的可核验费用 / 本组完整成功业务任务数
```

失败和重试不能从分子删除。分母为零时只报告总尝试、失败与消耗；敏感拒绝、取消、诊断、无模型校准、冷读和应用准备历史单列，不充当成功业务任务。未知远程结果须在分子边界中单列；不能用 reservation 总数直接报价。

一个请求的输入、输出、缓存和推理 token 可能差异很大。当前尚无四路线正式任务统一、去重后的 token 与可靠计费单价，金额保持 unknown；全局 `$1` 只是参考值，不是已实施的美元限额。人工开发/调试时间和真实版本升级实验也未知，物理行数、依赖条数与缓存构建秒数不能代替它们。

截点最近的 enrollment-006 研究清单覆盖 238 个明确闭合预算库、1528 条 reservation；这是登记范围内的累计投入，含成功、失败和中止。新 I24 removal 与本次 DSH formal 尚未纳入，其他未留/已删临时库也可能缺失，不能称完整研究账单。恢复 A/B、原判定和离线复核共用同一预算库，物理去重后只计一次。[用量台账](../../../validation/costs.md)、[比较组与分母](../../../validation/comparison.md)。

## 7. 原计划与实际执行的差异如何处理

| 原计划或常见预期 | 截点实际情况 | 报告处理 |
| --- | --- | --- |
| 九项任务全部有配置就已完成验证 | YAML 协议先冻结，部分 `grading_status` 仍保留早期 pending；真实专项另有代码与报告 | 进度依实施计划与最新已结束原件，配置用于解释协议，不单独作为执行状态 |
| 四路线详细结果来自统一不变的一套镜像 | DSH 业务态保存接法、最终补充与多个专项发生材料变化；bench/进程判定也升级 | 保留材料分组；不拼出未执行过的新镜像15/25轮完整批次 |
| 暂停/故障/隔离/成本必须等业务都通过才有任何信息 | 纯业务分页失败时，模型、原生状态和观察轨道可能仍完整有效 | 可进行明确标记的独立机制探索；业务和整轮失败仍保留，完整性错误仍停止 |
| I22 恢复通过即可证明故障和多租户能力 | I22 是已收束调用的受控安全暂停；I23 是突然退出/未知回执；I24 是可信后端边界 | 三类证据分开，不用一种机制通过代替另一种 |
| 成本档位2/5/10都已实测 | I25实际只有两用户单种子常驻/按需探索；常驻5/10预拒绝，按需5/10未测 | 不给5/10 RSS、容量、节省比例或生产成本结论 |
| 独立后端隔离可以自然移用到resident入口 | I24 multi-user 与 I25 instance-runtime 是不同接法；成本观察器也不是产品后端 | 新入口自身身份/控制和真实产品开销仍列为缺口 |

固定任务的失败不能通过放宽分页、增加预算、删除失败样本或反复挑选成功覆盖。材料和判定器确有问题时，先留下原因，使用新材料、新 ID 校准；能够只读复核的评分错误则追加新结论而保留原件。这样得到的是每个具体接法的证据边界，而非一个脱离实现与版本的抽象框架分数。

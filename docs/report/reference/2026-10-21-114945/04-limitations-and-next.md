# 限制与后续验证：哪些证据还会改变选择

资料截点：**2026-10-21 11:49:45（Asia/Shanghai）**。本篇只依据截点已保存材料描述缺口和下一实验；不启动实验、不改原判定、不预填仍在运行的结果。方法见 [实验方法](01-methodology.md)，已取得的分项结果见 [实验结果](02-results.md)，目前的取舍见 [分析](03-analysis.md)。

## 1. 先限定现在能够决定什么

当前已足以判断四条详细路线的工具、浏览器、扩展接法确有区别，也足以确认 DSH 与 Deep Agents 在固定三种子下能够安全暂停、删除 Worker、等待 600 秒并从原生状态继续。它们的原生恢复均为 3/3，但完整业务分别为 3/3、1/3，后者两次分页失败仍有效。

故障专项已经越过“只有接口材料”的阶段：两路线均有真实杀进程、换容器恢复证据。Deep Agents 也已有模拟后端下的双用户授权、真实重叠与重连证据，以及两用户常驻/按需资源探索。与此同时，正式故障矩阵未完成、双用户完整业务仍有失败、成本入口与产品授权未闭合，尚不足以决定产品迁移、生产可靠性或现网节省比例。

因此下一轮应围绕可能改变选择的证据推进，不把所有候选同时扩建成完整平台，也不为追求全绿反复重跑同材料。源依据：[最新比较](../../../validation/comparison.md)、[实施计划](../../../../IMPLEMENTATION_PLAN.md)。

## 2. 决策问题、最小下一实验与建议变化

### 2.1 现有任务失败，来自模型约束执行还是恢复机制

**缺证据。** 多轮 Deep Agents/OpenClaw/SDK 的业务失败是漏读分页或每页超过 5 条；Deep Agents 还出现过选错商品。报告、账本、原生完成及状态保存可能同时正确。现有三/五种子很少，无法判断这些失败在目标业务中的频率，也无法把同模型下的差异完全归因于框架。DSH、Deep Agents、SDK 的部分浏览器轮次用满 20 次预算，成功也缺少页面变化或重试余量。

**最小下一实验。** 先冻结一个接近实际业务的任务分布和通过标准。在不修改原实验的前提下，为最关键的分页、选品和浏览器约束增加少量预先登记的新输入，并区分“最终业务结果正确”“过程约束完整”“原生结束正常”。若考虑把分页上限或敏感规则下沉到工具执行层，应单列新变体、同条件重做基线，不能用新规则回评旧失败。

**可能改变建议。** 若目标业务可通过确定性工具契约降低模型错误，Deep Agents 的明确图控制价值可能高于旧任务的完整通过数所示；若必须依赖长页面链且预算严格，则有调用余量的接法更重要。新结果只能改变明确业务场景下的建议，不能直接产生通用框架排名。

来源：[详细矩阵](../../../validation/detailed.md)、[比较任务分组](../../../validation/comparison.md)。

### 2.2 安全暂停能否覆盖真实产品输入与更复杂停点

**缺证据。** I22 已完成约定三种子研究，但只覆盖固定工具任务和已收束的模型/工具调用。DSH 的最小暂停路径要求 claimed 输入为空、无并发 followup/steer/inject、inbox 为空；其机制是持久 Goal 继续。Deep Agents 是 superstep 边界 drain 后从 checkpoint 下一节点继续。两者都不是任意指令位置的内存快照，不能证明并发用户输入不丢、在途写入被撤销或浏览器现场恢复。

**最小下一实验。** 由目标产品先选一种真实需要的停点，例如模型进行中收到追加输入，或多个工具并行时收到暂停。只给一个候选新增这一条协议，预先定义哪些调用允许收束、输入队列怎样保留、谁持有唯一恢复权；删除 Worker 后检查原输入、待办和已提交操作，保留全部失败。暂不扩展浏览器现场恢复，除非业务确实需要。

**可能改变建议。** 如果复杂输入保存需要显著的应用状态机或内部接口，现有“薄接线即可恢复”的建设估计要上调；如果业务本就允许任务边界协作暂停，现有 I22 的证据已经更贴近需求，不必为了抽象完整性追求任意时刻冻结。

来源：[暂停设计的安全点约束](../../../validation/pause-recovery-design.md)、[暂停结果](../../../validation/pause-recovery.md)。

### 2.3 故障后能否可靠处理业务结果不确定

**缺证据。** DSH seed101 非幂等四故障冒烟 4/4；Deep Agents 同范围 2/4，另两条原生恢复有效但分页失败。正式矩阵尚缺大量格子。截点 DSH 正式 24 格批仅第一格 model_timeout/幂等/101 有效通过；第二格202的业务结果通过，9 项外层检查中 8 项通过，仅资源采样因 `fault_resource_sampling_gap` 失败，使整批完整性停止。这一格不能计为框架失败，也不能补成完整通过。

**最小下一实验。** 先只读定位第二格采样空档的原因，在新固定 bench 中校准观测链；保持原判定和费用。修正后按明确的新运行 ID 继续尚未完成的四故障×两模式×三种子矩阵，并补同镜像 202/303 正常基线；最终路线再做 kill/drop 的404/505关键窗口。每格继续分列业务、故障命中、原生恢复、已提交操作重发、资源/过程完整性与最终处置。

**可能改变建议。** 非幂等丢回执后仍无重复派发、且能完成原业务，会直接加强迁移或自建路线的可靠性依据；若只能明确失败或转人工，也应计作可控边界，并测补齐成本。幂等服务最终一条写入不证明候选 exactly-once；所有路线都不能仅据一次注入成功获得生产可靠性保证。

来源：[故障执行报告](../../../validation/fault-recovery-execution.md)、[最新正式批状态](../../../validation/comparison.md)。

### 2.4 当前隔离证据能否支持已有产品的多租户接入

**缺证据。** Deep Agents removal101 轮已完整执行，授权边界、真实并发、重连和资源生命周期通过，A主任务及两取消通过，B业务失败，整体 false；独立202在截点仍运行。模拟后端不是已有产品租户后端，当前是每用户独立 Worker/工具/代理和固定凭证绑定。浏览器账号/cookie/context 使用期隔离、同 Worker 跨用户复用、更多种子以及 DSH 后端接入都未完成。

**最小下一实验。** 先收取202的原始结果，不预判；继续已计划的独立种子并保留业务失败。选中拟产品化的入口后，把同样六类 state/events/artifacts/pause/resume/cancel 探针接到真实产品身份映射，验证 A 指向真实 B、重连后再次越权、过期 attempt 与控制目标绑定。浏览器隔离如属必需，增加实际登录/cookie/下载文件的 A/B 探针。共享 Worker 只有在明确需要省掉这层成本时才单列试验。

**可能改变建议。** 若产品已有可靠后端授权且独立 Worker 足够经济，现有接法可能只需较薄路由；若目标要求同进程共享，当前结果几乎不能回答其安全边界，研发成本需重新估计。不能用不同 user/session 字符串或一个共享 Gateway 代替真实授权证据。

来源：[多用户协议及实际结果](../../../validation/multi-user-design.md)。

### 2.5 按需是否在相同工作量下更经济

**缺证据。** 当前只完成 Deep Agents instance-runtime 的两用户 seed101 配对探索；常驻和按需各五个可评分业务3/5，故障A没有结果且不恢复，fault-B都漏读分页。两策略的生命周期、状态保留/冷读、两项新任务唤醒、观察/采样/关闭与清理有效，但完整成本验收仍 false。这个入口也未接 I24 的真实身份流程，256 MiB/0.25 CPU观察器占用后端预留档位却不提供产品后端功能。

**最小下一实验。** 先解决或明示同入口业务门槛与授权边界，再对已选定入口用预先登记的三种子重复完整配对。保留两个真实活跃任务，加入未活跃用户轮换；在现有6 GiB/3 CPU内验证按需 N=5/10，记录真实样本、状态字节、冷启动、额外模型调用。常驻 N=5/10 若需降低每 Worker 配额才可启动，应另立新配额变体、重跑对应基线与两种策略，不能把低配额结果接到原对照上。

**可能改变建议。** 两用户探索已显示空闲内存与启动等待的取舍：初始/回收后空闲整套样本均值按需31.41/47.85 MiB、常驻282.10/312.63 MiB；活跃阶段约390 MiB接近。按需请求到首个原生活动约21.07秒，常驻13.26秒。这支持继续研究回收策略，但不能算成功任务收益率，更不是现网API延迟。若实际用户多且空闲时间长，按需可能更有价值；若频繁交互且延迟敏感，保留部分对象或共享服务可能更合适，仍需实测。

**N=5/10必须单独解释。** 两个常驻档位均按冻结的每 Worker 2 GiB/0.75 CPU配额，在 Docker 启动前因总配额超限拒绝：`Docker_started=false`、`observed_RSS=null`。这不是实际运行到5/10用户后的内存、OOM或框架最大容量，没有RSS曲线可以外推。`i25_complete=false`和`savings_percent=null`仍应保留。

来源：[实例成本流程](../../../validation/instance-cost-flow.md)、[配额验收](../../../validation/resource-budget.md)、[resident入口](../../../validation/resident-runtime.md)。

### 2.6 继续改 OpenClaw、迁移 DSH、还是自建运行管理

**缺证据。** 当前能列出接入维护面，却没有统一的人时记录、同一个故障定位耗时对照或实际候选升级实验。DSH使用官方Goal/checkpoint配套及固定源码路径，已出现状态保存格式与轮次事件的适配问题；Deep Agents需要维护图状态物理解码、生命周期、后端与resident入口；OpenClaw有公开插件改造证据，但当前浏览器预算、分页和取消OOM限制仍在。Agents SDK公开RunState/after_turn存在，完整跨进程续跑未测。

**最小下一实验。** 围绕实际业务写一份最小改造清单，按候选自带、官方配套、业务代码、实验设施四类估算，并安排一次限定版本升级或一次真实业务规则变更。记录资料阅读、实现、调试、回归的人工投入与结果；只为有明确决策价值的一个备选补关键试验，不把所有暂缓候选同时扩建。

**可能改变建议。** 若OpenClaw公开插件和路由改造足以解决黑箱与定制问题，保留产品积累可能更经济；若DSH减少产品侧状态管理且插件维护可接受，迁移依据会加强；若业务需要明确执行图，Deep Agents可能更适合，但生产授权、调度、存储与资源管理仍需计入自研。轻量SDK不等于运行平台建设成本低，完整Agent产品也不必然每用户一容器。

来源：[工程清单](../../../validation/engineering-inventory.md)、[候选条件化建议](../../../validation/comparison.md)。

### 2.7 怎样把请求数变成可比较的真实费用

**缺证据。** 最近登记范围为238库、1528条reservation，其中1479条远程200、4条远程结果未确认、1条只有预留记录、36条内网模拟与8条本地注入。新removal与本次DSH formal尚未登记，也有未列/已删临时库。四路线正式组没有统一去重token与可靠价格，人工工时和生产CPU/内存/存储费用未知。

**最小下一实验。** 先对已结束且身份/预算/进程闭合的新增链追加台账，物理去重同一链预算，不查询活跃库推测结果。安全提取每次远程请求最终usage，统一输入/输出/cache/reasoning与重试口径，并从可核验价格或账单建立金额；未知断连与预留结果继续单列。按同任务/同版本/同配额组，用所有尝试消耗除以完整成功业务数，失败不能删除，拒绝与校准不能进入成功业务分母。

**可能改变建议。** 请求较少的方案可能每次上下文更长，加入失败开销与token后费用排序可能改变。共享服务固定开销、状态存储和冷启动成本也可能改变按需优势；在这些数据齐备前只比较已证实的请求用量和资源样本，不报价、不推全年节省。

来源：[用量台账](../../../validation/costs.md)、[比较分母](../../../validation/comparison.md)。

## 3. 所有结论都受这些共同限制

### 3.1 版本、入口与判定器不是一条不变的轴

详细任务、DSH新业务态保存、Goal暂停、fault-round-order、Deep Agents fault-send、multi-user、instance-runtime都按不同材料留存。候选相同不代表入口相同；bench变化也可能升级进程健康、原生状态或采样校验。DSH原15轮、新保存6轮与最终10轮不能拼成新镜像25轮；Deep Agents五种子可以按已核对的相同候选/任务/判定源码给描述汇总，但bench不同仍保留分组。

评分器误判可通过新固定bench、断网只读的追加复核纠正，原verdict和hash必须并列；复核不是第二次候选成功，也不新增模型调用。反过来，原生分页失败不能通过更改判定器或选成功重跑消除。旧scope YAML判定器与真实multi-user入口、旧设计段落与最新执行追加记录，也不能不加区分地引用。

### 3.2 业务、原生机制、实验完整性不能互相代替

原生恢复成功而业务漏分页，应同时报告两者；没有敏感副作用但模型未调用执行规则，表示该路径未覆盖；B在A退出后继续原生进展但最终漏分页，不能称不受影响的业务完整成功。采样错误导致的完整性中止，不应该给候选扣一条能力失败，也不能忽略后算通过。

同样，host passed、评分容器健康、付费writer已闭合、全trial清理、业务passed各自回答不同问题。137不自动等于OOM，`OOMKilled=false`也不等于健康退出。后续报告应继续保留分层字段，避免一个“通过率”吞掉含义。

### 3.3 小样本与受控环境限制外推

商品任务、页面、账号、模型和架构都固定，本地站点不能覆盖开放网页的登录变化、验证码、慢页面或外部系统波动。三种子与最终两种子增加的是输入变化，不是足够的随机重复；暂停每路线三条、成本每策略单种子两用户尤其不足以估计生产失败率、尾延迟或规模曲线。

不同候选的提示、工具面、原生协议与状态机制无法完全相同；公平性主要来自共同业务目标、工具粒度、预算与独立结果验收。不能把方案差异简单归成纯框架因果效应。尚无真实业务权重，所以不构造加权总分，不用功能数量、依赖数量或代码行数制造精确排行榜。

### 3.4 资源样本仍不是完整经济性

Docker样本均值与峰值含配套服务和实验观察器，未包含宿主/VM、真实产品后端或生产存储；没有完整CPU秒与内存时间积分。两秒是目标采样间隔，实际缺口必须留存。暂停Worker为零只证明该计算单元已释放，状态、共享服务与监测仍有成本。唤醒观察包含实验服务准备而无生产队列，不宜直接作为产品SLA。

## 4. 建议的推进顺序与停止规则

1. **先闭合已有执行。** 只读归因DSH正式第二格采样错误，收取截点仍运行的I24 202结果，核实原判定、退出和清理，再把已结束库补入用量台账。
2. **完成最能影响选择的既定专项。** 在材料冻结后补I23正式矩阵/正常基线/最终窗口，补I24剩余种子；业务失败保留，不能为了绿色结果无限修改候选。
3. **选择一条拟产品化入口再闭合成本。** 对这一入口补实际后端身份、业务标准、按需5/10和三种子同工作量配对；若必须改配额或工具契约，以新变体比较。
4. **用真实业务补一次维护与升级试验。** 记录人时和维护责任，再判断继续改OpenClaw、迁移DSH或用Deep Agents/SDK自建是否更符合研发约束。

若出现材料不一致、观测缺失、资源超限、未知评分进程状态，应先停止并解决实验完整性；若仅剩有充分证据的业务失败，可以结束该格并继续独立机制探索，但不把探索改称完整能力通过。最终建议应能同时说清“已证实能做什么”“失败会怎样表现”“应用还要补什么”和“哪些成本仍未知”。

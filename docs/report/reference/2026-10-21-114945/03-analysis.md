# 分析与条件化建议

资料截点：**2026-10-21 11:49:45（Asia/Shanghai）**。本篇解释[实测结果](02-results.md)，不增加新的能力判定。当前应继续完成 DSH 与 Deep Agents 的专项证据，尚不足以决定产品整体迁移或生产部署方案。

## 1. 基本任务已经区分出差异，仍需解释失败类型

四路线都能完成至少部分真实工具和业务扩展任务，并取得原生业务态冷读证据。差异不再只是“能不能接上模型”，而是过程约束、任务终态、工具面和状态生命周期在同一目标下能否共同成立。

**分页违规是任务质量问题。**Pi 初筛以及 OpenClaw、Deep Agents、Agents SDK 的详细任务都有相关失败。不能因报告和订单正确便忽略事先约定；也不能仅凭这些少量样本归因为某个框架的普遍缺陷。系统提示、工具 schema、运行时工具面与模型随机性都可能影响行为，当前没有进行对应的单变量消融。Deep Agents 还有一次错误商品选择，需与“只违反分页过程”区分。

**业务成功与运行正常结束不同。**OpenClaw 浏览器 303 已有正确写入和下载，仍因未正常结束而失败。对后台助手而言，产品需要知道任务是否真正收束、是否还会继续调用，这个判定有现实意义；但该结果只适用于当前入口、页面、模型和二十次预算。

**规则未触发与违规执行也不同。**Agents SDK 两次敏感任务由模型自行拒绝，没有禁用副作用；问题是未获得执行层拒绝的测试证据。后续补证要在真实执行边界验证策略，不能把无副作用直接提升为规则已验，也不能反过来称发生越权。

## 2. 状态和恢复必须跨越进程生命周期验证

DSH 旧业务态接法在当轮任务中正确，换进程却无法识别自定义必需事件；这说明演示内可写可读不等于长期存储契约兼容。修正为官方工具结果 metadata 后取得冷读和受影响任务复验，是有价值的接入修正，同时暴露出升级时必须维护的状态格式与扩展契约。

I22 已把证据推进到真实未完成任务继续：DSH 依赖官方持久 Goal、步边界与会话机制；Deep Agents 依赖公开 drain、同步 checkpoint 和空输入继续。两者在已测样本都释放了旧 Worker，并在新 Worker 保持预算和已完成写入。

Deep Agents 原生续跑 3/3、完整业务 1/3，应同时保留。图从正确位置继续解决的是执行进度，后续模型仍可能违反分页要求。DSH 的安全暂停通过也不替代旧取消缺原生结束事件的问题；安全点暂停、即时取消与突然崩溃分别有自己的语义。

故障冒烟进一步覆盖了原生崩溃后继续，以及提交成功但回执丢失的窗口。已有样本未重发已提交写入，但不能推导任意条件下的 exactly-once：候选持久日志与外部业务事务并非同一个提交，其他种子、幂等模式和在途情况仍需验证。

## 3. 能力由谁提供，决定未来要维护什么

| 路线 | 候选及官方组件提供 | 本仓库的接入或补齐 | 尚需产品层决定 |
| --- | --- | --- | --- |
| DSH | Agent 循环、工具 guard、profile、会话持久化；专项使用 Goal/checkpoint 与原生崩溃修复 | HTTP/MCP 桥、可信绑定、业务态投影、Goal 生命周期与故障诊断；部分按固定源码路径导入 | 后端授权、调度与回收、目标/队列边界、升级维护 |
| OpenClaw | Gateway、Agent 循环、会话库、公开插件和 hooks | Gateway 生命周期、任务/session 映射、工具/MCP、业务状态与取消观测 | 选择适合的控制入口、处理 OOM/预算问题、共享或按需部署及迁移取舍 |
| Deep Agents | 图执行、RunControl、checkpointer/SQLite saver、原生继续 | 业务工具/状态、可信绑定、生命周期、故障状态诊断；模拟后端、Worker 控制和 resident 入口 | 实际身份体系、调度、存储、Worker 复用、生产资源与故障治理 |
| Agents SDK | Agent/Runner、FunctionTool、RunHooks、Session、RunState、公开取消 | HTTP/MCP、身份绑定、模型终态观测、状态/传输适配 | after_turn 完整恢复、产品任务管理、授权、资源生命周期 |

Docker 实验编排、独立评分、模拟网站、故障注入和证据采样属于研究设施，不应全部计作未来产品必需代码。工具、身份绑定、持久化、生命周期和预算控制则需要在产品中有对应实现，但可以复用产品已有设施。

工程记录尚未发现本仓库对候选上游内核的自研源码补丁；OpenClaw 的 `BUSINESS_EXTENSION.patch` 是本仓库接入文件的历史 diff，DSH 的 `cordis.patch.yml` 是配置覆盖。没有 fork 不等于没有维护成本：固定源码路径、会话格式、序列化类型、HTTP 连接与关闭语义都需要随版本复核。当前没有升级实验或可靠人工工时，不能从代码行数给交付天数。

## 4. 多用户与成本证据支持到哪一步

Deep Agents 已在模拟后端下验证部分真实并发、重连和跨用户拒绝。责任边界包含本仓库的后端认证/授权、绑定与 Worker 控制，不能把整个结果归于图运行时。每用户独立 Worker 也没有证明同一个进程或 Worker 可以安全复用。

两用户成本探索显示：按需方式空闲阶段没有 Worker，常驻方式保留真实 Agent 对象；前者空闲内存更低，后者本次唤醒到首次原生活动更快。这是已测架构的取舍线索。当前两组都有业务失败，且缺更多档位、同入口作用域与产品后端证据，因此不计算收益百分比。

常驻 N=5/10 的拒绝依据是固定资源配置之和，不是实际 RSS。它回答“当前配额安排能否准入”，没有回答“框架本身最多能容纳几个用户”。同理，单个容器数减少也可能隐藏多进程常驻开销，后续仍须同时观察内存、CPU、进程/线程、状态存储和故障影响。

## 5. 哪些结果不应直接归因给候选

实验期间出现过 Docker 删除状态采样、跨时钟比较、LangGraph DeltaChannel/Send 诊断以及 DSH Goal 事件顺序等问题。它们影响证据和接入，需要保留失败及消耗；若因完整性中止，就不能据该轮宣布候选不支持恢复。

DSH 正式故障矩阵第二格的采样空档就是这种情况。业务结果正确并不能豁免证据要求；应先解决观测问题并以新材料、新运行取得有效证据，同时保留原停止记录。相反，业务失败而观测与原生执行链有效时，可以保留对应分项发现，不必把所有层次压成一个不透明的 PASS/FAIL。

这套区分也限制了“透明度”的结论：目前能说明日志、状态、工具和副作用可关联，尚未做相同故障下的人为定位时间实验，因此不能给排障效率排名。

## 6. 条件化选择

| 业务优先条件 | 值得继续验证的方向 | 支持该方向的现有证据 | 做决定前还需什么 |
| --- | --- | --- | --- |
| 优先复用已有 Harness，关注任务连续性 | DSH | 基本任务表现完整；Goal 三种子暂停续跑；四故障冒烟通过 | 完成故障矩阵、后端作用域和按需成本；确认源码路径/插件/状态契约的维护投入；处理取消边界 |
| 需要明确控制执行图、状态和安全点 | Deep Agents + LangGraph | 公开 drain/checkpoint 及三种子原生续跑；崩溃恢复与模拟后端分项证据 | 检验目标业务上的约束遵循；补全授权、生命周期、更多档位、Worker 复用和工程估算 |
| 优先保留现有 OpenClaw 产品积累 | 继续改 OpenClaw | Gateway/插件扩展、敏感执行规则和业务态冷读可用 | 定位浏览器预算及取消 OOM；选择恢复入口；核实际现网功能、按需回收和改造范围 |
| 业务循环较轻，团队愿意自行管理运行生命周期 | Agents SDK | 工具、浏览器、扩展与 immediate cancel 有实测 | 完整 RunState/after_turn 新容器恢复、执行规则覆盖、隔离与实例成本 |

Pi、ADK、Codex SDK、OpenHands 暂不参与深层能力或成本排序。它们目前只有共同初筛，某个原生 pause/session 接口的存在是下一步线索，不能替代同题专项；当前未测也不能作为淘汰理由。

## 7. 下一笔投入与交付边界

建议维持现有两条专项路线，优先完成会改变选择的证据：故障完整矩阵及非幂等写入窗口、多用户真实边界、同入口常驻/按需配对与业务结果。具体最小验证和停止条件见[局限与后续验证](04-limitations-and-next.md)。

并行需要补一份来自真实产品负责人的现状清单：现用 OpenClaw 版本、已上线流程、状态和工具、回收配置、延迟要求与已具备的平台能力。Hogee 源码只作实现参考，不能据此推出现网功能或迁移工作量。

在这些信息和专项证据齐备前，合适的结论是“DSH 与 Deep Agents 值得继续集中验证”；不据当前通过数确定唯一赢家，不给可靠性百分比、研发人日或云费用节省承诺。

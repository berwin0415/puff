# DeepSeek Harness 候选附录

资料截点：**2026-10-21 11:49:45，Asia/Shanghai**。本附录沿用截点前已有实验及追加复核，不重新评分。完整比较口径见[分组结果](../02-results.md)，原始运行与复核入口见[证据索引](../evidence/index.md)。

## 测试对象、版本与入口

测试的是 MIT 开源项目 `deepseek-ai/deepseek-harness`，固定提交 `dd6322d604e00eec1ba5e0c8541159906a21094a`，源码包版本 `0.1.2-alpha.3`。它承担用户指定的优先路线角色，并非预设赢家。

本轮实际存在三个层次的入口。初筛使用官方 `DeepSeekHarness` SDK 启动 `sdk-minimal`；同题详细任务改用公开 `runProfile`、`agents.create/resume({setup})`，在首次输入前挂好本任务的工具、规则和浏览器连接；暂停及故障专项另建 Goal 变体，加载官方持久目标、round driver 与 checkpoint 插件。高层 SDK 未开放所需的异步 setup，是转向直接 runtime 接口的接入原因。完整 `sdk` profile、原生 Shell/编辑器工具组合不在当前通过结论内。

这些入口、镜像和工具面分别冻结。Goal 变体还单独核对了实际工具面，不能把详细任务的普通工具面和通过数直接移给 Goal 变体。来源与接口见[候选报告](../../../../validation/deepseek_harness.md)、[接入说明](../../../../../adapters/deepseek_harness/README.md)及[暂停报告](../../../../validation/pause-recovery.md)。

## 接入与能力来源

官方提供 Agent 循环、工具执行和调度、Session 事件、JSONL 持久化与投影，以及专项中的 Goal 生命周期和原生崩溃日志修复。业务代码负责工具转发、可信身份绑定、回执状态、数量规则、浏览器产物搬运和控制证据。模型仍自行选择工具和下一步；工具桥不会代办筛选、下单或补查回执。

业务状态保存经历了一次有实测依据的修改。旧方案追加必需自定义事件 `harness-lab/business-state`，在原进程能完成任务，却在冷启动时被固定版本的静态事件目录拒绝；注册 projection 并不会注册新的可加载事件类型。将必需业务态标成可忽略会掩盖丢失，因此未采用。新方案通过公开 `output.presentationMeta`，把实际工具观察写入官方调度器提交的 `tool/result.data.meta.business_state`，再由原生投影重建。给模型的工具结果和业务步骤没有因此被代办。

当前工具保持默认 exclusive 串行，完整业务状态快照据此累积。若以后开启并行业务工具，还需重新设计状态合并，避免多个调用从同一旧状态生成快照后互相覆盖。此处的接线与限制属于维护成本，不能称为框架自动提供了任意业务事务。详见[状态兼容与修订记录](../../../../validation/deepseek_harness.md)。

## 分组实测与失败

| 组别 | 既有结果 | 应保留的边界 |
| --- | --- | --- |
| I08 初筛 | 两个新容器的工具任务均完整通过；分别 9、5 次模型请求，各 3 笔写入；模拟累计限额通过 | 同一种子的新任务重跑，不是恢复 |
| 原详细正式组 F1 | 五类 × 101/202/303，15/15；121 次真实模型请求、21 笔实际写入 | 候选镜像 `3c4da6e3…`；业务态仍为旧自定义事件接法 |
| 新保存组 F2 | 仅 extension / extension-denied × 三种子，6/6；31 次请求、9 笔写入 | 候选镜像 `dc5238ff…`；不把未重跑的其他三类搬到此镜像 |
| 最终补充组 F8 | 五类 × 404/505，10/10；78 次请求、14 笔写入 | 候选与 F2 相同，bench 及独立进程验收有差别，仍分组 |
| 新保存方式冷读 | 23 项通过，删除旧 Worker 后，新容器读回原生业务态且无新增模型/业务调用 | DSH 加载会追加合法原生边界，state 是受校验的可写挂载；不是全程只读，也不是任务续跑 |

F1 的浏览器请求为 20/20/16 次，前两轮用满额度；F8 为 19/18 次，仍只有很小余量。成功证明固定页面上的登录、跨页、提交和真实 CSV 下载完成，不能外推页面变化或额外重试下的稳定性。三组材料不拼成“同一镜像组合的 25 轮”，更不能把 F2 与 F1 当成互不重叠的能力样本。

两次详细取消原始失败仍保留：公开 `Agent.cancel` 后已 idle/noPending，却缺失原生 `turn/end`；公开错误观测记录结束事件带非 JSON 可序列化数据。后续 Goal 安全暂停通过没有修复或覆盖这条立即取消路径。冷读 001/002 为探针接线失败，003 为上述自定义必需事件兼容失败，004 才是新接法通过。[候选报告](../../../../validation/deepseek_harness.md)保留了这些不同归因。

### 暂停、故障与尚未完成的专项

I22 的 Goal 变体已完成三种子的真实暂停链：已发生业务写入且任务仍活动时请求暂停，原生安全点保存，删除 A，等待 600 秒，重建代理，再由新 B 沿原 Session / Goal 继续，没有重发任务提示或已提交写入。**原生暂停恢复 3/3，完整业务 3/3**。101 的完整通过来自既有追加离线复核；原先 16/17 的判定保留，复核只处理固定格式将省略的 `delegationDepth` 物化为 0 这一差异。此附录未再执行复核。详见[暂停报告](../../../../validation/pause-recovery.md)。

I23 使用另一个 `fault-round-order` 变体。两模式无故障基线 2/2，seed101 的非幂等服务四故障冒烟 4/4，覆盖模型超时、工具失败一次、写后丢回执与写前强杀；已提交操作没有重发。正式 24 格矩阵仅首格 `model_timeout / 幂等服务 / 101` 有效完成。第二格 202 的业务结果通过；9 项外层检查中 8 项通过，仅资源采样间隔违反完整性要求，整批停止；**有效完成 1/24，第二格不计候选能力成功或失败**。不能用四格冒烟替代正式矩阵。见[故障执行记录](../../../../validation/fault-recovery-execution.md)与[截点汇总](../../../../validation/comparison.md)。

截至截点，DSH 尚没有 I24 真实产品边界及双用户专项、I25 常驻/按需成本对照的通过结论。一个 runtime 可有多个会话只是部署机制线索，不能作为共享授权或资源收益证据。

## 维护投入与适用条件

已发生的工作包括直接 runtime 入口、工具/MCP 连接、metadata 业务投影、Goal 步边界与恢复绑定、原生日志和控制链诊断。故障接入还需理解官方“先入队下一轮、后更新轮数”的顺序；早期观察器把正常顺序误判为外部并发输入，失败与修订分别留存。上游核心未被重写，但部分接入依赖固定源码路径和具体插件契约，未来升级需重验事件格式、工具面、round 时序与状态重建。

这些事实支持在**允许维护领域插件与生命周期接入、需要持久目标和可观察过程**的场景继续评估该路线。它们尚不支持任意取消可靠性、外部副作用 exactly-once、多租户平台已完成或生产节省比例。真实人工工时和版本升级成本仍未知；公共故障注入、独立评分及资源采样是研究设施，应与产品运行必需代码分开估算。工程范围见[投入清单](../../../../validation/engineering-inventory.md)。

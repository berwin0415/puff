# Agent 框架是什么，这八条路线分别是什么

本篇介绍本轮比较的对象：先说明“Agent 框架 / Harness”到底指什么、它和模型是什么关系，再逐一介绍八个框架的来历、定位和在本轮中的角色。不熟悉这些项目时，从这里开始读；已经熟悉的读者可以直接跳到[总体实验设计](02-experiment-design.md)。

## 1.1 先厘清几个词

报告里反复出现几个词，含义并不相同，先统一定义。

| 词 | 指什么 | 不等于什么 |
| --- | --- | --- |
| **大模型** | 负责理解和生成的那部分，例如本轮使用的 `deepseek-v4-flash` | 不负责执行动作、保存进度、控制停止 |
| **Agent 框架 / Harness** | 围绕模型的那层运行系统：组织对话循环、决定能调用哪些工具、保存状态、处理停止与重试 | 不等于模型本身，也不等于产品界面 |
| **候选 / 路线** | 本轮参加比较的一个框架，连同把它接入实验的那层代码 | 不等于完整可用的云端产品 |
| **实验接入** | 本仓库为把框架接进统一环境而写的外层代码 | 不能算作框架自带能力 |

**“Harness”这个词**（原意是“马具”，引申为“驾驭、装载”）在行业里指**让模型能真正干活的运行装置**。模型本身只会“读入文字、输出文字”；要让它查资料、调工具、改文件、在出错后继续，中间必须有一层代码负责把这些动作组织起来——这一层就是 Harness。本轮的八个框架，就是这层装置的八种不同做法。

第 [01 篇](01-background-and-goals.md)里说的“围绕模型的运行系统”，指的就是它。

### 一次任务里，各部分各干哪些事

以本轮的模拟采购任务为例：

| 环节 | 谁负责 |
| --- | --- |
| 读懂“查 office 和 garden 类别、单价不超过 35 元” | 模型 |
| 决定先查第一页、再查第二页，还是直接调下单 | 模型 |
| 提供“查询商品”“写入订单”这些工具的实际接口 | 工具服务（实验设施） |
| 把模型的“我要调用查询工具”变成一次真实的 HTTP 请求 | **框架** |
| 把工具返回的结果拼回对话，继续下一轮 | **框架** |
| 保存进度，让程序关掉后还能接着做 | **框架**（或实验补建） |
| 限制总共只能调用多少次模型（常规 20 次，网页 40 次） | 实验设施 |
| 判断最终结果对不对 | 实验设施（独立判定） |

**本轮研究的正是中间那几行。** 上表里“框架”和“实验补建”的边界，是每份单框架报告要回答的核心问题——同样的“通过”，有的靠框架，有的靠我们自己写的代码，长期维护成本完全不同。

## 1.2 八个框架分别是什么

八个项目来自不同团队，形态差别很大：有的是完整产品，有的只是一个库。从“给你的东西有多少”来看，大致可以排成一条光谱：

```
轻量库 ←──────────────────────────────────────────→ 完整服务
Pi Core    Codex SDK   Agents SDK   ADK   Deep Agents   OpenHands   DSH   OpenClaw
```

左边只给你一个 Agent 对象，右边连后台服务和会话管理都带。**越往左，接入越简单但自建越多；越往右，开箱能力越多但要理解的东西也越多。**

### DeepSeek Harness（DSH）

- **来历**：DeepSeek 官方开源的 Agent Harness，本轮固定版本 `0.1.2-alpha.3`（MIT）。
- **形态**：完整运行系统，自带 Agent 循环、工具执行、会话事件和持久化，还有“持久目标”（Goal）机制。
- **为什么在本轮**：**我们已有的客户端就是基于它**。所以它既是被比较的候选，也是“客户端上云”这件事的直接研究对象。
- **本轮深度**：最深。详细四类、暂停、故障矩阵、多人、成本全部参加。

### OpenClaw

- **来历**：开源的个人 AI 助手/网关项目，本轮固定 `2026.10.5`。
- **形态**：完整产品形态——有常驻后台服务（Gateway）、插件系统、SQLite 会话历史、浏览器工具。
- **为什么在本轮**：**现有云端业务基于它**。它的使用反馈（过程不好看清、业务定制费力、实例成本随用户增长）是这次调研的三个出发点之一。
- **本轮深度**：详细四类。未进入暂停、故障、多人、成本专项。

### Deep Agents + LangGraph

- **来历**：LangChain 团队的两个项目——Deep Agents 0.7.28 提供“开箱即用的 Agent”，LangGraph 1.2.16 是它底下的图执行引擎。
- **形态**：图状态机。执行被拆成节点和边，状态在每个节点间传递，检查点可以完整保存。
- **为什么在本轮**：它把“步骤”和“状态”暴露得最清楚，最适合验证**“中断后从原处继续”**这件事。
- **本轮深度**：最深之一，与 DSH 并列参加全部专项。

### OpenAI Agents SDK

- **来历**：OpenAI 官方开源的 Python Agent 框架，本轮固定 0.24.0。
- **形态**：轻量库，核心是 `Agent` + `Runner`。工具定义直接，取消接口明确。
- **为什么在本轮**：代表**“产品已有任务管理，只缺一个 Agent 循环”**的用法。
- **本轮深度**：详细四类。未进入专项。

### Pi Agent Core

- **来历**：Pi 项目的核心模块（`@earendil-works/pi-agent-core`），1.3.0。
- **形态**：最轻。只有一个进程内的 `Agent` 对象，状态在内存里。
- **为什么在本轮**：代表**“只要循环，其余全自己建”**的极端。

### Google ADK

- **来历**：Google 官方的 Agent Development Kit（Python），2.12.0。
- **形态**：带标准会话服务的 Runner，`SessionService` 可按用户和会话索引。
- **为什么在本轮**：会话抽象做得完整，适合观察**“会话服务”和“任务恢复”差多远**。

### OpenHands

- **来历**：OpenHands 项目的软件 Agent SDK，1.56.0。
- **形态**：`Conversation` 对象自带持久化（`persistence_dir` + `conversation_id`）。
- **为什么在本轮**：持久化设计是所有初筛框架里最接近“可恢复”的。
- **重要边界**：本轮**只用 SDK 核心**，没用 Agent Server、Canvas 界面和内置浏览器。

### OpenAI Codex SDK

- **来历**：OpenAI Codex CLI 的 TypeScript SDK，`rust-v0.163.0`。
- **形态**：SDK 包装真实的 `codex` 命令行程序，走 Responses 协议。
- **为什么在本轮**：它代表**“复用现成 CLI”**的路线，工具执行能力最强。

## 1.3 本轮怎么分组比较

八条路线不是平均用力，而是分三档递增投入：

| 档位 | 路线 | 参加了什么 | 为什么这样安排 |
| --- | --- | --- | --- |
| 初筛 | 全部八条 | 独立运行、累计额度、两次工具任务 | 先确认都能跑起来，排除“只能在原开发机跑” |
| 详细 | DSH、OpenClaw、Deep Agents、Agents SDK | 再加工网页、业务扩展、两类拒绝、诊断、取消、状态冷读 | 前三者有明确业务背景；Agents SDK 代表轻量路线 |
| 专项 | DSH、Deep Agents | 再加工暂停、故障矩阵、多人、成本 | 恢复和隔离需要新接法，按前两档结果集中投入 |

**没参加不等于不支持。** 这是读整份报告时最需要守住的一条：初筛框架没做恢复实验，只说明我们没测，不说明它做不到。

## 1.4 版本与来源

本轮所有候选都固定到具体源码提交，并在镜像内从导出的源码构建，没有直接用官方成品镜像，也没有使用名称相近的 registry 包替代。

| 框架 | 版本 | 说明 |
| --- | --- | --- |
| DeepSeek Harness | 0.1.2-alpha.3 | 官方源码包，MIT |
| OpenClaw | 2026.10.5 | 官方源码导出，57,891 个条目 |
| Deep Agents + LangGraph | 0.7.28 / 1.2.16 | 两个上游，均 MIT |
| OpenAI Agents SDK | 0.24.0 | 官方源码，非 editable 安装 |
| Pi Agent Core | 1.3.0 | 从源码编译三个 workspace |
| Google ADK | 2.12.0 | 官方源码包，2,990 个文件 |
| OpenHands | 1.56.0（SDK） | 官方 `software-agent-sdk` |
| Codex SDK | `rust-v0.163.0` | 官方发布包，未在镜像内重编译 |

**受测的不是自有客户端，也不是现有云端业务的线上容器。** 结果说明“这些框架加这套接法”的表现，迁移到实际产品仍需核对版本、配置和已有改造。各框架的提交号与核验入口见[资料来源](sources.md)，逐框架细节见[单框架实验报告](candidates/README.md)。

# 3. 首轮结果汇总

首轮实验已经收尾，本篇依据 **2026 年 10 月 21 日 15:29（北京时间）** 的最终记录。基本任务、暂停和约定的故障阶段完成；多用户、实例成本及完整费用统计按实际缺口收尾。实验容器和网络已清理，镜像、保存状态和原始记录保留。

DeepSeek Harness 与 OpenClaw 的结果来自官方开源固定版本加实验接入代码的自建容器，不是自有客户端或实际云端业务容器的测试结果。下面的“通过数”描述固定任务的已测结果，不代表线上可靠性。 每项实验的逐框架、逐测试组结果见[基本能力](experiments/01-basic-capabilities.md)、[暂停与故障](experiments/02-pause-and-failure.md)、[多人使用与成本](experiments/03-users-and-cost.md)；[参与范围表](02-experiment-design.md)说明哪些框架实际参加了哪些实验。

## 3.1 先看研究问题得到了什么回答

| 最初的问题 | 首轮得到的回答 | 本轮没有回答的部分 | 对应详细实验 |
| --- | --- | --- | --- |
| 框架能否独立部署并办事？ | 八条路线均有真实模型和工具接入；七条两次新环境任务均通过，Pi 一次分页违规 | 不同生产环境的部署与规模表现 | [实验一至三](experiments/01-basic-capabilities.md) |
| 能否看清过程、增加业务要求？ | 四条路线都有工具、运行事件、状态和规则接点；也暴露保存兼容性、规则未触发和取消问题 | 排障到底省多少人工时间，版本升级维护要花多少工作 | [实验四](experiments/01-basic-capabilities.md) |
| 能否暂停、省掉等待资源并继续？ | 两条路线各三次成功接回任务；完整业务分别为 DeepSeek Harness 3/3、Deep Agents 1/3 | 任意时刻立即停止、网页现场恢复、生产长期运行 | [实验五](experiments/02-pause-and-failure.md) |

| 建设和运行总成本如何？ | 形成有明确登记范围的请求和模型用量统计，并列出了接入维护面 | 完整账单、请求与用量逐条关联、可靠工时和升级成本 | [实验九](experiments/03-users-and-cost.md) |

## 3.2 基本任务：差异出现在要求是否完整满足

初筛每条路线从同一固定镜像新建两个容器，各做一次工具任务。DeepSeek Harness、OpenClaw、Deep Agents、Google ADK、OpenAI Agents SDK、Codex SDK、OpenHands 均为 2/2；Pi Agent Core 为 1/2，失败轮违反每页最多五条的要求。八条路线的模拟重试和换容器累计额度检查均通过。后者证明实验计数接入有效，不代表框架自带完整费用管理。

四条详细路线分别做工具、网页、业务扩展和两种执行规则测试，每类三组输入。下表只列原三组，完整通过要求最终结果与操作过程都符合约定。

| 用例 | DeepSeek Harness | OpenClaw | Deep Agents | OpenAI Agents SDK |
| --- | --- | --- | --- | --- |
| 多步工具业务 | 3/3 | 2/3 | 2/3 | 3/3 |
| 网页操作 | 3/3 | 0/3 | 3/3 | 3/3 |
| 新工具与业务记录 | 3/3 | 1/3 | 1/3 | 2/3 |
| 敏感操作在执行前拒绝 | 3/3 | 3/3 | 3/3 | 1/3 |
| 超量购买在执行前拒绝 | 3/3 | 1/3 | 3/3 | 3/3 |
| 固定五类测试合计 | 15/15 | 7/15 | 12/15 | 12/15 |

这个合计包含两类“应该拒绝”的任务，不能叫十五笔正常业务的成功率。

**本轮扩展到全部八条路线。** 另外四条路线此前只做了初筛，没有测网页、扩展和规则。本轮为它们补齐同样的接法后，各按三组输入完整执行五类任务：

| 用例 | Pi Agent Core | Google ADK | OpenHands | Codex SDK |
| --- | --- | --- | --- | --- |
| 多步工具业务 | 3/3 | 3/3 | 3/3 | 3/3 |
| 网页操作（40 次预算） | 3/3 | 3/3 | 3/3 | **3/3** |
| 新工具与业务记录 | 3/3 | 3/3 | 3/3 | 3/3 |
| 敏感操作在执行前拒绝 | 3/3 | 3/3 | 3/3 | **2/3** |
| 超量购买在执行前拒绝 | 3/3 | 3/3 | 3/3 | 3/3 |
| 固定五类测试合计 | 15/15 | 15/15 | 15/15 | **14/15** |

四条路线合计 **59/60，483 次模型请求**。唯一失败是 Codex 的敏感第三组：模型自行拒绝、未调用工具，执行层规则未被真正触发。按“没有副作用不等于规则有效”的标准保留为未通过。

**网页预算的调整说明。** 首轮网页任务与其余用例同为二十次上限，八条路线中通过轮次集中在 16–20 次，OpenClaw 和 Codex 整组撞线。本轮把**网页用例单独提高到四十次**并重跑八条路线，结果**二十四次全部通过**：

| 路线 | 20 次预算 | 40 次预算 | 平均请求 |
| --- | --- | --- | ---: |
| DSH | 3/3 | 3/3 | 18.7 |
| OpenClaw | **0/3** | **3/3** | 31.7 |
| Deep Agents | 3/3 | 3/3 | 19.3 |
| OpenAI Agents SDK | 3/3 | 3/3 | 17.7 |
| Pi Agent Core | 3/3 | 3/3 | 19.0 |
| Google ADK | 3/3 | 3/3 | 18.3 |
| OpenHands | 3/3 | 3/3 | 18.3 |
| Codex SDK | **0/3** | **3/3** | 32.7 |

**只有此前撞线的两条路线结果改变，其余六条不变。** 这验证了首轮把 OpenClaw 记为“预算组合下的失败”而非能力缺陷的判断是正确的。

**更值得注意的是消耗差异。** OpenClaw 和 Codex 完成同一个网页任务平均要 31.7 和 32.7 次，其余六条在 17.7–19.3 次之间——**多花六成以上**。按统一预算上线时它们会被判失败，放宽预算则成本显著更高。

这 60 次运行使用本轮重建的候选镜像，与首轮四条路线的正式组不是同一批次；网页用例的两批预算结果也不可比。逐项明细见[基本能力篇](experiments/01-basic-capabilities.md#本轮八路线结果扩展后)。

OpenClaw 的三次网页任务都用完二十次模型调用，其中一轮已提交并下载正确文件，但没有正常结束；其他失败还包括分页要求未满足和未真正触发数量拦截。Deep Agents 的工具与扩展任务出现分页约束违规，另有一次选错商品。OpenAI Agents SDK 的两次敏感任务由模型自行拒绝，没有敏感副作用，却没有触发需要验证的执行规则，因此不能算这条规则已经测过。

DeepSeek Harness 原任务虽通过，随后新进程读取状态时发现自定义保存方式不兼容。改成另一种官方接口支持的接法后，受影响的扩展与数量规则六项重新验证，全部通过；再补两组输入的十项基本测试，全部通过。Deep Agents 对应补充测试通过九项，另一项仍违反分页要求。

这三组 DeepSeek Harness 结果使用过不同接入或检查版本，分别保留，不能拼成一个统一新版本的总通过数。它们说明本次接法经过实际修订，也提醒我们：能完成当次任务，不等于保存的数据经得起重启。

网页任务还有共同限制：多条路线的成功轮次接近甚至用满二十次调用。复杂网页和额外重试的空间，需要在目标业务中再检查。

## 3.3 过程、规则与取消：接口可用，但语义有区别

四条详细路线均能把运行事件与实际工具操作对应，也都已在新容器中读回保存的业务状态。这能支持继续建设过程展示和业务扩展，但本轮没有测“人排查同一个故障花了多久”，不能给排障效率排名。

取消不是同一种动作。Deep Agents 在当前执行步骤结束后协作停止；OpenAI Agents SDK 的立即取消接口已有实测。DeepSeek Harness 原取消实验两次缺少结束记录，OpenClaw 的修订接法虽然记录到了停止，但容器内存不足，整体仍失败。这些问题不被其他成功任务覆盖。取消也不能撤销已经提交的订单。

## 3.4 暂停：执行资源能释放，业务正确仍要单独检查

两条路线各执行三条暂停链：任务真实运行后请求暂停，保存状态，删除旧容器，等待十分钟，再由新容器从同一任务继续，不重新发原任务，不重置额度。

| 观察项 | DeepSeek Harness | Deep Agents |
| --- | --- | --- |
| 成功接回原任务 | 3/3 | 3/3 |
| 完整业务通过 | 3/3 | 1/3 |
| 三条恢复链模型请求合计 | 35 | 17 |
| 等待期执行任务的容器数及内存 | 0；0 MiB | 0；0 MiB |

Deep Agents 另外两条链的订单和报告正确，但没有遵守分页要求。恢复机制成立与业务完整通过，是两条不同结论。DeepSeek Harness 一条链曾被检查程序误判，后来对原记录追加离线复核；原判定保留，没有重新执行任务挑选成功。

等待时共享服务仍运行，两条路线的共享服务内存样本均值约为 58—59 MiB，另有监测开销。因此，这里证明能释放执行程序，等待总成本并不为零。调用总数也没有包含各自正常对照及中止尝试，不能直接当成全部研究成本。

## 3.5 故障：固定阶段已经全部结束

故障专项包含模型请求报超时错误、工具写入前失败一次、订单提交后确认消息丢失、写入前强制结束程序。正式阶段交叉两种业务服务和三组输入，共二十四种组合；之后另补无故障对照与两组新输入下的关键故障。

| 阶段 | DeepSeek Harness 完整业务 | Deep Agents 完整业务 | 用来回答什么 |
| --- | --- | --- | --- |
| 早先两种服务的第一组无故障对照 | 2/2 | 0/2 | 没有故障时，任务是否能按要求完成 |
| 正式四故障×两种服务×三组输入 | 23/24 | 10/24 | 不同故障下的恢复、业务和重复提交情况 |
| 补充两组无故障对照 | 4/4 | 2/4 | 检查分页失败是否本来就会发生 |
| 两组新输入的强制退出与确认丢失补测 | 8/8 | 4/8 | 补充关键写入窗口的证据 |

正式阶段按故障分类，DeepSeek Harness 依次通过 5/6、6/6、6/6、6/6；Deep Agents 依次为 2/6、5/6、2/6、1/6。两条路线这几批业务失败均仅发生在分页验收，不能直接解释为恢复失败。

机制检查给出了另一组结果：两路线正式阶段各六次强制退出，均能换新容器从原状态继续；最终补测各四次也全部成立。已测组合中，已提交操作重发次数均为零，业务写入与回执可以对应，实验记录及清理有效。

这说明两条路线都有真实故障后恢复和处理写入结果不确定的能力依据。DeepSeek Harness 在本轮固定任务中的完整业务表现更好；Deep Agents 无故障时也出现分页失败，不能把故障组全部失败归因于恢复机制。两者均未获得任意故障下只写一次的普遍保证。

DeepSeek Harness 早期两批因资源采样问题停止的记录继续保留。后续修订实验观察和删除协调后，以独立批次完成正式阶段；旧停止批不回填通过，也不与新批混算成功率。

## 3.6 多人使用：有边界证据，首轮仍未完成全部目标

Deep Agents 三组双用户实验都通过用户归属、跨用户访问与控制拒绝、实际并发、断线重连、取消及资源生命周期检查。其中两组业务也全部通过，第一组有一个用户的业务失败，因此整组为 2/3。

DeepSeek Harness 的新入口单用户对照通过。双用户试跑两个主任务均通过，但两个取消任务因模型结果在途或未知，尚未完成可采信的取消判定；符合约定的同时工作证据和删除期间的资源记录也没有通过，整体失败，正式三组未执行。

本轮在这些缺口处收尾，没有继续扩建实验台取得全部通过。已测的是独立模拟产品后端和固定执行入口；浏览器使用期间的数据隔离、同一执行程序切换用户，以及与实际产品的连接，都仍需单独验证。

## 3.7 实例成本：已经看到实现路径，仍算不出可靠收益

Deep Agents 两用户配对探索比较持续保留执行程序与按需启动，两种方式均只有 3/5 个可评分业务通过。按需方式可回收空闲程序，再唤醒新任务；原状态保留和另一用户继续工作也有独立证据。

但追加检查发现，两轮在一些阶段都超过五秒没有资源记录。原样本能描述当时观察到的占用，不能保证覆盖完整过程和最高占用，所以不计算可靠节省比例。

新的五用户按需轮换实验保存五份用户历史，同时最多两个任务活跃；首次唤醒此前未工作的两个用户，任务均通过。整轮七个可评分业务通过四个，另外三个都请求每页一百条，违反每页最多五条的约定，订单和报告仍正确。

五用户实验共留下一百四十八份样本，采样节奏检查通过，但一份记录跨过空闲阶段与后续程序启动的边界，漏记了新增程序当次的资源。回收后空闲窗口因此是二十九份完整、一份不完整，阶段平均和最高占用保留未知。十用户实验未执行。持续运行方案在五、十用户档位因预设配额不足而未启动，也不能解释为框架实际容量上限。

## 3.8 用量与投入：有范围内的统计，没有完整账单

最终第十版登记统计覆盖 343 个独立预算库，共 2485 条额度记录。其中 2416 条已确认收到远程成功响应，另有 36 条模拟、28 条本地故障注入、4 条远程结果未确认、1 条仅预留额度但结果未知。成功响应不等于业务成功，本地注入也不等于付费模型调用。

四条详细路线已提取的已知模型用量为 **10,253,403 个计量单位**，通常称为 token，反映模型处理的输入与输出规模。仍有缺失用量记录，没有与请求逐条对应，也没有可靠金额。另有十七个未登记预算库没有纳入查询，包括最新双用户和五用户等部分记录，不能称完整研究总账。

工具连接、状态扩展、运行控制和业务后端等需要维护的部分已经列出，但可靠人工工时、版本升级成本和实际产品迁移投入尚未测得。首轮能够支持下一笔技术投入，不能据此承诺省多少钱或几天完成迁移。

# 2. 总体实验设计

[上一篇：Agent 框架是什么](01b-frameworks.md)

这轮实验围绕三类需求展开：为已有客户端上云拆清工作、研究现有云端业务反馈涉及的能力、探索更多框架的云端用途。共同问题是：任务能不能办成，过程能不能看清，出错后能不能继续，服务多人时还要补多少东西。

因此，我们先让候选完成一段结果可核对的业务，再逐步增加规则、暂停、故障和多人使用。每一步都保留业务结果与运行过程，最后再讨论技术选择和成本。

## 2.1 实际测试对象和准备范围

本轮 DeepSeek Harness 使用官方开源源码包版本 **0.1.2-alpha.3**，OpenClaw 使用 **2026.10.5**，都固定到具体源码提交，再加本仓库的实验接入代码自行构建镜像。其余候选同样核对开源来源并固定版本。[版本及构建依据](sources.md)列出核验入口。

这里没有运行自有客户端版本，也没有使用现有云端业务容器。官方框架提供任务执行、工具扩展和状态机制；本仓库负责把统一模型、工具、业务规则、控制请求与实验记录接进去。因此，结果对应的是固定框架在这套接法下的表现。实际产品还需要对照版本、配置和已有改造。

实验准备由五部分组成：

| 准备项 | 具体准备什么 | 为什么需要 |
| --- | --- | --- |
| 固定运行环境 | 官方源码、依赖和接入代码打进 Docker 镜像；新容器可独立启动 | 排除依赖某台开发机器或旧进程才能运行的情况 |
| 模型与额度控制 | 选定远程模型，统一请求计数；每个任务单独保存消耗记录 | 重试、故障和恢复不能偷偷获得一份新额度 |
| 可核对的业务环境 | 商品数据、查询与下单服务、网页站点、输入文件和订单账本 | 让结果可以独立算出来，避免只相信助手自报成功 |
| 持久保存与用户绑定 | 每个任务的进度、工作文件、身份、访问凭据和订单分别保存 | 换执行环境时保留正确任务，同时防止串到其他用户 |
| 独立检查和资源记录 | 保存工具请求、真实写入、运行事件、容器状态和资源样本 | 分清业务错误、运行机制失败和实验记录不完整 |

这些是实验设施，不表示未来产品必须照搬同一套代码。未来产品已有的账号、存储和调度服务可以接入相同职责。

## 2.2 比较时统一哪些条件

| 条件 | 本轮设置 | 为什么这样设置，以及有什么限制 |
| --- | --- | --- |
| 执行位置 | 候选、工具、浏览器、模拟服务和验收都在本地 Docker 容器；模型远程调用 | 先验证独立部署及状态边界；本地结果不能直接当成生产云平台性能 |
| 模型 | 使用选定的 `deepseek-v4-flash` | 减少模型不同带来的影响；框架默认提示和工具包装仍可能不同 |
| 单任务额度 | 通常最多 20 次模型请求、300 秒活跃时间，最多两次客户端重试 | 给各方案相同任务约束；恢复累计，不能重置额度。暂停等待另计，重新启动耗时计入活跃时间 |
| 数据变化 | 正式任务使用第一、第二、第三组固定数据；重点路线再补第四、第五组 | 更换商品和输入，降低只对一份数据有效的可能；同组不是多次随机重复，不能据此估计线上成功率 |
| 资源上限 | 整套实验最多 6 GiB 内存、3 个 CPU；单任务通常 2 GiB、1 个 CPU | 配套服务也计入；双任务专项改为每个执行程序 0.75 个 CPU，并另做相同接法的单任务对照 |
| 资源记录 | 目标每两秒一次；专项检查相邻记录是否超过五秒，并核对每份是否覆盖当时的实际容器 | 既要及时采样，也要记录完整；缺失不能补成零占用 |
| 普通与敏感操作 | 授权内普通写入自动执行；测试中明确禁止的操作直接拒绝 | 同时检查能做事和能守规则，不建设人工审批流程 |
| 暂停目标 | 保存任务进度、业务记录和工作文件；等待十分钟后换容器继续 | 验证能释放执行资源，不要求恢复原网页标签页、登录态或未提交表单 |

第一至第五组测试数据的原始生成编号依次为 101、202、303、404、505。编号用于重复生成相同输入，不是实验次数或分数；例如，前三组采购目录分别包含19、21、23种商品。每个候选都获得同样的任务要求，不提供标准答案或完整操作顺序。工具能力尽量保持相同粒度，不能给某条路线一个“一键完成采购”的工具，另一路线却要逐步查询和下单。

框架可以使用适合自己的官方接口，接入工作分别记录。我们比较的是完成同一目标所需的整套接法，不把不同默认设置隐藏成“完全相同的环境”。

## 2.3 设计了哪些实验，各自回答什么

为便于分享，以下按九个问题组织。它们与原实施任务表的编号不同，但都可以通过详细篇中的来源链接回到原记录。

| 实验 | 验证的问题 | 为什么采用这类测试 | 详细设计与结果 |
| --- | --- | --- | --- |
| 一：独立运行与额度 | 固定版本能否从全新环境启动，并遵守累计请求限制？ | 连续换两个新容器，排除旧环境依赖；再用模拟错误触发重试 | [基本能力篇](experiments/01-basic-capabilities.md) |
| 二：多步工具业务 | 能否查全数据、记住约束、做对写入并生成报告？ | 采购任务包含分页、筛选、排序、计算和下单，可独立核对 | [基本能力篇](experiments/01-basic-capabilities.md) |
| 三：网页操作 | 能否根据页面逐步完成登录、提交与下载？ | 只给基础页面动作，避免预写脚本包办流程 | [基本能力篇](experiments/01-basic-capabilities.md) |
| 四：扩展、规则与控制 | 新业务工具和状态好不好接，规则是否真正拦截，过程能否查看和停止？ | 普通成功与禁止操作配对，再加入错误、取消和重启读取 | [基本能力篇](experiments/01-basic-capabilities.md) |
| 五：暂停与继续 | 能否释放执行资源，之后接回同一任务？ | 运行中暂停、删除旧容器、等待十分钟、从原进度继续 | [恢复篇](experiments/02-pause-and-failure.md) |
| 六：突然故障 | 超时、临时失败、程序退出或确认消息丢失后，是否漏做或重复做？ | 四类故障与两种写入服务模式交叉，再用正常任务对照 | [恢复篇](experiments/02-pause-and-failure.md) |
| 七：多人使用 | 用户能否访问和控制自己的任务，且不会影响别人？ | 两个真实任务同时运行，交叉尝试读取、暂停、恢复和取消 | [多人使用与成本篇](experiments/03-users-and-cost.md) |
| 八：运行资源 | 空闲用户能否只保留数据，按需启动有什么收益和代价？ | 保持最多两个任务活跃，比较持续运行与按需启动，再增加用户并轮换 | [多人使用与成本篇](experiments/03-users-and-cost.md) |
| 九：用量与工程投入 | 为完成任务和补齐能力实际消耗了什么？ | 成功、失败、中止都登记；模型请求、用量、金额和人工投入分别看 | [多人使用与成本篇](experiments/03-users-and-cost.md) |

每项详细设计都说明准备条件、执行步骤和判定标准，并按参与框架列出实际结果、失败原因和结论。不同实验的参与范围如下；未参与某项实验，不代表该框架不支持相应能力。

**本轮扩展。** 首轮只有四条路线接入实验二至四。此后为另外四条路线补齐了同样的接法，重组候选镜像后各按第一至第三组完整执行五类任务，共 60 次运行、445 次模型请求。扩展结果单列在[基本能力篇的本轮八路线结果](experiments/01-basic-capabilities.md#本轮八路线结果扩展后)，不与首轮通过数相加。

| 实验 | 实际参与框架 | 结果范围 |
| --- | --- | --- |
| 一：独立运行与额度 | 全部八条路线 | 逐框架核对新环境运行与累计限额 |
| 二：多步工具业务 | 全部八条（首轮四条进入详细比较，本轮补齐另四条的正式三组） | 初筛两次任务、正式三组输入、两条重点路线的两组补测分别列出 |
| 三：网页操作 | 全部八条路线（首轮四条，本轮补齐另四条） | 各框架逐组业务与结束状态；DSH、Deep Agents 另有两组补测 |
| 四：扩展、规则与控制 | 全部八条路线（首轮四条，本轮补齐另四条） | 扩展、两类拒绝、错误诊断、取消与新进程读取状态分别列出 |
| 五：暂停与继续 | DSH、Deep Agents | 各框架三组无暂停对照、暂停后继续与完整业务结果 |
| 六：突然故障 | DSH、Deep Agents | 普通对照、故障试跑、正式矩阵和关键窗口补测分别列出 |
| 七：多人使用 | DSH、Deep Agents | DSH 单用户对照与双用户试跑；Deep Agents 三组双用户结果 |
| 八：运行资源 | Deep Agents 实际执行；DSH 未形成完整对比实验 | 两用户按需与常驻、五用户按需分别列出；未执行档位明确标注 |
| 九：用量与工程投入 | 八条路线均有请求登记和接入记录；四条详细路线提取了模型用量 | 各框架的已知消耗、缺失范围和工程发现单列，实际金额与人工工时尚未知 |

其中 DSH 指 DeepSeek Harness，Deep Agents 指 Deep Agents + LangGraph。全部八条路线还包括 Pi Agent Core、Google ADK、Codex SDK 和 OpenHands。各表中的“通过”以对应实验的标准为准。未参与或未执行的任务不记作失败；已执行但未通过时，分别说明是业务要求未满足、控制机制未通过，还是实验依据不完整。

**术语约定。** 后面各篇统一使用三个词，不再混用：

| 用词 | 指什么 | 不是指什么 |
| --- | --- | --- |
| **执行程序** | 承载某个任务、负责跑 Agent 循环的进程 | 不指业务服务、工具服务或模型代理；这些统称**共享服务** |
| **执行容器** | 运行该执行程序的 Docker 容器 | 不指整个实验环境 |
| **Worker** | 与“执行程序”同义，仅在引用框架原生概念（如 Worker 控制接口）时保留 | 不作为本报告的独立术语 |

本仓库代码与实施任务表沿用英文 `Worker`；分享报告为便于通读采用中文“执行程序”，两处指同一对象。

## 2.4 为什么分三个阶段推进

**先广泛初筛八条路线。** 检查来源、固定环境、模型与工具接入及请求限制。范围包括 DeepSeek Harness、OpenClaw、Deep Agents + LangGraph、OpenAI Agents SDK、Pi Agent Core、Google ADK、Codex SDK 和 OpenHands。

**再详细比较四条路线。** DeepSeek Harness 对应客户端上云的实现研究，OpenClaw 对应已有云端业务反馈涉及的能力，Deep Agents 和 OpenAI Agents SDK 分别提供自定义执行过程和使用轻量框架的观察角度。四者执行相同的工具、网页、扩展和规则任务。

**最后集中做两条路线的专项。** DeepSeek Harness 和 Deep Agents 进入暂停、故障和多用户等深入验证。这些工作需要新的接入与检查，因此根据前一阶段结果集中投入。其他候选只保留已验证的范围，暂未深入不等于不支持。

专项开始前先校准工具、故障注入和检查程序，再做正常任务或最小流程对照，避免把实验设施的问题当成框架缺陷。校准和对照也单独记录，不计入正式能力通过数。

## 2.5 怎样从记录得到结论

一次实验要分别回答三个问题：

1. **业务是否完整完成。** 订单、文件、金额和操作过程都与要求一致。例如，每页最多五条也是约定，最终订单碰巧正确不能抵消违规查询。
2. **被测机制是否成立。** 是否真的暂停、换新程序继续、拒绝跨用户操作，或者没有重发已完成的写入。
3. **实验是否有效。** 固定材料、执行状态、资源记录和清理是否符合条件。证据不完整时，先保留缺口，不凭最终一句“完成”下结论。

这让我们能解释两种看似矛盾的结果：Deep Agents 可以恢复成功但业务仍违反分页要求；某次任务可以做对，但资源记录缺失，使成本问题仍没有答案。

变更源码接法或检查方式后，使用新的批次记录，旧失败不覆盖。DeepSeek Harness 业务状态保存的修订、故障实验早期的采样中止都按此处理。正式任务、正常对照、补充输入和诊断不混成一个总成功率。

首轮在约定阶段和资料复核完成后收尾。多用户与成本中的未完成项保留下来，不为了得到全绿结果持续扩跑。下一轮是否继续，取决于真实业务和投入价值。

# 4. 首轮结论与下一步

首轮的价值，是把“选哪个框架”拆成了可以讨论的具体工作：基本任务是否完整做对，执行过程能否接入，保存进度后能否释放资源，故障与多人使用还缺什么。结果支持下一步的小范围业务验证，尚不足以直接决定生产迁移或承诺费用下降。

## 4.1 回到三个出发点，分别得到什么

**对于现有 DeepSeek Harness 客户端上云，已经找到可验证的技术基础。** 官方框架加实验接入后，在独立容器中完成工具与网页任务、暂停后换容器继续，以及固定故障阶段。可以据此盘点客户端需要调整的运行入口、工具位置、持久保存和产品接口。受测的不是自有客户端，因此已有客户端代码能复用多少，还要核对版本与依赖差异。

**对于 OpenClaw 云端业务反馈，已经看到可以研究的接点与限制。** 官方开源版本有工具插件、过程记录和会话保存接口，本轮接法也遇到了网页预算、执行规则未触发和取消时内存不足等问题。它们提供排查方向，不直接证明现有业务也有这些故障，更不能把现有部署方式都归因于框架。

**对于更多框架的云端能力，已经形成分层证据。** 八条路线均接上模型和工具；四条做了详细业务与控制比较；两条进一步验证暂停、故障和多人使用。Deep Agents 展示了明确保存进度和继续执行的能力，轻量框架也有基本任务与扩展证据。验证深度不同的候选，保留各自已知能力和未测问题，方便以后按需求选择。

## 4.2 哪些结论有证据，哪些还没有

| 当前判断 | 直接依据 | 对实际工作的含义 |
| --- | --- | --- |
| 多步工具和网页任务已有可用起点 | 四条详细路线的逐类结果；多条网页任务完整完成 | 可以围绕真实业务试接，但要继续检查约束和调用余量，不能只看最终回答 |
| 任务状态可以独立于执行程序保存 | 两路线暂停后删除旧容器、等待十分钟，再由新容器继续，各3/3 | 可以研究按需启动与回收，用户保留任务不必等于程序持续运行 |
| 故障恢复与业务正确性是两项工作 | 两路线正式强制退出恢复各6/6；完整故障业务为23/24和10/24，失败均仅分页 | 进度恢复有效，仍要保证工具参数、读取范围和业务规则被完整遵守 |
| 用户访问边界可以接到框架外部 | Deep Agents三组双用户边界检查通过，整组2/3 | 产品后端负责可信身份，框架与接入层负责绑定和执行；换入口仍需重新验证 |
| 尚不能判断生产成本优势 | 两用户采样有空档；五用户一份跨阶段资源缺测；完整用量和金额仍缺 | 空闲回收方向有依据，节省多少和唤醒是否可接受要通过有效配对实验回答 |
| 尚不能判断迁移工期和维护排名 | 已列接入文件与维护职责，未取得可靠工时或升级实验 | 需要记录真实业务试接过程，代码行数和自动构建时间不能代替人力 |

详细依据分别见[基本能力](experiments/01-basic-capabilities.md)、[暂停与故障](experiments/02-pause-and-failure.md)、[多人使用与成本](experiments/03-users-and-cost.md)。

## 4.3 客户端上云，应当怎样拆工作

以下是根据实验形成的核对清单，不表示现有客户端全部缺失这些能力。

| 工作 | 首轮已经提供什么 | 与实际产品连接时要做什么 |
| --- | --- | --- |
| 后台任务入口 | 官方框架和实验入口可在容器中执行任务 | 核对客户端如何提交任务、查询进度和取回结果，确定产品接口 |
| 工具与浏览器 | 已有由模型逐步操作的工具、网页任务 | 盘点本机路径、桌面进程、账号与网络依赖，逐个决定服务端接法 |
| 进度和工作文件 | 暂停与故障后能使用原状态继续 | 接入持久存储，确定保存范围、版本兼容及恢复责任，保留操作凭据 |
| 运行控制和过程展示 | 已有事件、错误和控制接口；取消仍有路线差异 | 明确暂停何时生效、取消后哪些操作已发生，让用户看到一致状态 |
| 用户身份与归属 | 模拟后端下部分多用户接入已验证 | 将可信产品身份绑定任务、文件、工具与控制请求，覆盖实际使用入口 |
| 资源分配与回收 | 暂停期间执行程序可关闭，按需唤醒与轮换已有探索 | 接入调度、并发限制和回收策略，补完整资源观测及启动延迟评价 |

故障注入、模拟采购、独立判分属于研究设施，未来产品不需要原样搬过去；身份绑定、保存进度、运行控制和资源管理这些职责则必须有人承担，可以复用已有产品服务。

## 4.4 各路线下一步适合投入什么

| 路线 | 当前建议及依据 | 会影响选择的条件 |
| --- | --- | --- |
| DeepSeek Harness | 优先挑一段真实业务做云端试接。它与已有客户端有关联，且本轮基本任务、暂停和故障业务表现较完整 | 先限定取消、用户接入、按需运行的补齐范围；如果要长期修改核心或维护大量内部契约，优势需要重新评估 |
| Deep Agents + LangGraph | 保留为需要深入定义步骤、状态与恢复方式的路线；保存和继续执行、多用户边界已有证据 | 团队能承担任务与资源管理接入，并能解决反复出现的业务约束违规；不能因恢复方便就认定总体成本低 |
| OpenClaw | 保留改造现有方案的选项，用官方实验结果寻找扩展、过程展示和控制接点 | 要与实际产品的版本和接法对应；若有限改动就能满足需求，继续利用已有积累可能比迁移更合适 |
| OpenAI Agents SDK | 当业务收敛为少量工具、简单步骤，且产品已有任务管理能力时，值得试接 | 完整暂停续跑、故障写入、用户边界和实例成本本轮未验；不要漏算这些补建工作 |
| Pi、Google ADK、Codex SDK、OpenHands | 保留初筛证据，遇到匹配其特点的业务时再决定深入哪条 | 暂未深入不等于不支持；也不能继承其他候选的恢复或多用户结论 |

这是按现有证据安排下一笔投入，不是综合名次。不同路线的结果同时受框架、模型、工具包装和接入方式影响，本轮没有把每个因素的因果贡献单独测出。

## 4.5 首轮未完成的部分，怎样转化成下一轮问题

首轮已经结束，以下是供业务确定后选择的后续工作，不是仍在后台执行的实验。

| 后续问题 | 如果决定继续，最小需要做什么 | 得到结果后怎样用于决策 |
| --- | --- | --- |
| 自有客户端实际需要改多少 | 对照官方实验版本盘点依赖，选一段真实任务完成提交、查看结果、暂停继续，并记录人工时间 | 把上云清单变成具体改动与交付范围 |
| DeepSeek Harness 用户接入是否可用 | 保留现有失败，先查清取消结果未知、有效并发与删除采样问题，再用固定新材料验证 | 判断该接法能否进入产品试接，而不是用两个主任务成功代替整体通过 |
| 新入口和浏览器是否保持用户边界 | 对目标入口做跨用户读取、控制和运行中数据隔离检查 | 决定可共享到哪一层，哪些资源应继续独立 |
| 按需启动是否值得做 | 修正跨阶段资源记录，确认业务完成后，以同工作量比较保留程序与按需启动 | 在空闲占用、启动等待与工程投入之间作取舍；再决定是否扩大用户档位 |
| 费用和维护投入是否可接受 | 按明确范围补登记格式、缺失用量与可靠价格，记录业务试接及一次版本升级的实际工作 | 形成可核对的成本依据，而不由请求总数或文件行数猜测金额和人日 |

故障专项的本轮固定阶段已经完成；后续应根据真实业务选择还值得覆盖的异常，不再笼统写成“等待正式故障实验结束”。多人使用、实例成本和完整计量的缺口则明确保留，需要时再投入。

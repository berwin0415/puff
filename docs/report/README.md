# 智能助手如何上云：八条开源路线的实测报告

**一句话结论：** 八条开源 Agent 框架都能在容器里跑通工具和网页任务；**状态保存和故障恢复**只在 DeepSeek Harness（下称 DSH）和 Deep Agents 两条路线上实测成立，**用户隔离**只验了 Deep Agents 一条路线，**成本收益**和**迁移工作量**本轮都没有答案。三个出发点里，只有「其他框架能做什么」被完整回答。

**建议的下一步：** 用 DeepSeek Harness 挑一段真实业务做云端试接，**边做边记录人工投入**。这一步同时回答本轮最大的两个空白——「客户端要改多少」和「过程透不透明够不够用」。在拿到真实工时和真实排障体验之前，不建议做迁移选型决策或承诺成本收益。

本轮实测八条路线、九个实验维度，累计 **284 次完整运行、2,453 次模型请求**，已计量 **1,025 万 token**。数据截至 2026-10-28。

---

## 1. 要解决的问题

我们有一个基于 **DeepSeek Harness** 的客户端，想把它搬到云端持续服务多个用户。同时，现有基于 **OpenClaw** 的云端业务有三个反馈值得验证：过程看不清、业务定制费力、用户增长带来实例成本增长。

| 问题 | 关心的具体能力 |
| --- | --- |
| 现有客户端怎么上云？ | 任务入口、状态保存、用户绑定要改多少 |
| 现有云端业务哪里可改善？ | 过程透明、业务扩展、实例成本 |
| 其他框架能做什么？ | 八条路线各自的云端能力和缺口 |

三个问题分别回答到什么程度，见[第 6 节](#6-结论三个出发点分别回答到什么程度)——**只有一个被完整回答**。

**受测对象不是自有产品。** 全部使用官方开源固定版本 + 本仓库接入代码，自行构建容器。结论对应「某个框架 + 某种接法」，迁移到实际产品仍需核对版本差异。

## 2. 我们到底在比什么

大模型只会「读入文字、输出文字」。要让它查资料、调工具、改文件、出错后继续，中间必须有一层运行系统，行业里叫 **Agent Harness**。

```
用户请求 → [ 模型：理解 + 决策 ] → [ Harness：调工具 / 存状态 / 控停止 / 记账 ] → 业务系统
```

本轮测的就是中间那层。

| 术语 | 含义 |
| --- | --- |
| **模型** | 负责理解与决策，如 `deepseek-v4-flash` |
| **Harness / 框架** | 围绕模型的运行系统 |
| **候选 / 路线** | 一个框架 + 本仓库为它写的接入代码 |
| **实验接入** | 我方补的外层代码，**不算框架能力** |
| **执行程序** | 跑某个 Agent 循环的进程 |
| **共享服务** | 工具服务、模拟业务、模型代理 |
| **DSH** | DeepSeek Harness 的简称 |
| **DA / Deep Agents** | Deep Agents + LangGraph 的简称 |
| **种子** | 一组固定的测试数据编号（101/202/303），同一种子生成同样商品和订单 |

**为什么要区分「框架自带」与「实验补充」：** 同样是「通过」，有的靠框架，有的靠我们写的代码。后者意味着产品化时要自己养一套。

## 3. 八条路线

从「给你的东西有多少」看，大致排成一条光谱：

```
轻量库 ←────────────────────────────────────────→ 完整服务
Pi Core   Codex SDK   Agents SDK   ADK   Deep Agents   OpenHands   DSH   OpenClaw
```

**为什么 DSH 排在 OpenHands 右边：** 两者都能保存会话状态，差别在 DSH 额外自带**持久目标**——任务有明确的目标生命周期，暂停后是「继续这个目标」，而不是「恢复一段对话」。这是它能做到暂停续跑的基础。**OpenClaw 最靠右**，因为它连常驻后台服务、插件系统和会话库都带齐了。

| 路线 | 版本 | 形态 | 为什么选它 |
| --- | --- | --- | --- |
| **DeepSeek Harness** | 0.1.2-alpha.3 | 完整运行系统，含持久目标 | 已有客户端的底座 |
| **OpenClaw** | 2026.10.5 | 产品形态：Gateway + 插件 | 现有云端业务的底座 |
| **Deep Agents + LangGraph** | 0.7.28 / 1.2.16 | 图状态机，检查点完整 | 最适合验证「中断后继续」 |
| **OpenAI Agents SDK** | 0.24.0 | 轻量库，取消接口直接 | 代表「产品已有任务管理」的用法 |
| **Pi Agent Core** | 1.3.0 | 最轻，只有内存中的 Agent 对象 | 代表「只要循环，其余自建」 |
| **Google ADK** | 2.12.0 | Runner + 标准会话服务 | 观察「会话」与「恢复」的距离 |
| **OpenHands** | 1.56.0（SDK） | Conversation 自带持久化 | 持久化设计最完整 |
| **Codex SDK** | rust-v0.163.0 | SDK 包装 codex CLI | 代表「复用现成 CLI」 |

**投入分三档，不代表能力高低：** 八条都做了独立运行、工具和网页；八条都做了扩展与规则；只有 **DSH 和 Deep Agents** 额外做了暂停、故障矩阵、多人及成本专项——因为这两项需要为每个候选单独写恢复接法，成本高。

未做某项实验**只说明没测**，不说明不支持。

## 4. 怎么测的

九项实验按递进设计：先确认能跑，再加业务复杂度，最后加压。

| # | 实验 | 核心问题 | 参与 |
| --- | --- | --- | --- |
| 一 | 独立运行与额度 | 能否从干净环境启动，累计额度跨容器有效？ | 八条 |
| 二 | 多步工具业务 | 分页查询、筛选、计算、下单、报告能否全对？ | 八条 |
| 三 | 网页操作 | 能否登录、跨页、填表、下载，而非只启动浏览器？ | 八条 |
| 四 | 扩展、规则与控制 | 新工具与状态能否接？规则能否真拦？能否取消？ | 八条 |
| 五 | 暂停续跑 | 停掉后换容器能否接回？是否重发？ | DSH、Deep Agents |
| 六 | 突然故障 | 四类故障下漏做或重做？ | DSH、Deep Agents |
| 七 | 多人使用 | A 能否看到或控制 B 的任务？ | DSH、Deep Agents |
| 八 | 实例成本 | 按需启动省多少，代价多少？ | 仅 Deep Agents |
| 九 | 用量与投入 | 实际花了多少？ | 八条 |

**统一的对照条件：** 全部在本机 Docker 里跑、模型远程调用；统一用 `deepseek-v4-flash`；预算常规 **20 次**请求 / 300 秒，网页用例 **40 次**；数据用三组固定种子（101/202/303），重点路线再补两组；授权内操作自动执行，敏感操作在执行层直接拒绝，**不设人工审批流程**。

**判定分三层，缺一不可：**

1. **业务是否完整完成** — 报告、订单、金额、操作过程全部符合
2. **被测机制是否成立** — 是否真的暂停、换容器、拒绝、不重发
3. **实验是否有效** — 材料、采样、清理是否可靠

> 为什么要分三层：Deep Agents 能恢复成功但业务违反分页；某次任务做对了但资源记录缺失。混在一个「通过率」里会同时丢失这两种信息。

## 5. 结果

### 5.1 总体

八条路线，五类任务，每类三组输入。**全部路线统一按网页 40 次、其余 20 次预算统计。**

| 路线 | 工具 | 网页 | 敏感拒绝 | 扩展 | 超量拒绝 | 合计 |
| --- | --- | --- | --- | --- | --- | --- |
| **DeepSeek Harness** | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **15/15** |
| **Google ADK** | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **15/15** |
| **OpenHands** | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **15/15** |
| **Pi Agent Core** | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **15/15** |
| **Codex SDK** | 3/3 | 3/3 | 2/3 | 3/3 | 3/3 | **14/15** |
| **OpenAI Agents SDK** | 3/3 | 3/3 | 1/3 | 2/3 | 3/3 | **12/15** |
| **Deep Agents** | 2/3 | 3/3 | 3/3 | 1/3 | 3/3 | **12/15** |
| **OpenClaw** | 2/3 | 3/3 | 3/3 | 1/3 | 1/3 | **10/15** |

**读这张表要注意三点：**

1. **这个合计包含两类「应该拒绝」的任务，不是业务成功率。**
2. **共 12 个失败格，扩展列占 5 个**，其余分散在敏感拒绝（3）、工具与超量拒绝（各 2）。其中 **7 格是分页违规**（扩展 5、工具 2），**3 格是模型自己拒绝、规则未被触发**（敏感拒绝），另有 2 格是规则没真正拦下（超量拒绝）——**都不是框架做不了**。
3. **网页一列全部是 3/3**，但代价差别很大：OpenClaw 和 Codex 要多花六到八成调用（见 5.2①）。**通过率相同不代表成本相同。**

### 5.2 五个关键发现

**① 网页任务真正的问题不是「能不能」，而是「多贵」**

提高到 40 次预算后八条路线全部通过，但消耗分成两档：

| 档位 | 路线（平均请求） |
| --- | --- |
| 常规 **17.7–19.3 次** | Agents SDK 17.7、ADK 18.3、OpenHands 18.3、DSH 18.7、Pi 19.0、Deep Agents 19.3 |
| 高消耗，**多出 60–80%** | OpenClaw **31.7**、Codex **32.7** |

**用统一预算会误判高消耗路线。** OpenClaw 和 Codex 在 20 次下被判失败，在 40 次下通过——能力没问题，成本有问题。

**② 分页违规跨框架普遍存在**

「每次查询最多 5 条」这条约束，在 Pi、OpenHands、Deep Agents、OpenClaw 上都出现过违规。**报告和订单都对，只有分页不合规**，因此判失败。

这不是某个框架的缺陷，更像任务约束与模型行为的匹配问题。但结论是硬的：**业务正确性不能靠模型自觉。**

**③ 敏感拒绝发生在哪一层，差别很大**

| 在哪拦截 | 含义 | 路线 |
| --- | --- | --- |
| **框架自己拦下** | 请求还没发出去就被执行层拒绝 | DSH 可以 |
| **业务服务拦下** | 请求已发出，业务服务回 403 | 其余全部 |

**如果业务服务本身不拒绝，多数框架不会替你拦住。**

另有一类要单独看：Agents SDK 和 Codex 有组次是**模型自己口头拒绝、根本没调工具**。没有副作用，但规则从未被测试——按标准判失败。

**④ 恢复能力：能接回不等于业务做对**

DSH 与 Deep Agents 各跑 3 条暂停链（暂停 → 删除执行容器 → 等 10 分钟 → 新容器继续）。**原生恢复都成功，但完整业务只有 3/3 与 1/3。**

| 项目 | DSH | Deep Agents |
| --- | --- | --- |
| 暂停后换容器原生继续 | 3/3 | 3/3 |
| 其中完整业务通过 | **3/3** | **1/3** |
| 暂停链 / 不暂停基线的模型请求数 | 35 / 32 | 17 / 17 |
| 等待期执行程序、内存 | 0 个、0 MiB | 0 个、0 MiB |

故障矩阵同样：DSH 正式 **23/24**、Deep Agents **10/24**。**两条路线合计 15 个失败格，全部只是分页违规**——DSH 唯一失格是「模型超时 / 非幂等 / 第一组」，Deep Agents 失 14 格。业务其余部分（报告、订单、金额）都正确。两条路线强制退出后恢复各 6/6，已提交操作重发 0。

**⑤ 用户边界可以外置，但成本收益还算不出**

Deep Agents 三组双用户：边界检查全部通过，整组 2/3（第一组有一个用户的业务失败）。DSH 双用户试跑整体未通过（取消未确认、并发未验证）。

按需 vs 常驻，两用户各 3/5 可评分业务。**采样存在超过 5 秒的空档，整阶段均值与峰值保持未知**——不算节省比例。

### 5.3 用量

**先分清两个数字，它们统计的不是同一件事：**

| 数字 | 含义 |
| --- | --- |
| **2,453 次**（开篇） | **本轮实验**实际发出的模型请求，按每次运行的结果账本汇总 |
| **2,485 条**（下表） | **整个调研期**所有运行留下的请求记账，含早期批次、诊断和中止任务 |

| 项目 | 数值 |
| --- | --- |
| 已登记的请求记录库 | 343 个（每个任务一份独立计数库） |
| 请求记账 | 2,485 条，其中 2,416 条收到远程成功响应 |

## 6. 结论：三个出发点分别回答到什么程度

开篇的三个问题，逐条给出回答状态。**标 ❌ 的部分本轮没有答案，不要当作已解决。**

| 出发点 | 回答状态 |
| --- | --- |
| 一、现有客户端怎么上云 | ⚠️ **能力已回答，工作量未回答** |
| 二、现有云端业务哪里可改善 | ⚠️ **三条反馈只答清两条** |
| 三、其他框架能做什么 | ✅ **已完整回答** |

### 6.1 出发点一：现有客户端（DSH）怎么上云？

| 子问题 | 回答 | 依据 |
| --- | --- | --- |
| 框架能力够不够 | ✅ **够**。首轮四条路线里唯一 15/15；八条全测后有四条并列 15/15 | DSH 15/15；暂停 3/3；故障 23/24 |
| 云端要的几项能力是否成立 | ✅ **基本成立**。状态可脱离执行程序、故障后能恢复 | 暂停换容器 3/3；强制退出恢复 6/6，重发 0 |
| 还要补哪些 | ⚠️ **三个明确缺口** | 取消 2 次失败；用户接入未通过；按需运行未验证 |
| **要改多少工作量** | ❌ **没有回答** | 未取得任何可靠工时数据 |

**结论：可以挑一段真实业务开始试接，但不能据此排期。** 试接时用真实任务记录人工时间，才能回答“要改多少”。

已有的三个缺口按影响排序：

1. **取消**——调用了官方的取消接口，但框架没有产生表示「本轮已结束」的结束事件，两次都判失败。用户点“停止”后能否看到确定状态，现在没有答案。
2. **用户接入**——双用户试跑整体未通过，原因是取消未确认、并发窗口未命中、删除采样失败。不是“不支持”，是“没验成”。
3. **按需运行**——等待期执行程序确实归零（0 个、0 MiB），但共享服务仍占 58–59 MiB，完整成本未测。

### 6.2 出发点二：OpenClaw 云端业务的三个反馈

| 反馈 | 回答状态 | 本轮结论 |
| --- | --- | --- |
| 过程看不清 | ❌ **本次未测** | 九项实验里没有针对“过程透明”的项。只知道框架有会话事件和插件接点，**没测排障效率** |
| 业务定制费力 | ✅ **已回答** | 扩展能接：三轮都正确写入业务状态，**失败全部来自分页违规**，与扩展本身无关；真正的问题是**规则不可靠**——超量拒绝只有 1/3 在执行层真正拦下 |
| 实例成本随用户增长 | ❌ **未在 OpenClaw 上测过** | 本轮唯一的成本实验（实验八）只跑了 Deep Agents：按需比常驻省内存（空闲 31.41 vs 282.10 MiB），但采样有超 5 秒空档，峰值与节省比例未知。**OpenClaw 未参与，不能拿这组数据回答它的成本问题** |

**两条反馈没有答案，必须说清：**

- **“过程看不清”** 是三个反馈之首，但本轮**没有任何实验覆盖它**。只确认了框架有会话事件和插件接点，**没测排障效率**——不要读成问题已解决。
- **“实例成本”** 做了实验，但**只测了 Deep Agents，OpenClaw 未参与**。现有数据不能直接套用到 OpenClaw。

**“业务定制费力”的答案值得展开：** 插件系统本身能接新工具（三轮状态写入都正确），失败在规则层——任务要求买 4 件、上限 3 件，OpenClaw 只有 1/3 真正在执行层拦下。这说明**定制能力的瓶颈不在“能不能加工具”，而在“规则能否可靠生效”**。

### 6.3 出发点三：其他框架能做什么？

✅ **已完整回答。**

| 路线 | 建议 | 前提条件 |
| --- | --- | --- |
| **Deep Agents** | 保留为「需要深入定义步骤与状态」的路线 | 团队能自建应用运行层，并解决反复出现的分页违规 |
| **OpenClaw** | 保留改造现有方案 | 先解决预算消耗（比常规高七成）；取消有个坑——任务由 HTTP 接口发起，用另一套 RPC 的停止接口无效，必须断开原 HTTP 连接 |
| **OpenAI Agents SDK** | 业务收敛、产品已有任务管理时试接 | 暂停续跑、故障写入、用户边界、成本均未验证 |
| **ADK / OpenHands / Pi** | 补齐路线里表现最稳，可按需评估 | 暂停、故障、多人、成本全部未测 |
| **Codex SDK** | 调用消耗最高，需谨慎 | 网页均值 32.7 次；输出 token 无硬上限；模型元数据缺失 |

选型时最该看的三件事，按重要性排序：

1. **调用消耗**——同样完成任务，路线之间差六到八成，直接决定单位成本
2. **规则生效位置**——框架层拦截（DSH）还是业务服务兜底（其余全部）
3. **恢复粒度**——能否从原状态继续，还是只能重跑

### 6.4 本轮没有回答的问题

按对下一步的影响排序：

**优先级建议：先做第 1 项，其余按需。** 第 1 项是唯一能同时解锁多个决策的动作；第 2 项可以顺带完成（试接时本来就会遇到排障）。

| 优先 | 未回答的问题 | 影响 | 最小补证动作 |
| --- | --- | --- | --- |
| **①** | **客户端要改多少工作量** | 无法排期、无法评估投入产出 | 用一段真实任务试接，记录人工时间 |
| **②** | **过程透明能改善多少** | OpenClaw 首要反馈无结论 | 试接时记录一次真实排障花多久 |
| ③ | DSH 用户接入是否可用 | 决定能否多用户上线 | 查清取消、并发、采样三个问题后重验 |
| ④ | 按需启动是否值得 | 决定实例成本策略 | 修正跨阶段采样后重做配对 |
| ⑤ | 费用是否可接受 | 无法做成本决策 | 补登记格式、缺失用量与价格 |

# 智能助手如何上云：八条开源路线的实测报告

**一句话结论：** 八条开源 Agent 框架都能在容器里跑通工具和网页任务，但「能跑」与「能当云端服务用」之间还隔着状态保存、故障恢复、用户隔离和成本控制四道关，每道关的补建工作量差别很大。

本轮实测八条路线、九个实验维度，累计 **284 次完整运行、2,453 次模型请求**，已计量 **1,025 万 token**。数据截至 2026-10-28。

---

## 1. 要解决的问题

我们有一个基于 **DeepSeek Harness** 的客户端，想把它搬到云端持续服务多个用户。同时，现有基于 **OpenClaw** 的云端业务有三个反馈值得验证：过程看不清、业务定制费力、用户增长带来实例成本增长。

| 问题 | 关心的具体能力 |
| --- | --- |
| 现有客户端怎么上云？ | 任务入口、状态保存、用户绑定要改多少 |
| 现有云端业务哪里可改善？ | 过程透明、业务扩展、实例成本 |
| 其他框架能做什么？ | 八条路线各自的云端能力和缺口 |

**受测对象不是自有产品。** 全部使用官方开源固定版本 + 本仓库接入代码，自行构建容器。结论对应「某个框架 + 某种接法」，迁移到实际产品仍需核对版本差异。

## 2. 我们到底在比什么

大模型只会「读入文字、输出文字」。要让它查资料、调工具、改文件、出错后继续，中间必须有一层运行系统，行业里叫 **Agent Harness**。

```
用户请求 → [ 模型：理解 + 决策 ] → [ Harness：调工具 / 存状态 / 控停止 / 记账 ] → 业务系统
```

本轮测的就是中间那层。

| 术语 | 含义 |
| --- | --- |
| **模型** | 负责理解与决策，如 `deepseek-v4-flash` |
| **Harness / 框架** | 围绕模型的运行系统 |
| **候选 / 路线** | 一个框架 + 本仓库为它写的接入代码 |
| **实验接入** | 我方补的外层代码，**不算框架能力** |
| **执行程序** | 跑某个 Agent 循环的进程 |
| **共享服务** | 工具服务、模拟业务、模型代理 |

**为什么要区分「框架自带」与「实验补充」：** 同样是「通过」，有的靠框架，有的靠我们写的代码。后者意味着产品化时要自己养一套。

## 3. 八条路线

从「给你的东西有多少」看，大致排成一条光谱：

```
轻量库 ←────────────────────────────────────────→ 完整服务
Pi Core   Codex SDK   Agents SDK   ADK   Deep Agents   OpenHands   DSH   OpenClaw
```

| 路线 | 版本 | 形态 | 为什么选它 |
| --- | --- | --- | --- |
| **DeepSeek Harness** | 0.1.2-alpha.3 | 完整运行系统，含持久目标 | 已有客户端的底座 |
| **OpenClaw** | 2026.10.5 | 产品形态：Gateway + 插件 | 现有云端业务的底座 |
| **Deep Agents + LangGraph** | 0.7.28 / 1.2.16 | 图状态机，检查点完整 | 最适合验证「中断后继续」 |
| **OpenAI Agents SDK** | 0.24.0 | 轻量库，取消接口直接 | 代表「产品已有任务管理」的用法 |
| **Pi Agent Core** | 1.3.0 | 最轻，只有内存中的 Agent 对象 | 代表「只要循环，其余自建」 |
| **Google ADK** | 2.12.0 | Runner + 标准会话服务 | 观察「会话」与「恢复」的距离 |
| **OpenHands** | 1.56.0（SDK） | Conversation 自带持久化 | 持久化设计最完整 |
| **Codex SDK** | rust-v0.163.0 | SDK 包装 codex CLI | 代表「复用现成 CLI」 |

**投入分三档，不代表能力高低：**

| 档位 | 路线 | 测了什么 |
| --- | --- | --- |
| 初筛 | 全部八条 | 独立运行、累计额度、工具任务 |
| 详细 | 全部八条 | 再加网页、业务扩展、两类规则 |
| 专项 | DSH、Deep Agents | 再加暂停、故障矩阵、多人、成本 |

未做某项实验**只说明没测**，不说明不支持。

## 4. 怎么测的

九项实验按递进设计：先确认能跑，再加业务复杂度，最后加压。

| # | 实验 | 核心问题 | 参与 |
| --- | --- | --- | --- |
| 一 | 独立运行与额度 | 能否从干净环境启动，累计额度跨容器有效？ | 八条 |
| 二 | 多步工具业务 | 分页查询、筛选、计算、下单、报告能否全对？ | 八条 |
| 三 | 网页操作 | 能否登录、跨页、填表、下载，而非只启动浏览器？ | 八条 |
| 四 | 扩展、规则与控制 | 新工具与状态能否接？规则能否真拦？能否取消？ | 八条 |
| 五 | 暂停续跑 | 停掉后换容器能否接回？是否重发？ | DSH、DA |
| 六 | 突然故障 | 四类故障下漏做或重做？ | DSH、DA |
| 七 | 多人使用 | A 能否看到或控制 B 的任务？ | DSH、DA |
| 八 | 实例成本 | 按需启动省多少，代价多少？ | DA |
| 九 | 用量与投入 | 实际花了多少？ | 八条 |

**统一的对照条件：**

| 条件 | 设置 |
| --- | --- |
| 执行位置 | 全部在本地 Docker；模型远程调用 |
| 模型 | 统一 `deepseek-v4-flash` |
| 额度 | 常规 **20 次**模型请求 / 300 秒；网页用例 **40 次** |
| 数据 | 三组固定种子（101/202/303），重点路线再补两组 |
| 策略 | 授权内自动执行，敏感操作直接拒绝（不设人工审批） |

**判定分三层，缺一不可：**

1. **业务是否完整完成** — 报告、订单、金额、操作过程全部符合
2. **被测机制是否成立** — 是否真的暂停、换容器、拒绝、不重发
3. **实验是否有效** — 材料、采样、清理是否可靠

> 为什么要分三层：Deep Agents 能恢复成功但业务违反分页；某次任务做对了但资源记录缺失。混在一个「通过率」里会同时丢失这两种信息。

## 5. 结果

### 5.1 总体

| 路线 | 工具 | 网页 | 敏感拒绝 | 扩展 | 超量拒绝 | 合计 |
| --- | --- | --- | --- | --- | --- | --- |
| **DeepSeek Harness** | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **15/15** |
| **OpenAI Agents SDK** | 3/3 | 3/3 | 1/3 | 2/3 | 3/3 | **12/15** |
| **Deep Agents** | 2/3 | 3/3 | 3/3 | 1/3 | 3/3 | **12/15** |
| **OpenClaw** | 2/3 | 0/3 → 3/3※ | 3/3 | 1/3 | 1/3 | **7/15** |
| **Google ADK** | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **15/15** |
| **OpenHands** | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **15/15** |
| **Pi Agent Core** | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 | **15/15** |
| **Codex SDK** | 3/3 | 0/3 → 3/3※ | 2/3 | 3/3 | 3/3 | **14/15** |

※ 网页用例预算从 20 次提高到 40 次后重跑。前四行是首轮（20 次预算）结果，后四行是补齐后的完整结果。

**这个合计包含两类「应该拒绝」的任务，不是业务成功率。**

### 5.2 五个关键发现

**① 网页任务真正的问题不是「能不能」，而是「多贵」**

提高到 40 次预算后八条路线全部通过，但消耗分成两档：

| 档位 | 路线（平均请求） |
| --- | --- |
| 常规 **17.7–19.3 次** | Agents SDK 17.7、ADK 18.3、OpenHands 18.3、DSH 18.7、Pi 19.0、Deep Agents 19.3 |
| 高消耗，**多出 60–80%** | OpenClaw **31.7**、Codex **32.7** |

**用统一预算会误判高消耗路线。** OpenClaw 和 Codex 在 20 次下被判失败，在 40 次下通过——能力没问题，成本有问题。

**② 分页违规跨框架普遍存在**

「每次查询最多 5 条」这条约束，在 Pi、OpenHands、Deep Agents、OpenClaw 上都出现过违规。**报告和订单都对，只有分页不合规**，因此判失败。

这不是某个框架的缺陷，更像任务约束与模型行为的匹配问题。但结论是硬的：**业务正确性不能靠模型自觉。**

**③ 敏感拒绝发生在哪一层，差别很大**

| 层次 | 含义 | 路线 |
| --- | --- | --- |
| `candidate_execution` | 框架执行层拦下，HTTP 未发出 | DSH 可以 |
| `fixture_execution` | 业务服务返回 403 | 其余全部 |

**如果业务服务本身不拒绝，多数框架不会替你拦住。**

另有一类要单独看：Agents SDK 和 Codex 有组次是**模型自己口头拒绝、根本没调工具**。没有副作用，但规则从未被测试——按标准判失败。

**④ 恢复能力：能接回不等于业务做对**

DSH 与 Deep Agents 各 3 条暂停链，原生恢复 **3/3 与 3/3**，但完整业务只有 **3/3 与 1/3**：

| 项目 | DSH | Deep Agents |
| --- | --- | --- |
| 暂停后换容器原生继续 | 3/3 | 3/3 |
| 其中完整业务通过 | **3/3** | **1/3** |
| 暂停链 / 基线请求数 | 35 / 32 | 17 / 17 |
| 等待期执行程序、内存 | 0 个、0 MiB | 0 个、0 MiB |

故障矩阵同样：DSH 正式 **23/24**、Deep Agents **10/24**，十四个失败格**全部**仅分页失败。两条路线强制退出后恢复各 6/6，已提交操作重发 0。

**⑤ 用户边界可以外置，但成本收益还算不出**

Deep Agents 三组双用户：边界检查全部通过，整组 2/3。DSH 双用户试跑整体未通过（取消未确认、并发未验证）。

按需 vs 常驻，两用户各 3/5 可评分业务。**采样存在超过 5 秒的空档，整阶段均值与峰值保持未知**——不算节省比例。

### 5.3 用量

| 项目 | 数值 |
| --- | --- |
| 已登记预算库 | 343 个 |
| 调用记账 | 2,485 条（远程 200 共 2,416） |

## 6. 结论与建议

### 6.1 能确定什么

| 判断 | 依据 | 对工作的含义 |
| --- | --- | --- |
| 多步工具与网页任务有可用起点 | 八条路线多数通过；网页提高预算后全部通过 | 可围绕真实业务试接，但要盯**调用消耗**而非只看通过率 |
| 状态可独立于执行程序保存 | 两路线暂停后删容器、等 10 分钟、新容器继续，各 3/3 | 按需启动与回收值得研究 |
| 恢复与业务正确性是两件事 | 强制退出恢复 6/6，但完整业务 23/24、10/24 | 进度恢复有效，业务约束仍要单独保证 |
| 用户边界可接到框架外部 | DA 三组边界检查全过 | 产品后端管身份，框架管执行 |
| 生产成本优势尚不能判断 | 采样空档、缺测、无完整用量 | 节省比例要有效配对实验才能回答 |
| 迁移工期尚不能判断 | 未取得可靠工时 | 代码行数和构建时间不能代替人力 |

### 6.2 各路线下一步

| 路线 | 建议 | 前提条件 |
| --- | --- | --- |
| **DeepSeek Harness** | **优先挑一段真实业务做云端试接** | 先补取消（两次缺原生结束事件）、用户接入、按需运行 |
| **Deep Agents** | 保留为「需要深入定义步骤与状态」的路线 | 团队能自建应用运行层，并解决反复出现的分页违规 |
| **OpenClaw** | 保留改造现有方案 | 先解决预算消耗（比常规高七成）和取消路径（必须走 HTTP 断连） |
| **OpenAI Agents SDK** | 业务收敛、产品已有任务管理时试接 | 暂停续跑、故障写入、用户边界、成本均未验证 |
| **ADK / OpenHands / Pi** | 补齐路线里表现最稳，可按需评估 | 暂停、故障、多人、成本全部未测 |
| **Codex SDK** | 调用消耗最高，需谨慎 | 网页均值 32.7 次；输出 token 无硬上限；模型元数据缺失 |

### 6.3 没回答的问题

1. **自有客户端要改多少** — 需对照官方版本盘点依赖，并用一段真实任务记录人工时间
2. **DSH 用户接入是否可用** — 需查清取消结果未知、有效并发、删除采样三个问题
3. **按需启动是否值得** — 需修正跨阶段资源记录后重做配对
4. **费用是否可接受** — 需补登记格式、缺失用量和可靠价格

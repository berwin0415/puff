# Google ADK 实验报告

**版本** google-adk 2.12.0，提交 `365084db7b14e796f36ad2929f987e8d83874961`
**本轮深度** 初筛 + 详细五类（网页、扩展、两类规则已补齐）
**定位** 会话服务齐全，本轮分页约束表现最稳的一条

## 一、测试对象与入口

源码来自 `google/adk-python`，导出 2,990 个源码文件。模型通过官方 `google.adk.models.lite_llm.LiteLlm` 适配远程模型——**这是本实验的接入选择，不是 ADK 的默认模型路径**。

依赖单独解析：上游没有提供适用于本安装组合的 `uv.lock`，所以本实验生成了独立的锁，冻结 76 个包。**没有安装 `google-adk[extensions]`**，因为其中包含本轮不用的 Kubernetes、云服务和其它框架集成。SQLite session 服务属于基础能力，不依赖扩展。

**入口**：官方 `Agent` / `LlmAgent` + `Runner.run_async`。任务的选工具、排序、下单全部由 Agent 和模型执行，没有预写步骤。

## 二、能力边界总表

| 能力项 | 框架自带 | 实验补充 | 本轮结论 |
| --- | --- | --- | --- |
| Agent 循环 | ✅ `Runner.run_async` | — | 正常 |
| 工具调用 | ✅ 原生 tool 定义 | HTTP 工具桥 | 正常 |
| 会话服务 | ✅ `SessionService`（可按 app/user/session 索引） | — | 正常 |
| 持久会话 | ✅ `SQLiteSessionService` 可用 | 未启用 | **未验证** |
| 任务中断恢复 | ⚠️ invocation resume 与历史保留是两件事 | 未接 | **未验证** |
| 工具执行前拦截 | ❌ 无 guard | 无 | 拒绝只靠服务端 |
| 浏览器接入 | ❌ 未接 | — | 未验证 |
| 业务扩展 | ❌ 无 | **未接通** | 见 4.1 |

**一个容易误解的点**：ADK 的 `SessionService` 用 `app_name/user_id/session_id` 做键，看起来像是多租户方案。但 **`user_id` 只是会话命名空间，不是身份认证**。本报告不把它算作多用户能力。

## 三、逐项实验

### 实验一：独立运行与额度

**效果**：两个新环境均完成真实模型与工具调用，2/2。模拟累计限额通过。

**一个接入细节**：ADK 的 LiteLLM 适配层和底层传输**各自都可能重试**。如果两层都开着，同一次失败会消耗两次额度。本实验明确协调了二者，避免重复叠加。

### 实验二：多步工具业务 —— 本轮表现最稳

**首轮结果**：两轮均通过（7、6 次请求）。

**本轮补充测试**（新数据）：

| 商品数据 | 结果 | 模型请求 | 失败项 |
| --- | --- | ---: | --- |
| 第一组（首轮） | 通过／通过 | 7、6 | — |
| **第二组**（本轮新增） | **通过** | 6 | — |
| **第三组**（本轮新增） | **通过** | 6 | — |

**四个补充种子、全部通过、每次 6–7 次请求。** 这是本轮测试中分页约束表现最好的一条：Pi 和 OpenHands 都在补充组出现了 `all_pages_read` 失败，ADK 没有。

**但要克制**：只有四组数据，不是可靠性统计。分页违规可能只是没有在这四组里出现，不代表不会发生。而且 ADK 没有进入五种子正式比较，样本量比四条详细路线小。

### 实验三：网页操作 —— 已接通，3/3 通过

**框架自带**：ADK 2.12.0 的依赖图里没有 MCP 客户端，本轮为它新增 `mcp==1.28.1`（与 Deep Agents、OpenAI Agents SDK 使用同一版本，便于横向比较）。

**实验补充**：`BaseTool` 子类包装官方 MCP 会话，工具名、描述、inputSchema 全部取自 MCP 服务。ADK 的 `run_async` 本身是异步的，因此直接持有 `AsyncExitStack`，比其他框架少一层线程桥。

**效果**：

| 商品数据 | 结果 | 模型请求 |
| --- | --- | ---: |
| 第一组 | 通过 | 18 |
| 第二组 | 通过 | 18 |
| 第三组 | 通过 | 19 |

**3/3 通过**（四十次预算）。三轮都在 18–19 次，**远低于四十次上限**——这条路线在二十次预算下已经能通过，提高预算对它的结论没有影响。

### 实验四：业务扩展、规则与控制

#### 4.1 新增工具与持久业务状态 —— 已接通，3/3 通过

**本轮已补齐。** 新增 `query_order_status`（转发一次真实 receipt 查询），业务状态由真实回执聚合后写入原生 Session 快照，并生成带哈希与 JSON 指针的投影。

**效果**：7、6、6 次请求，**3/3 通过**。业务状态来源是 ADK 自己的 `SessionService` 快照，不是另造的存储。

#### 4.2 敏感操作拒绝 —— 本轮新增，通过

**本轮补充测试**（新数据）：

| 项目 | 结果 |
| --- | --- |
| 判定 | **通过**（11/11 项） |
| 模型请求 | 2 |
| 业务写入 | 0 |
| 拒绝所在层 | **`fixture_execution`（业务服务端 403）** |
| 候选层是否有拒绝记录 | **无** |

与 Pi 相同：拒绝靠业务服务，不靠框架。因为 ADK 没有执行前的工具 guard。

#### 4.3 取消 —— 未接通

运维层拒绝（`尚未接通原生取消触发器`）。ADK 的 Runner 有 `abort` 类路径，但本轮没有接线验证。

## 五、适用条件与后续

**适合**：需要标准会话抽象、工具调用和 Runner 执行引擎的应用。本轮五类三组全部通过，是补齐路线里唯一零失败的。

**需要先确认的三件事**：

1. **会话服务是否够用**。`SessionService` 保存对话历史，但**历史不等于可续跑**。中断的任务能不能继续，是另一回事，本轮没测。
2. **`user_id` 不是认证**。如果要做多用户，可信身份必须在外面绑定。
3. **重试叠加**。LiteLLM 和传输层都可能重试，接的时候必须明确只留一层。

**如果要继续**：接通取消用例，并用 `SQLiteSessionService` 验证“中断后继续”与“历史回放”的区别——这是这条路线最有价值、也最容易搞混的一点。

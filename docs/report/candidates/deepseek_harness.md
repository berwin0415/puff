## 一、测试对象与入口

测试的是官方开源固定源码，**不是自有客户端**。镜像把官方源码、依赖和本仓库接入代码一起打进容器，新容器可独立启动。

本轮实际用到三层入口，各自冻结，不能互相继承结论：

| 入口 | 用在哪 | 官方接口 |
| --- | --- | --- |
| `DeepSeekHarness` SDK（`sdk-minimal`） | 初筛 I08 | SDK 自带源码启动，`tsx/esm` 加载 |
| 公开 `runProfile` + `agents.create/resume({setup})` | 详细四类 | 在首轮输入前挂好本任务工具、规则与浏览器连接 |
| Goal 变体（官方持久目标 + round driver + checkpoint 插件） | 暂停、故障 | 官方目标驱动循环 |

**为什么从 SDK 转到直接调 runtime**：高层 SDK 的 `createSession` 没有开放 `setup`，无法在首轮提示词之前异步挂好该 Agent 的 MCP 工具。本报告不能把这个限制说成框架缺陷，它只是接入路径的选择依据。

## 二、能力边界总表

这张表是整份报告的核心。每一行回答一个问题：**这项能力是框架给的，还是我们自己在外面建的？**

| 能力项 | 框架自带 | 实验补充 | 本轮结论 |
| --- | --- | --- | --- |

## 三、逐项实验

### 实验一：独立运行与额度

**要求的能力**：从全新环境启动；累计请求限制跨容器有效。

**框架自带**：源码启动支持（缺构建产物时用 `tsx/esm`）。本身不提供请求计数或预算。

**实验补充**：统一计数服务在请求发往模型前预占额度，SQLite 持久化并绑定运行凭证。真实密钥只由代理持有，候选只拿到本地 run token。

**效果**：两个新环境均完成真实模型与工具调用，2/2。模拟重试与跨容器累计限额通过。**额度是实验补建的，不是框架能力。**

### 实验二：多步工具业务

**要求的能力**：分页查询（每页最多 5 条）、按条件筛选、按价格与编号排序、金额计算、写入下单、生成报告。

**框架自带**：工具调用循环。原八项工具由统一服务提供，框架只负责决定何时调用。

**实验补充**：工具 schema 接入、工作区文件工具。**没有**代办筛选、排序或下单——模型仍自己决定下一步。

**效果**：

| 材料组 | 第一组 | 第二组 | 第三组 | 合计 |
| --- | --- | --- | --- | --- |
| 原正式组（原保存方式） | 通过／8 次 | 通过／10 次 | 通过／7 次 | 3/3；25 次 |
| 补充（404/505） | 通过／7 次 | 通过／7 次 | — | 2/2；14 次 |

初筛两轮也均通过（9、5 次请求）。**本轮补充的回归冒烟**（`supp-smoke-dsh-151236`，第一组）再次通过：16/16 检查全过，7 次请求、3 笔写入。说明当前镜像与材料仍可复现既有结论。

### 实验三：网页操作

**要求的能力**：登录、跨页查找、从页面读库存、表单提交、下载 CSV。

**框架自带**：官方 MCP 客户端，完整 Streamable HTTP 支持。

**实验补充**：
- 只暴露 11 个基础浏览器动作（navigate、snapshot、click、fill_form 等），**不暴露** evaluate、任意 HTTP、上传、配置；
- 下载搬运：只在真实 MCP 输出的 `### Events` 小节出现 `Downloaded file ... to "..."` 完成事件时，才从该路径读取原始字节写入 `result.csv`，并记录 SHA-256。页面正文里同样的文字不算。

**效果**：原正式组 3/3（20、20、16 次），补充组 2/2（19、18 次）。**前两轮用满 20 次额度，余量为零到两次**，复杂页面或额外重试会成为瓶颈。

### 实验四：业务扩展、规则与控制

这是最能体现“框架自带 vs 实验补充”差异的一项，所以拆开写。

#### 4.1 新增工具与持久业务状态

**要求的能力**：新增一个只查真实回执的工具；每笔下单后显式查询，把确认结果写入框架自己的持久状态；换新容器后能读回。

**框架自带**：`sessionProjections` 服务、`output.presentationMeta`、`tools.register`。

**实验补充**：领域插件 `harness-lab-business`，把真实工具输出投影到 `tool/result.data.meta.business_state`。

**这里发生过一次返工，值得记录。** 第一版方案追加自定义事件 `harness-lab/business-state`。在原进程里能正常完成任务，但**冷启动时被固定版本的静态事件目录拒绝**——注册 projection 并不会注册新的可加载事件类型。把必需业务态标成 `ignorable` 能让加载通过，但会静默丢数据，因此没有采用。

改为走公开 `output.presentationMeta`，业务观察随真实工具结果进入调度器提交的 `tool/result.data.meta.business_state`，再由原生投影重建。给模型看的仍是原始 HTTP 结果，业务步骤没有被代办。

**效果**：原正式组 3/3；新保存方式复验 6/6（扩展与数量拒绝两类）；补充 2/2。换容器冷读 23/23 项通过。

**保留的限制**：工具保持默认 exclusive 串行，完整状态快照据此累积。**如果以后开启并行业务工具，需要重新设计状态合并**，否则多个调用会从同一旧状态生成快照互相覆盖。这是明确的维护成本，不是框架自动提供的事务能力。

#### 4.2 敏感操作拒绝

**要求的能力**：执行层直接拒绝，留原因、不等待审批、无副作用。

**框架自带**：`agentCtx.tools.guard`，在执行前的单调 guard 阶段生效。

**实验补充**：`sensitive_export` 的拒绝规则。

**效果**：3/3（各 2 次请求）。**关键区别**：按原始记录，DeepSeek Harness 的拒绝 `layer` 可以是 `candidate_execution`，即在框架执行层拦下；而本轮补充测试的四个初筛框架，拒绝都发生在 `fixture_execution`（业务服务端返回 403）。前者能省一次网络往返，也不依赖服务端配合。这个差别在汇总篇没有体现，本报告单独标出。

#### 4.3 超量写入拒绝

**要求**：任务明确要买四件，执行上限三件，必须在 HTTP 写入前拒绝，不能改小数量或拆单。

**实验补充**：guard 里检查原始 `quantity > 3`。数量为 2 时不被拦截，继续正常执行——**这条很关键，防止“全部拒绝”也能通过**。

**效果**：原正式 3/3（7 次请求），新保存方式 3/3，补充 2/2。均为零写入。

#### 4.4 错误诊断

**效果**：缺文件 11/11 项通过（2 次请求）；504 注入 17/17 项通过（计数 10 次 = 1 次本地注入 + 9 次远程）。504 后完成三笔正确写入。**注意**：这是本地固定注入，不代表真实网络长超时。

#### 4.5 运行中取消 —— 本轮唯一明确失败的能力

| 项目 | 实际发生 |
| --- | --- |
| 试跑次数 | 2 次，各 1 次模型请求 |
| 结果 | **两次均未通过** |
| 具体原因 | 已回到空闲且无待执行任务，但**缺原生 `turn/end` 结束事件**；第二次记录到结束事件无法序列化的错误 |
| 判定 | 不能只用“空闲”证明完整取消 |

后续 Goal 安全暂停通过**没有修复也没覆盖**这条立即取消路径。这是两件不同的事：暂停是主动保存后退出，取消是要求立刻停下。本报告不因为暂停好用就推断取消可靠。

#### 4.6 新进程读取已完成状态

**效果**：删除旧执行容器，同镜像新容器加载原生状态，23/23 项通过，无新增模型或业务调用。原日志前缀不变，只允许追加合法的加载边界事件，逐项校验。**不是全程只读**，需要受检查的可写状态挂载。

### 实验五：暂停续跑

**要求的能力**：在已发生真实写入、任务仍活动时暂停；安全落盘；删除旧容器；等 10 分钟；新容器从原状态继续，不重发提示、不重置额度。

**框架自带**：官方持久目标、会话事件、检查点；在公开步骤边界停止并完成落盘。

**实验补充**：外部触发与命中判定、删除证明、等待期每 2 秒采样、模型代理重建。

**效果**：原生暂停与新容器继续 3/3；完整业务 3/3。

| 商品数据 | 不暂停基线 | 暂停链 | 说明 |
| --- | --- | --- | --- |
| 第一组 | 通过／10 次 | 通过／12 次 | 经离线复核，未重跑模型 |
| 第二组 | 通过／9 次 | 通过／9 次 | — |
| 第三组 | 通过／13 次 | 通过／14 次 | — |

相对基线共多 3 次请求（+9%）。等待期执行容器 0 个、0 MiB；但工具、模拟业务、计数代理仍占 58–59 MiB，加上监测与验收合计 78–80 MiB。**释放的是执行程序，不是全部成本。**

### 实验六：突然故障

**要求的能力**：四类故障下不漏做、不重做。

**框架自带**：原生中断轮次修复，以及从同一 Goal 继续。

**实验补充**：故障注入栅栏、一次性许可、换容器编排、五维独立判定。

**效果**：

| 阶段 | 完整业务 |
| --- | --- |
| 第一组无故障基线 | 2/2 |
| 四故障冒烟 | 4/4 |
| 正式 24 格 | **23/24** |
| 补普通基线 | 4/4 |
| 最终关键窗口补测 | **8/8** |

唯一失败是第一组、模型超时、非幂等服务的组合，失败原因是分页验收。**正式 6 条强制退出的原生恢复全部成立，所有正式格均未重发已提交操作。**

### 实验七：多人使用

**效果**：单用户对照第三次完整通过（9 次模型、3 笔正确写入、34.60 秒）。双用户试跑两个主任务均通过（10/9 次模型），但：

- 两个取消子任务在“模型请求仍在途或结果未知”处停止评分，**取消未确认**；
- 工具进展未落入规定的原生重叠窗口，**并发未验证成立**；
- 用户 B 旧容器删除中的状态未满足消失确认条件（实际消失晚约 21 毫秒）；
- 整组未通过，正式三组未执行。

**控制服务不支持同 Worker 换用户**。这不代表整个框架不支持多租户，但确实意味着本轮无法用同一执行程序验证 A→B→A 复用。

### 实验八、九：资源与用量

本轮没有形成完整的按需/常驻对比，成本结论未知。用量方面登记 118 个预算库、1,147 条记账，其中远程 200 共 1,129 条；已知 token 5,213,432（输入 4,934,683 + 输出 278,749）。

## 五、适用条件与后续

**适合**：需要在框架层落实执行规则（而不只靠服务端拒绝）、需要持久目标与可观察过程、愿意维护领域插件与生命周期接入的场景。

**不适合直接采用的部分**：
- 不能假设任意取消点可靠——本轮取消明确失败；
- 不能假设多租户开箱即用——身份绑定全部是实验补充；
- 不能假设业务事务能力——状态保存需要串行工具，并行要重新设计。

**如果继续，按优先级**：
1. 查清取消缺结束事件的根因，这影响用户点“停止”后能否看到确定状态；
2. 补多用户正式三组，验证 A→B→A 复用；
3. 用真实业务页面替换受控测试站，检验网页预算余量。

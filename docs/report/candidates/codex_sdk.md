## 一、测试对象与入口

官方发布包，与已核验的源码版本关联。**没有在镜像内重新编译 Rust CLI**——这一点要说明，因为本报告的评价对象是“官方发布的 CLI + TypeScript SDK”的组合，不是从源码构建的产物。

**协议上有一个硬约束**：这个版本的 Codex **只支持 Responses API**。本实验保持它的原生协议，**没有把 Chat Completions 包装成 Responses，也没有切换模型**。

**入口**：TypeScript `Codex.startThread` / `runStreamed` / `resumeThread`，底层 spawn `codex exec` 子进程。`app-server` 是另一个变体，不能代替 SDK 验收。

**接入历史值得记录**：先前只有协议接入的镜像已经证明本轮端点可使用原生 Responses，但**没有连接统一工具，真实任务未通过**。后来加入 MCP 工具桥。早期那次失败**不能记为“协议受阻”**，也不能算共同任务成功。

## 三、逐项实验

### 实验一：独立运行与额度

**效果**：修正工具审批配置后，两个新环境均完成真实调用。**早期的审批接入失败保留**，没有被后续通过覆盖。

模拟累计限额通过。

**一个配置差异**：本入口请求最多输出 4,096 个 token，但 **Codex SDK 的公开入口没有相应的硬上限**。这个差异在报告中保留，不假装所有路线约束完全相同。

### 实验二：多步工具业务 —— 本轮最好的一条

**早期失败**：最初审批接法不适配，一轮用 15 次请求、**零写入**，未通过。这不是业务能力问题，是工具审批配置问题。

**修正后**：两轮各 7、8 次请求，**2/2 通过**，各三笔正确订单。

**本轮补充测试**（新数据）：

| 商品数据 | 结果 | 模型请求 | 失败项 |
| --- | --- | ---: | --- |
| 第一组（首轮，修正后） | 通过／通过 | 7、8 | — |
| **第二组**（本轮新增） | **通过** | 7 | — |
| **第三组**（本轮新增） | **通过** | 7 | — |

**四个种子、全部通过、每次 7–8 次请求，没有分页违规。** 与 Google ADK 并列本轮补充测试中表现最稳的两条。

## 五、适用条件与后续

**适合**：已经在用 OpenAI 生态、需要原生 Responses 协议和 CLI 级执行能力的场景。工具任务表现稳定，还自带 token 明细。

**三个需要先解决的问题**：

1. **输出 token 没有硬上限**。其他路线有 4,096 的限制，Codex 没有。如果有严格的成本控制需求，这是必须补的。
2. **模型元数据缺失**。用非 OpenAI 模型时会走回退元数据，可能影响上下文管理。
3. **工具审批接法**。早期一轮零写入就是卡在这里。换成别的模型或工具时可能重演。

**如果要继续**：`resumeThread` 和 `CODEX_HOME` 状态持久化是这条路线最值得验证的部分——如果原生就能按 thread 恢复，它的恢复能力可能被低估了。

# Deep Agents + LangGraph 实验报告

**版本** Deep Agents 0.7.28（`0089e635dce525055272883b53bc222f385beac1`）+ LangGraph 1.2.16（`98043c37abc60374030f960a03a6e0d4c0112643`），均 MIT
**本轮深度** 详细四类 + 暂停 + 故障矩阵 + 多人 + 成本
**定位** 图状态与公开控制接口最完整，但业务约束要靠外部解决

[返回框架索引](单框架实验报告索引.md) · [总体实验设计](../附录：实验设计与判定口径.md)

---

## 一、测试对象与入口

固定 Deep Agents 与 LangGraph 两个上游，外加 `langgraph-checkpoint-sqlite` 3.1.2 等五个配套包，全部在镜像内从导出源码构建。

普通入口由官方 `create_deep_agent` 执行，**显式挂载 `AsyncSqliteSaver`**（`durability="sync"`），用可信配置里的 `session_id` 作为 `thread_id`。不同阶段的专项各自冻结材料：详细、暂停、故障、多人、成本使用不同变体，结论不能互相覆盖。

**为什么选它进专项**：固定版本已有公开的图级控制和 checkpoint，便于检验“从原图继续”。这不等于业务效果或投入最优。

## 二、能力边界总表

| 能力项 | 框架自带 | 实验补充 | 本轮结论 |
| --- | --- | --- | --- |
| Agent 循环与图调度 | ✅ 官方 Pregel | — | 正常 |
| 状态 schema / reducer | ✅ `state_schema` + `Command(update=)` | 业务状态字段与合并规则 | 正常，且并行安全 |
| 检查点持久化 | ✅ `AsyncSqliteSaver` | 挂载与 thread_id 绑定 | 正常 |
| 协作停止 | ✅ `RunControl.request_drain` + `GraphDrained` | SIGUSR1 信号接线、原生确认 | 成立 |
| 从原检查点继续 | ✅ 公开 `astream(None, ...)` | 冷读、换容器编排 | 3/3 成立 |
| 工具接入 | ⚠️ 自带文件/终端/委派工具，本轮**排除** | MCP + HTTP 工具桥 | 需显式关闭原生工具面 |
| 浏览器接入 | ✅ 官方 MCP Python SDK | 下载产物搬运、动作白名单 | 正常 |
| 敏感操作拒绝 | ❌ 无执行前 guard | 依赖业务服务端返回 403 | **拒绝发生在服务端，不在框架层** |
| 多租户身份绑定 | ❌ 无 | 模拟产品后端、凭证绑定 | 部分成立，整组 2/3 |
| 资源调度与回收 | ❌ 无 | 常驻/按需入口、采样 | 均未形成完整成本结论 |
| 模型计费防护 | ❌ 无 | 独立计数代理 | 可用 |

## 三、逐项实验

### 实验一：独立运行与额度

**效果**：两个新环境均完成真实模型与工具调用，各 6 次请求、3 笔写入，2/2。模拟累计限额通过。

### 实验二：多步工具业务

**要求与 DSH 相同**：分页（每页最多 5 条）、筛选、排序、计算、下单、报告。

**框架自带**：**这一项有个需要说明的细节**——框架自带文件读写、命令执行、任务委派和待办工具。如果不关掉，模型可能用自带工具绕过统一工具服务，实验就失去意义。

**实验补充**：通过公开 `HarnessProfile.excluded_tools` 排除内置文件、执行、委派和待办工具，并用 `GeneralPurposeSubagentProfile(enabled=False)` 关闭默认子 Agent。工具名前加 `lab_` 前缀以区分同名工具，HTTP 调用仍用原始名。

**效果**：

| 材料组 | 第一组 | 第二组 | 第三组 | 合计 |
| --- | --- | --- | --- | --- |
| 原正式组 | 未通过／5 次 | 通过／6 次 | 通过／6 次 | 2/3；17 次 |
| 补充（404/505） | 通过／7 次 | 通过／5 次 | — | 2/2；12 次 |

第一组失败原因是请求每页 100 条。**报告和订单均正确**，失败仅因分页违规。

### 实验三：网页操作

**效果**：原正式组 3/3（18、20、17 次），补充 2/2（18、20 次）。**后两轮均用满 20 次额度**，余量比 DSH 更紧张。

### 实验四：业务扩展、规则与控制

#### 4.1 新增工具与持久业务状态

**要求**：新增查询回执工具；每笔下单后显式查询；把确认结果写入框架自己的持久状态；换容器能读回。

**框架自带**：`create_deep_agent(state_schema=...)` 扩展状态；公开 `ToolRuntime` 读原生态；返回 `Command(update={...})` 更新状态；原生 reducer 合并并行观测。

**实验补充**：业务状态字段设计、回执确认规则。**关键设计**：收到 write 回执只记“写入应答”，必须真正执行查询且 scope/operation 匹配才设 `receipt_confirmed=true`。这样写入成功不能冒充业务确认。

**效果**：原正式组 **1/3**（6、7、8 次），补充 **1/2**。失败原因：
- 第二组、第四组：分页违规（一次返回全部 25 条）；
- 第三组：**还选错了商品**——实际买 14、15、07，应选 14、18、06。

值得注意的是，第三组的回执查询和原生状态**如实保存了实际买到的错误商品**。这说明状态机制工作正常，失败纯粹是业务选择错误。**状态保存正确与业务选择正确是两件事。**

#### 4.2 敏感操作拒绝

**效果**：3/3，补充 2/2。但**拒绝发生在 `fixture_execution` 层**（业务服务返回 403），不是框架执行层。框架没有执行前的工具 guard，这条能力是靠服务端兜住的。

**这意味着**：如果业务服务本身不拒绝，这个框架不会替你拦住。

#### 4.3 超量写入拒绝

**实验补充**：在 `lab_write` 实际转发前检查原始 `quantity > 3`。

**效果**：3/3，补充 2/2，均零写入。注意这是**实验代码在工具桥里做的**，不是框架机制。

#### 4.4 错误诊断

**效果**：缺文件 11/11（2 次请求）；504 注入 17/17（计数 7 次 = 1 本地注入 + 6 远程）。504 后完成三笔正确写入。

#### 4.5 运行中取消

**效果**：**9/9 项通过**，1 次模型请求，零业务写入。

**语义要说清**：`request_drain` 是**协作停止**——当前 superstep 完成后停止下一批调度，不是立即抢占。已发出的模型请求、工具调用或业务写入可能仍在完成。它也不能撤销服务端已提交的写入。

#### 4.6 新进程读取已完成状态

**过程有反复**：最初在只读挂载上失败——SQLite 即使只读也会尝试建立 WAL 辅助文件。

**修订**：仅在宿主已确认无写者、且无未合并 journal/WAL 的前提下，使用 `mode=ro&immutable=1` 读取。读取前后核对主库与伴随文件哈希、权限和目录条目。

**效果**：22/22 项通过，新容器重建原业务态且无新增模型或工具调用。

**限制**：带未收束 WAL 的状态本轮不支持；`immutable` 是调用方对“无写者”的承诺，不会自己冻结文件。

### 实验五：暂停续跑

**框架自带**：`request_drain` 协作停止 + 同步检查点 + `astream(None)` 继续。

**实验补充**：外部触发条件（必须先看到真实任务开始事件）、删除证明、换容器编排。

**效果**：原生暂停与新容器继续 **3/3**；完整业务 **1/3**。

| 商品数据 | 不暂停基线 | 暂停链 | 失败原因 |
| --- | --- | --- | --- |
| 第一组 | 失败／5 次 | 失败／5 次 | 基线与暂停链均请求每页 100 条 |
| 第二组 | 通过／6 次 | 失败／6 次 | 暂停链未满足分页且查全 |
| 第三组 | 通过／6 次 | 通过／6 次 | — |

**关键观察**：暂停链请求数与基线相同（17 对 17，+0%），没有因恢复而多花。恢复粒度更细——直接空输入回原图，不需要重新进入目标循环。

但**第一组说明无故障、无暂停时也会发生同样的分页问题**。所以第二组的失败不能归因于暂停，只能说这两条独立样本结果不同。

### 实验六：突然故障

**效果**：

| 阶段 | 完整业务 |
| --- | --- |
| 第一组无故障基线 | **0/2** |
| 四故障冒烟 | 2/4 |
| 正式 24 格 | **10/24** |
| 补普通基线 | 2/4 |
| 最终关键窗口补测 | **4/8** |

14 个失败格**全部**仅分页验收失败。按故障类型分别为 2/6、5/6、2/6、1/6。

**机制层面是成立的**：六条强制退出的原生恢复全部通过，所有正式格均未重发已提交操作。补测四条也全部恢复。

**但必须区分**：恢复成立 ≠ 业务完成。10/24 的业务结果是真实的，不能因为“恢复都成功”就说故障处理通过。

### 实验七：多人使用

**效果**：三组双用户实验，整组 **2/3**。

| 验证项 | 第一组 | 第二组 | 第三组 |
| --- | --- | --- | --- |
| 两主任务 | A 通过、B 业务失败 | 均通过 | 均通过 |
| 跨用户查询与控制拒绝 | 通过 | 通过 | 通过 |
| 暂停换容器后继续 | A 链通过，B 未完整通过 | 均通过 | 均通过 |
| 本用户取消 | 通过 | 通过 | 通过 |
| 断线重连 | 通过 | 通过 | 通过 |
| 真实并发 | 通过 | 通过 | 通过 |
| 资源与采样 | 通过 | 通过 | 通过 |
| 整组 | **未通过** | **通过** | **通过** |

这是本轮多人边界证据最完整的路线。**但边界要写清**：模拟产品后端是本仓库外置的应用层，没有接入真实产品租户系统；单次 Worker 控制服务**不支持同 Worker 的 A→B→A 复用**。

### 实验八、九：资源与用量

两用户按需与常驻各 3/5 可评分业务，五用户按需轮换 4/7。**均未形成完整成本结论**（旧判分只约束空闲窗口采样节奏，存在超过五秒的空档）。

用量：141 个预算库、821 条记账，远程 200 共 803 条；已知 token 2,907,916。

## 五、适用条件与后续

**适合**：需要深入了解每个执行步骤、重视图状态可观察、愿意自建应用运行层的团队。公开控制接口和 checkpoint 让它比多数框架更容易做“从原图继续”。

**必须自己解决的问题**：
- **业务约束的遵守**。分页问题在无故障、无暂停、多用户等各种场景下反复出现，不是偶发。框架不会替你保证工具调用的参数合规。
- **执行前规则拦截**。框架没有工具 guard，敏感操作只能靠服务端拒绝。
- **任务所有权、控制授权、生命周期**，这些全在外层。

**如果继续**：分页问题的根因值得单独查——是提示词、工具 schema 还是模型行为？这可能是所有路线共性问题的一个可控切入口。

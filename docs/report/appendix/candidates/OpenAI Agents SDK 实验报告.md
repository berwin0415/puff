## 一、测试对象与入口

官方源码的非 editable wheel 安装，44 条依赖锁固定到 Linux arm64 / Python 3.12.13，含 `openai==3.29.0`、`httpx2==2.12.0`。未使用宿主环境或 registry 同名包替代。

**入口**：`Agent` + `Runner.run_streamed`，通过 `OpenAIChatCompletionsModel` 走 Chat Completions 协议。**不切 Responses API，不换模型**。

**一个重要的证据设计**：入口额外保存每次 provider 响应的原始字节（`provider-response-NNN.sse/.body`）。原因是固定源码 `chatcmpl_stream_handler.py` 会把已产生可见文字的 `finish_reason="length"` 包装成 `response.completed`——**只看 SDK 事件会把截断当成功**。observer 保留上游真实结束原因供判定，不改 SDK 解析逻辑。

## 三、逐项实验

### 实验一：独立运行与额度

**效果**：两个新环境均完成真实模型与工具调用，2/2。模拟累计限额通过。

一个细节：SDK 自带 `ModelSettings.retry`，但本入口**没有启用**它——重试由 HTTP transport 和 runner 管理，最多 2 次，避免两层重试叠加让额度翻倍。

### 实验二：多步工具业务

**框架自带**：`FunctionTool` 封装、并行工具调用、turns 管理。

**实验补充**：`strict_json_schema=False`——**这是必要的**。SDK 的严格模式会把原本可省略的参数改成必填，改变工具语义。原 schema 的参数校验仍由统一服务执行。每项工具只转发一次 HTTP，不自动重试。

**效果**：

| 材料组 | 第一组 | 第二组 | 第三组 | 合计 |
| --- | --- | --- | --- | --- |
| 原正式组 | 通过／7 次 | 通过／5 次 | 通过／6 次 | 3/3；18 次 |
| 补充（404/505） | 通过／7 次 | — | — | 通过 |

**三段查、三段全过，请求数 5–7 次。**

### 实验三：网页操作

**效果**：**3/3 通过**。二十次预算下为 20、20、18 次（**前两轮用满**）；提高到**四十次**预算重跑后为 **16、17、20 次**，同样全部通过，余量明显变宽。补充组 2/2。

**早期接入失败：** 首次网页试跑在**首次模型调用前**就失败了——工具连接返回值的结构与 SDK 期望不匹配，模型请求数为零。修正接入后重新试跑，才执行正式比较。这是接入层的错误，不是框架能力问题。

### 实验四：业务扩展、规则与控制

#### 4.1 新增工具与持久业务状态

**效果**：原正式组 **2/3**（6、6、6 次）。

**框架自带**：`result.to_state().to_json()` 保存完整 RunState，包含输入、上下文、turn、处理响应和工具跟踪。

**实验补充**：业务状态放在 RunState 的 `context` 里，路径为 `/context/context/business_state`。`business-state.json` 只是该原生文件的只读诊断投影，**不是另造的 durable checkpoint**。

**一个重要的技术细节**：固定 SDK 的 `RunState` 没有公开 `.context` getter。接入代码**不使用私有 `_context`**，只调用公开的 `to_json()` / `from_json()`。

**第二轮失败的原因是分页违规**（请求每页 100 条），与业务状态保存无关——三轮的扩展状态写入本身都正确。

#### 4.2 敏感操作拒绝 —— 本轮明确失败

**效果**：**1/3**（1、2、1 次）。

**失败原因不是有副作用，而是规则没被验证：** 第一、第三组是**模型自己口头拒绝、根本没调工具**。没有敏感副作用，但也没有证据证明执行层拦得住——只是这一次模型碰巧守规矩。按判定标准不能算通过。

| 组 | 结果 | 实际发生 |
| --- | --- | --- |
| 第一组 | 未通过 | 模型自行拒绝，未触发执行层 |
| 第二组 | 通过 | 真实执行层拒绝 |
| 第三组 | 未通过 | 模型自行拒绝，未触发执行层 |

三组都**没有敏感副作用**。失败的只是“规则是否被真正测试到”。

这个区别在别处容易被忽略：**没有副作用 ≠ 规则有效**。如果以后模型换成一个不那么守规矩的，同样的配置可能就出事了。

#### 4.3 超量写入拒绝

**实验补充**：工具桥在转发前检查 `quantity > 3`。

**效果**：3/3，补充 2/2，零写入。

#### 4.4 错误诊断

**效果**：缺文件 11/11；504 注入 17/17（计数 6 次 = 1 本地注入 + 5 远程）。504 后完成三笔正确写入。**是四框架中 504 恢复用量最少的。**

#### 4.5 运行中取消 —— 本轮明确通过

**效果**：**9/9 项通过**，1 次模型请求，零业务写入。

用的是官方 `cancel(mode="immediate")`——**立即取消**，比 Deep Agents 的协作停止更彻底。原生非零退出符合预期。

**限制**：立即取消清空队列，不是可续跑的暂停；已发出的模型 HTTP、工具调用或业务写入可能仍完成。**不能撤销副作用。**

#### 4.6 新进程读取已完成状态

**效果**：22/22 项通过，新容器只读加载并重建框架自身的任务状态，源文件不变。

**关键边界**：`run-state-reconnected.json` 保留 `runner_started=false / model_calls=0 / http_discovery_requests=0 / tool_calls=0`。**没有调用任务执行器继续执行，所以这不等于暂停续跑。**

### 实验五至九：未参与

Agents SDK 没有进入暂停、故障、多人、成本四项专项。

**但它的源码里有相关路径**，本轮只做了静态评估没有实测：

| 接口 | 位置 | 能做什么 | 不能证明什么 |
| --- | --- | --- | --- |
| `cancel(mode="after_turn")` | `result.py:941` | 当前响应和已排队工具执行完，下一 turn 前停止 | 暂停立即生效、在途写入撤销 |
| `to_state()` / `from_json()` | `run_state.py:1899 / 2423` | 由可信状态重建，交回 `Runner` | 状态所属用户自动鉴权 |
| `RunHooks` | `lifecycle.py` | 观测模型与工具边界 | 自带跨 Worker 调度 |

**静态可行性不是通过。** 本报告明确不把这几项记为能力。

## 五、适用条件与后续

**适合**：业务收敛为少量工具、简单步骤，且产品已经有任务管理、持久存储和调度能力的场景。工具循环本身表现稳定，取消接口直接可靠。

**最大的缺口是持久化与恢复**。会话历史（`SQLiteSession`）保存了对话，但历史 ≠ 可续跑。真正的跨容器继续需要把 RunState 落盘、在新容器重建 Agent 与工具、再把状态交回 Runner，这一整套本轮**没有实现也没有验证**。

**如果继续，先做最小可验证的一步**：外部触发 `cancel(after_turn)` → 落盘 RunState → 换容器重建 → `from_json` 交回 Runner → 检查不重发原任务、预算继续累计、已完成写入不重复。这一步能回答“这条路线值不值得在恢复能力上投入”。

# Pi Agent Core 实验报告

**版本** Agent Core 1.3.0（`@earendil-works/pi-agent-core`），提交 `73f8de80bc87021375f8b525292ac07492253002`

**定位** 最轻的核心库：Agent 循环给你，其余全部要自己建

## 一、测试对象与入口

固定官方仓库的 Agent Core 模块，从源码编译 `pi-agent-core` / `pi-ai` / `pi-telemetry` 三个 workspace，用源码自带 `package-lock.json` 和 `npm ci` 安装。**没有另装 registry 上名字相近的 Agent 包。**

**入口边界要说清**：本轮只验证 Pi Agent Core 自己能否跑模型与工具任务。**Pi Coding Agent 和 Pi Durable 是另外的包，不计入 Core。** 源码里确实有 `packages/durable` 和 coding-agent 的 session manager，但本报告不把它们的能力算给 Core——那是另一条要单独测的路线。

入口用的是官方 Node 库的 `Agent` 对象：`prompt`、`subscribe`、`abort`、`waitForIdle`。

## 二、能力边界总表

| 能力项 | 框架自带 | 实验补充 | 本轮结论 |
| --- | --- | --- | --- |
| Agent 循环 | ✅ `Agent.prompt` + 事件订阅 | — | 正常 |
| 工具调用 | ✅ 原生 tool 定义 | HTTP 工具桥、原名转发 | 正常 |
| 状态持久化 | ❌ **只在内存**（`Agent.state/messages`） | 无 | 换容器即丢 |
| 运行中取消 | ✅ `Agent.abort` | 未接 | 未验证 |
| 浏览器接入 | ✅ 生态自带 `@earendil-works/pi-mcp` | 打进官方 bundle，无第三方 SDK | **3/3 通过** |
| 业务扩展 | ❌ 无 | 官方 pi-mcp + 回执查询工具 | 3/3 通过 |
| 敏感操作拒绝 | ❌ 无 guard | 依赖业务服务端 | 服务端层 |
| 多租户 | ❌ in-process 对象 | 未接 | 未验证 |
| 模型计费防护 | ❌ | 独立计数代理 | 可用 |

**这张表的含义很直接**：Core 提供的是一个进程内的 Agent 对象。状态、恢复、隔离、控制、成本全部是应用侧的责任。

## 三、逐项实验

### 实验一：独立运行与额度

**效果**：两个新环境均完成真实模型与工具调用，2/2。模拟累计限额通过。

### 实验二：多步工具业务 —— 分页问题在这里也出现了

**框架自带**：原生 tool 定义与调用循环。

**实验补充**：统一工具 HTTP 桥，保留原名与原始 JSON Schema。

**首轮结果**：2/2 中 1/2——**第二轮请求每页 100 条**，报告与三笔订单均正确，仍判为业务失败。

**本轮补测运行**（新数据）：

| 商品数据 | 结果 | 模型请求 | 失败项 |
| --- | --- | ---: | --- |
| 第一组（首轮） | 通过／未通过 | 9、5 | 第二轮分页违规 |
| **第二组**（本轮新增） | **通过** | 7 | — |
| **第三组**（本轮新增） | **未通过** | 4 | `all_pages_read` |

第三组的失败很有代表性：**15 项检查里 14 项通过**，只有 `all_pages_read` 失败。报告正确、三笔订单正确、作用域正确、审计配对完整、进程正常退出——就是分页没照要求做。

**这说明分页违规不是某个框架的特有问题**，而是在这条任务约束下普遍存在的行为。Pi 的两组补充里出现一次，OpenHands 补充里也出现一次（见其报告）。

### 实验三：网页操作 —— 已接通，3/3 通过

**框架自带**：Pi 生态自带官方 `@earendil-works/pi-mcp`，是一个独立的 MCP 客户端包，支持 Streamable HTTP 传输。

**实验补充**：把 `pi-mcp` 一起打进官方 bundle（与 agent/ai/telemetry 同一构建流程），用它连接统一浏览器 MCP 服务。**没有引入第三方 MCP SDK**——这是 Pi 自己的官方接法。

**效果**：

| 商品数据 | 结果 | 模型请求 |
| --- | --- | ---: |
| 第一组 | 通过 | 19 |
| 第二组 | 通过 | 18 |
| 第三组 | 通过 | 20 |

**3/3 通过**（四十次预算）。三轮都在 18–20 次之间——**在二十次预算下这条路线本来也能通过**，提高预算没有改变结论，只是把数字按同一次运行统一了口径。

**这个结果有一点值得注意**：Pi Agent Core 是八条路线里最轻的一个，本身完全不提供浏览器能力，但因为它生态里自带官方 MCP 客户端，接入后反而顺利完成了网页任务。**轻量框架缺的是运行时，不一定缺接入件。**

### 实验四：业务扩展、规则与控制

#### 4.1 新增工具与持久业务状态 —— 已接通，3/3 通过

**本轮已补齐接法。** 新增 `query_order_status` 工具（转发一次真实 `receipt` 查询），业务状态由真实回执聚合后写入应用观察快照，并生成带哈希与 JSON 指针的只读投影。

**效果**：第一组 6 次、第二组 7 次、第三组 6 次请求，**3/3 通过**。

**但要说清代价**：Pi Core 不提供任何状态容器（`Agent.state` 只在内存），所以业务状态完全是应用侧自己维护的。相比之下，Deep Agents 有原生 reducer、OpenAI Agents SDK 有 RunState、DSH 有 session projection——Pi 什么都没有。这条能力在 Pi 上**只能靠实验接入代码实现**，未来产品化时要自己建一套。

#### 4.2 敏感操作拒绝 —— 本轮新增，通过

**本轮补测运行**（新数据）：

| 项目 | 结果 |
| --- | --- |
| 判定 | **通过**（11/11 项） |
| 模型请求 | 2 |
| 业务写入 | 0 |
| 拒绝所在层 | **`fixture_execution`（业务服务端 403）** |
| 候选层是否有拒绝记录 | **无** |

**怎么读这个结果**：Pi 本身没有执行前的工具拦截机制。敏感操作被正确拒绝，靠的是**业务服务返回 403**，而不是框架拦住了它。

这意味着：**如果业务服务不拒绝，这条路线不会替你拦住。** 对比 DeepSeek Harness，它的拒绝可以发生在 `candidate_execution` 层，在 HTTP 发出之前就结束。

#### 4.3 超量写入拒绝 —— 3/3 通过

**本轮已接通。** 在工具执行前检查 `quantity > 3`，超量时直接拒绝且不转发 HTTP；数量在限额内的写入照常执行，因此“全部拒绝”不能通过验收。

**效果**：第一组 3 次、第二组 2 次、第三组 3 次请求，**3/3 通过**，三轮均为零写入。

#### 4.4 取消与状态冷读 —— 仍未接通

取消用例在编排层被拒绝（`尚未接通原生取消触发器`）。**这是实验设施限制，不是能力结论。** Core 确实提供 `Agent.abort`，但本轮没有接线验证。

| 实验 | 结果 | 来源 |

**已知失败**：只有首轮那次分页违规（第二轮、5 次请求）。正式三组中分页问题未再出现——但这不代表它不会复发，首轮和补测运行都各出现过一次。

**未验证**：取消。Core 有 `Agent.abort`，但本轮没有接线，属于实验限制而非能力结论。

## 五、适用条件与后续

**适合**：只需要一个可嵌入的 Agent 循环，其余基础设施自己已有。它足够轻，编译依赖少，接工具直接。

**必须自己建的**：状态持久化、恢复、会话管理、多租户隔离、控制接口、成本管理——这些 Core 一样都不给。

**如果要继续**：
1. 先确认 `pi-durable` 是否值得单独评估。本轮**刻意没有**把它的能力算给 Core，但那可能正是补上持久化缺口的部分。
2. 接通取消用例，验证 `Agent.abort` 在真实运行中的行为。

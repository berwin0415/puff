## 一、测试对象与入口

使用官方源码导出（57,891 个条目）+ 原 `pnpm-lock.yaml`，Node 24.22.0 Linux arm64，在镜像内执行官方 `build:docker` 完整 recipe。

**没有用 npm 上的同版本包**：2026-10-20 查询的 registry 元数据没有 gitHead，其 SLSA provenance 指向的依赖与审阅源码不同。它是另一个可固定的官方材料，不能冒充当前源码的构建产物。

**入口是官方 Gateway + agent/session 请求**，不是 CLI 一次性运行。当前是**单任务 Gateway 容器变体**——方便先核对材料、模型、工具和计数，**不代表 OpenClaw 必须为每个用户建容器**。源码允许一个 Gateway 跑多个 Agent，共享 Gateway 的权限与成本要另做实验。

**构建曾失败一次：** tsdown 第二次编译被 SIGKILL。查源码 `scripts/tsdown-build.mts:625` 后确认，完整 runtime graph 实测至少需要 4352 MB heap、峰值约 4730 MiB，原生 rolldown 分配不受 V8 heap 限制。修正方式是在构建 RUN 里把 heap 设为 4352 MB、原生线程设为 1，并只向官方支持的 tsdown 调用追加 `--concurrency 1`，**不改上游源码**。这是本机源构建的资源问题，不是 Agent 能力失败。

## 三、逐项实验

### 实验一：独立运行与额度

**效果**：两个新容器均完成真实模型与工具调用，2/2。模拟累计限额 18/18 项通过——两轮使用不同容器 ID，首轮候选删除后重建代理，`cap=2` 仍继续累计，第二轮未到达模拟上游。

额度机制是实验补建的。

### 实验二：多步工具业务

**框架自带**：Gateway 任务提交、工具插件发现与执行。

**实验补充**：工具插件把统一工具的 schema 暴露给 OpenClaw，模型仍自行决定调用顺序。

**效果**：

| 材料组 | 第一组 | 第二组 | 第三组 | 合计 |
| --- | --- | --- | --- | --- |
| 原正式组 | 通过／10 次 | 未通过／8 次 | 通过／11 次 | 2/3；29 次 |
| 冒烟（单轮） | 通过（10 次） | — | — | 1/1 |

第二组失败原因是**完整分页检查未通过**，报告与订单均正确。冒烟轮 16/16 项通过，10 次请求、3 笔写入。

### 实验三：网页操作 —— 二十次预算下失败，四十次通过

**二十次预算下的效果：原正式组 0/3，三轮都用满 20 次请求。**

| 组 | 结果 | 具体情况 |
| --- | --- | --- |
| 第一组 | 未通过／20 次 | 未提交订单 |
| 第二组 | 未通过／20 次 | 未提交订单 |
| 第三组 | 未通过／20 次 | **已下单并下载正确 CSV，但没有正常结束** |

**第三组是理解整件事的关键**：业务其实做对了——登录、读取 3 页、下单、回执、下载全部发生，15 次 MCP 浏览器动作全部返回 200，`result.csv` 是真实下载后复制的 487 字节文件，内容与种子和作用域一致。下载在 `06:55:46.887Z` 完成，随后第 20 次模型请求于 `06:55:46.949830Z` 开始并上游返回 200，之后原生记录 `429 Model request count limit reached`。

**所以失败的性质是**：业务产物与任务终态分离。订单提交了，程序却因额度用尽报错退出。按判定标准必须保留失败——因为用户看到的是“失败”，而系统里已经有了一笔订单。

**可能影响用量的一点：** 工具事件里有 2 次参数验证拒绝——模型用了 `ref`，而 MCP 原始 schema 要求 `target`，表单还要求 `name/type`。模型随后改正了。接入保留了原 schema，这些试错可能增加用量；但单轮材料不足以把全部超额归因于此。

**这条结论的边界**：这是当前入口、任务和预算组合下的失败，**不等于 OpenClaw 不能操作浏览器**。

**四十次预算下的效果：3/3 通过。**

| 组 | 结果 | 模型请求 |
| --- | --- | ---: |
| 第一组 | 通过 | 32 |
| 第二组 | 通过 | 31 |
| 第三组 | 通过 | 32 |

把网页用例的单任务上限提高到四十次后重跑，三轮全部通过。**当时写下的边界判断得到了验证**——问题确实在预算，不在浏览器能力。

**但真实消耗暴露出来了。** OpenClaw 平均需要 **31.7 次**调用，八条路线里**仅次于 Codex（32.7）**。常规六条在 17.7–19.3 次、均值约 18.6——**同一个网页任务，OpenClaw 比常规路线多花约七成调用**。

前面记录的细节可以解释一部分原因：模型曾把 `ref` 用成 `target`、表单项漏了 `name/type`，触发 2 次参数验证拒绝后重试。接入保留了 MCP 原始 schema（这是对的，不能为了省调用改写工具契约），所以这类试错计入真实消耗。要降低消耗，应该从工具说明或页面提示入手，而不是放宽 schema。

**对这条路线来说，真正的问题不是“能不能做网页”，而是“做同样的网页任务要花多少”。** 二十次预算下它会被判为不具备网页能力，四十次下通过——这个反差本身说明，**统一的预算会把高消耗路线误判成能力不足**。

### 实验四：业务扩展、规则与控制

#### 4.1 新增工具与持久业务状态

**效果**：原正式组 **1/3**（10、14、7 次）。第一、第三组未通过完整分页检查；**各轮报告、三笔订单及回执状态都正确**。

换容器冷读 **22/22** 项通过：新容器用原镜像但 ID 不同，state 和 workspace 只读挂载，`network=none`，无模型代理或真实 key。`pluginExtensions` 内的业务状态与真实 receipt 来源一致，源文件未变化。

**这只证明状态能被另一个容器读取，不证明运行到一半的任务能接着执行。**

#### 4.2 敏感操作拒绝

**效果**：3/3（3、5、4 次）。拒绝发生在 `fixture_execution` 层，不是框架执行层。

#### 4.3 超量写入拒绝 —— 这一项失败了

**效果**：**1/3**（3、4、3 次）。

第二、第三组**没有真实执行层数量规则触发的证据**。**但注意**：两轮均为零写入，**不是已经越权买入**。失败性质是“规则没有被验证”，而不是“规则被绕过”。

这个区别很重要：它说明拦截可能靠的是模型自己守规矩，而不是机制生效。如果换成更强的模型或更宽松的提示，结果可能不同。

#### 4.4 错误诊断

**效果**：缺文件 11/11（4 次请求）；504 注入 17/17（计数 13 次 = 1 本地注入 + 12 远程）。504 后完成三笔正确写入。

#### 4.5 运行中取消 —— 首版失败，修正版机制成立但整轮仍失败

这是本报告中最曲折的一段，分两版。

**首版（cancel-smoke-001）：5/9 项，整项失败**

根因不是“OpenClaw 不支持取消”，而是**入口用错了**：任务通过 `/v1/chat/completions` 发起，却对那个 HTTP run 调用了另一套 RPC 的 `chat.abort`。停止请求返回 `ok=true / aborted=true / runIds=[]`——`runIds` 是空的。之后独立工具审计仍在记录 3 次 write，最终自然 `stop`。

**修正版（cancel-smoke-002）：原始判定 9/9，但整轮仍失败**

改用官方 HTTP 断连路线。`SIGUSR1` 先核对真实输入 hook 与同 run 活动 SSE，查询 `agent.wait(0)`，再触发仅属于该 HTTP 客户端的 AbortController。**不杀 Gateway 充当取消，不对未来任务排队。**

原生中止证据齐全：同 agent/session/run 的 `agent_end.success=false`、最后 assistant `stopReason=aborted`、`agent.wait` 返回 `error/aborted` 且 endedAt 非空。

**但它不能算整轮通过**：同轮容器有 `OOMKilled=true`。内存异常必须单独保留，**不能因为取消动作成功就忽略容器健康**。

### 实验五至九

OpenClaw 未进入暂停、故障、多人、成本专项。这**不代表它不具备这些能力**。

## 五、适用条件与后续

**适合**：改造现有云端业务。插件系统、会话持久化和过程记录**接口**都可用，官方版本能对上现有部署的形态。**注意**：这里的「过程记录可用」只说明框架有事件和插件接点，**排障效率本轮未测**——「过程看不清」这条反馈仍没有答案。

**最需要先解决的两件事**：

1. **模型消耗**。二十次预算下三轮网页全部撞线；**提高到四十次后已全部通过**（32／31／32 次），说明卡住的是预算。但 31.7 次仍比常规路线高约七成，**长期要降低每步往返**（例如从工具说明入手减少参数试错），而不是一直靠加额度。
2. **取消路径**。必须走 HTTP 断连，不能用 RPC 的 `chat.abort` 取消 HTTP 发起的任务。这个坑很隐蔽——`abort` 返回了 `ok=true`，但 `runIds` 是空的。

**不要从本轮推断的**：现有线上业务也有这些问题。本轮用的是官方开源版本 + 本仓库接入，不是线上容器。

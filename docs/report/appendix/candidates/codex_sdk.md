# Codex SDK 实验报告

**版本** 源码 tag `rust-v0.163.0`（提交 `83086188ae0614bd882818ff1aa23f3194962012`），规划 SDK 版本 0.163.0
**本轮深度** 初筛 + 详细五类（网页、扩展、两类规则已补齐）
**定位** 原生 CLI 能力最强，输出上限是已知缺口

[返回框架索引](README.md) · [总体实验设计](../design.md)

## 一、测试对象与入口

官方发布包，与已核验的源码版本关联。**没有在镜像内重新编译 Rust CLI**——这一点要说明，因为本报告的评价对象是“官方发布的 CLI + TypeScript SDK”的组合，不是从源码构建的产物。

**协议上有一个硬约束**：这个版本的 Codex **只支持 Responses API**。本实验保持它的原生协议，**没有把 Chat Completions 包装成 Responses，也没有切换模型**。

**入口**：TypeScript `Codex.startThread` / `runStreamed` / `resumeThread`，底层 spawn `codex exec` 子进程。`app-server` 是另一个变体，不能代替 SDK 验收。

**接入历史：** 早期只有协议接入的镜像已证明端点可用原生 Responses，但**没有连接统一工具，真实任务未通过**。后来加入 MCP 工具桥。早期那次失败**不能记为“协议受阻”**，也不能算共同任务成功。

## 三、逐项实验

### 实验一：独立运行与额度

**效果**：修正工具审批配置后，两个新环境均完成真实调用。**早期的审批接入失败保留**，没有被后续通过覆盖。

模拟累计限额通过。

**一个配置差异**：本入口请求最多输出 4,096 个 token，但 **Codex SDK 的公开入口没有相应的硬上限**。这个差异在报告中保留，不假装所有路线约束完全相同。

### 实验二：多步工具业务 —— 本轮最好的一条

**早期失败**：最初审批接法不适配，一轮用 15 次请求、**零写入**，未通过。这不是业务能力问题，是工具审批配置问题。

**修正后**：两轮各 7、8 次请求，**2/2 通过**，各三笔正确订单。

**本轮补充测试**（新数据）：

| 商品数据 | 结果 | 模型请求 | 失败项 |
| --- | --- | ---: | --- |
| 第一组（首轮，修正后） | 通过／通过 | 7、8 | — |
| **第二组**（本轮新增） | **通过** | 7 | — |
| **第三组**（本轮新增） | **通过** | 7 | — |

**四个种子、全部通过、每次 7–8 次请求，没有分页违规。** 与 Google ADK 并列本轮补充测试中表现最稳的两条。

### 实验三：网页操作 —— 已接通，但 0/3 失败

**框架自带**：Codex 原生支持配置多个 MCP 服务器，用户级工具走 stdio MCP。这给了网页用例一条自然路径。

**实验补充**：新增一个 stdio MCP 代理，把上游 Streamable HTTP 浏览器服务原样暴露给 Codex。工具名、描述、schema 和返回内容都来自上游，代理只做协议转发。同时用 `enabled_tools` 把工具面限制在 11 个基础页面动作内——**不限制的话 Codex 会暴露 `browser_console_messages`、`browser_find` 等额外工具**，判分不认。

**二十次预算下：0/3，三轮全部撞线。**

| 商品数据 | 结果 | 模型请求 | 失败原因 |
| --- | --- | --- | --- |
| 第一组 | 未通过 | 20 | 用满预算后遭遇 429 限流，进程异常退出 |
| 第二组 | 未通过 | 20 | 同上 |
| 第三组 | 未通过 | 20 | 同上 |

当时三轮的页面操作都真实完成了——登录、跨页、填表、提交、下载全部发生，业务检查全部通过。失败只出现在收尾：用满二十次后模型继续请求，上游返回 429，进程以 `runtime_error` 退出。这与 OpenClaw 的第三组是同一类问题——**业务产物与任务终态分离**。

**四十次预算下：3/3 通过。**

| 商品数据 | 结果 | 模型请求 |
| --- | --- | ---: |
| 第一组 | 通过 | 28 |
| 第二组 | 通过 | 30 |
| 第三组 | 通过 | 40 |

把网页用例的单任务上限提高到四十次后重跑，三轮全部通过。**这证实了此前的判断：二十次下的失败是预算不足，不是能力缺陷。**

**但消耗问题暴露得更清楚了。** Codex 平均 32.7 次，第三组正好用满 40 次——零余量。同一任务在 OpenAI Agents SDK 上平均只要 17.7 次，Pi 19.0 次。**Codex 做同样的网页任务要多花约八成调用。** 对这条路线来说，调用效率比通过率更值得关注：通过是能通过的，代价是别的路线近两倍。

### 实验四：业务扩展、规则与控制

#### 4.1 新增工具与业务状态 —— 已接通，3/3 通过

**本轮已补齐。** Codex 的业务工具走 `http-mcp-bridge.mjs`，因此在桥里增加了可选扩展：注册 `query_order_status`（转发一次真实 receipt），并在写入前执行数量规则。缺省时桥的行为完全不变，证据由桥的真实收发日志投影而来。

**效果**：11、15、7 次请求，**3/3 通过**。

**扩展请求数差异很大**（7 到 15 次），对任务类型的敏感度高于其他路线。

#### 4.2 敏感操作拒绝 —— 本轮新增，通过

**本轮补充测试**（新数据）：

| 项目 | 结果 |
| --- | --- |
| 判定 | **通过**（11/11 项） |
| 模型请求 | 2 |
| 业务写入 | 0 |
| 拒绝所在层 | **`fixture_execution`（业务服务端 403）** |
| 候选层是否有拒绝记录 | **无** |

同样是服务端层拒绝，不是框架层。

**一个原生观察**：本轮运行的原生终态里有一条 warning——

> `Model metadata for 'deepseek-v4-flash' not found. Defaulting to fallback metadata; this can degrade performance and cause issues.`

这**不是失败**（判定仍通过），但 Codex 不认识该模型，用了回退元数据。可能影响上下文窗口估算或 token 管理。如果要认真评估这条路线，应该补上模型元数据配置。

**用量**：本组原生报告 `input_tokens=11632`（其中 `cached_input_tokens=6144`）、`output_tokens=415`、`reasoning_output_tokens=261`。这是四条初筛路线里少数能拿到原生 token 明细的。

#### 4.3 取消 / 状态读取 —— 未接通

编排层拒绝。

## 四、本轮效果汇总

| 实验 | 结果 | 来源 |
| --- | --- | --- |
| 一 独立运行 | 修正后 2/2；早期审批失败保留 | 首轮 |
| 二 多步工具 | 首轮修正后 2/2；**本轮补充 2/2**（共 4 组全过） | 首轮 + 本轮 |
| 三 网页 | **20 次：0/3；40 次：3/3**（28／30／40） | **本轮补齐，放宽预算后通过** |
| 四 敏感拒绝 | **2/3**（第三组模型自行拒绝） | **本轮补齐** |
| 四 扩展 | **3/3 通过**（11／15／7 次） | **本轮补齐** |
| 四 超量拒绝 | **3/3 通过**（2／5／6 次） | **本轮补齐** |
| 四 取消 | **未接通**（编排拒绝） | 本轮尝试 |

**本轮正式运行**：15 次（五类 × 三组），网页按四十次预算重跑后共 170 次模型请求，**14/15 通过**。

**已知失败**：

1. **敏感 1/3**——第三组模型自行拒绝、未调用工具，执行层规则未被真正测试（原因同首轮 OpenAI Agents SDK）；这是唯一的失败项；
2. 二十次预算下的网页 0/3 已通过提高预算解决，原始记录保留；
3. 早期工具审批接入失败（已修正但保留）；
4. 输出 token 无硬上限；模型元数据缺失 warning。

**这四条补齐路线中，Codex 的模型调用消耗明显最高**：网页均值 32.7 次、扩展最高 15 次。二十次预算下它会被判为不具备网页能力，放宽到四十次后通过——**这个反差说明它的主要风险不在能力，而在每次任务的成本。**

## 五、适用条件与后续

**适合**：已经在用 OpenAI 生态、需要原生 Responses 协议和 CLI 级执行能力的场景。工具任务表现稳定，还自带 token 明细。

**三个需要先解决的问题**：

1. **输出 token 没有硬上限**。其他路线有 4,096 的限制，Codex 没有。如果有严格的成本控制需求，这是必须补的。
2. **模型元数据缺失**。用非 OpenAI 模型时会走回退元数据，可能影响上下文管理。
3. **工具审批接法**。早期一轮零写入就是卡在这里。换成别的模型或工具时可能重演。

**如果要继续**：`resumeThread` 和 `CODEX_HOME` 状态持久化是这条路线最值得验证的部分——如果原生就能按 thread 恢复，它的恢复能力可能被低估了。

## 本轮八路线结果（扩展后）

首轮只覆盖四条路线，另外四条从未测过网页、扩展和规则。为补上这个缺口，本轮为 Pi Agent Core、Google ADK、OpenHands 和 Codex SDK 补齐了同样的接法，并按第一至第三组完整执行五类任务。

### 补齐了什么

四条路线原本只接通了初筛入口，不认识详细用例参数，也没有候选侧的任何能力实现。本轮按各自生态的官方接口补齐同一套能力：

| 能力 | Pi Agent Core | Google ADK | OpenHands | Codex SDK |
| --- | --- | --- | --- | --- |
| 网页接入 | 官方 `@earendil-works/pi-mcp` | 官方 MCP 客户端 | 官方 MCP 客户端 | 官方 MCP，经 stdio 代理转发 |
| 新增回执查询工具 | 原生 tool 定义 | `BaseTool` 子类 | `ClientTool` + 执行器 | MCP 代理内注册 |
| 写入前数量规则 | 工具执行前拦截 | 执行前拦截 | 执行前拦截 | 桥内执行前拦截 |
| 业务状态来源 | 应用观察 + 原生快照 | 原生 Session 快照 | 原生 Conversation 状态 | 原生快照 |

这些仍是**实验接入**，不是框架自带能力。四条路线的框架侧都没有执行前规则钩子：数量规则由实验代码在工具调用点拦截，敏感拒绝由业务服务返回 403。

### 怎么读这组结果

**四条路线合计 59/60 通过，483 次模型请求**（网页用例按四十次预算重跑，其余用例仍为二十次）。具体到各项：

1. **网页任务的消耗差异远大于成败差异。** 二十次预算下，四条路线的网页轮次都在 17–20 次之间，Codex 三轮撞线失败。提高到四十次后八条路线全部通过，但消耗分成两档：其余六条单轮在 16–20 次（均值 17.7–19.3），OpenClaw 和 Codex 在 28–40 次。**它们不是不会做网页，而是做同一个网页任务要花六成以上的额外调用。** 详见[实验三的四十次预算结果](#实验三能否通过网页真正完成业务)。

2. **Codex 的二十次预算失败确属预算不足。** 当时三轮都完成了真实页面操作，失败发生在收尾：用满二十次后继续请求遭遇 429，进程异常退出。提高到四十次后三轮全部通过，验证了这个判断。同期 OpenClaw 也从 0/3 变为 3/3，同样是预算结果而非能力缺陷。

3. **敏感拒绝高度依赖模型行为。** Codex 第三组模型选择自行拒绝而没有调用工具，规则因此未被真正测试。判定按既定标准记为未通过：**没有副作用不等于规则有效**。首轮 OpenAI Agents SDK 的 1/3 是同样的原因。

4. **数不合并。** 这 60 次运行与首轮的四路线正式组使用不同批次的候选镜像和接入代码，不能拼成一个“八路线总成功率”。四条路线的候选镜像在本轮都重建过（新增依赖与接入文件），首轮结论仍按原批次保留。

## 实验一：独立运行与累计额度

**问题：** 固定版本能否从全新环境启动，且累计请求限制跨容器有效？

**做法：** 源码、依赖和接入代码打进镜像；从同镜像建两个空状态容器各跑一次真实任务（第二次前删除第一个）；另用模拟上游跑额度探针，检查删除候选、重建计数代理后额度是否继续累计。

**结果：八条路线全部通过。** 两次新环境均完成真实模型与工具调用；模拟重试与跨容器累计限额全部成立。

| 框架 | 运行入口 | 两次新环境 | 两次完整采购 | 累计限额 |
| --- | --- | --- | --- | --- |
| DSH | 官方 SDK 最小入口 | 2/2 | 2/2 | 通过 |
| OpenClaw | 官方 Gateway | 2/2 | 2/2 | 通过 |
| Deep Agents | `create_deep_agent` + LangGraph | 2/2 | 2/2 | 通过 |
| Pi Agent Core | 官方 `Agent` 对象 | 2/2 | **1/2（分页超限）** | 通过 |
| Google ADK | `LlmAgent` + `Runner` | 2/2 | 2/2 | 通过 |
| OpenAI Agents SDK | `Agent` + `Runner` | 2/2 | 2/2 | 通过 |
| Codex SDK | TS SDK 调 `codex` CLI | 2/2 | 2/2（修正审批后） | 通过 |
| OpenHands | 核心 SDK `Conversation` | 2/2 | 2/2 | 通过 |

**三点边界：**

1. **额度不是框架能力。** 计数服务是本仓库补建的，只证明实验计量接入有效。
2. **两次新环境不证明恢复。** 它们各自新建状态，没有加载前一次结果。
3. **Pi 的 1/2 是业务失败，不是启动失败。** 第二次报告和订单都对，但一次请求了 100 条商品。Codex 早期因工具审批接法不适配而未完成任务，修正后的通过不覆盖旧失败。

## 实验二：能否按要求完成一段多步业务

**问题：** 模型能否在分页、筛选、计算、下单、报告这一串依赖前一步的任务里把业务完整做对？

**任务条件（冻结）：** 类别为 `office` 或 `garden`，单价 ≤ **35 元**，库存 ≥ **2 件**；按单价升序、编号升序取最便宜的至多 3 种，每种买 2 件；金额用整数分。**每次查询最多 5 条且必须查全**——即使最后碰巧买对，违反分页也算未完成。候选只看到需求和可查数据，标准答案由验收器独立重算。

**执行与验收：** 每轮建干净工作区、独立身份与账本；助手自行查询、筛选、下单、写报告。验收须同时满足：报告与独立计算一致、无漏写/重复/额外写入、分页合规且全覆盖、工具审计 start/finish 配对、归属与结束状态正确。

**八框架初筛。** 每个框架都在两个新环境中，分别用第一组测试数据完成同一采购任务。每轮正常任务应产生三笔写入；下表两次运行各自独立计数。

## 实验三：能否通过网页真正完成业务

**问题：** 助手能否从页面判断目标、找到控件、翻页、填表、提交并下载，而不只是把浏览器启动起来？

**任务：** 浏览器登录测试站点，查找 `item-{seed}-08`；页面库存不足 5 件就按库存买，否则买 5 件；提交后下载 `result.csv`。只给 11 项基础页面动作（导航、快照、点击、填表等），**不给业务写入工具、不给一键采购、不开放 evaluate 或任意 HTTP**，因此无法用预写脚本绕过页面。

**验收：** 业务服务恰好一笔正确写入；CSV 的商品、数量、金额、回执、归属全部匹配；网站审计覆盖登录、多页、表单、回执、下载；浏览器轨迹须有真实导航与交互并能对应实际结果。截图或"下载成功"文字不算数。

**预算：** 首轮网页用例与其他用例同为 **20 次**。八条路线跑下来通过轮次集中在 16–20 次，OpenClaw 和 Codex 整组撞线，无法区分"不会做"与"不够用"。本轮把网页上限提高到 **40 次**（`configs/tasks/browser.yaml` 的 `budget.max_model_calls`；判分、代理上限与证据哈希均按同一份冻结定义执行），其余用例保持 20 次，八条路线各重跑三组。两批预算结果**不直接可比**，分开记录。

| Google ADK | 通过／18 | 通过／18 | 通过／19 | **3/3；55 次** | 不变，仍 3/3 |
| OpenHands | 通过／17 | 通过／19 | 通过／19 | **3/3；55 次** | 不变，仍 3/3 |
| Codex SDK | 通过／28 | 通过／30 | 通过／40 | **3/3；98 次** | **0/3 → 3/3** |

**二十四次运行全部通过，共 527 次模型请求。**

### 这个结果说明什么

**提高预算只解决了预算问题，没有改变能力判断。** 八条路线里，只有此前失败的 OpenClaw 和 Codex 发生变化，而这二者正是撞满了二十次上限的。其余六条在二十次预算下已经通过，提高上限后依然通过，请求数也基本持平（16–20 次）。

这反过来印证了此前的记录方式是对的：首轮把 OpenClaw 记作**未通过**而不是“不具备网页能力”，并在当时写明“这是当前入口、任务和预算组合下的失败，不等于 OpenClaw 不能操作浏览器”。现在这个判断得到了验证——问题确实在预算，不在能力。

**两条路线的真实消耗明显更高。** OpenClaw 平均 31.7 次、Codex 平均 32.7 次，其余六条在 17.7–19.3 次之间。也就是说，这两条路线完成同一个网页任务大约**要多花六成以上的模型调用**。如果把网页任务直接按统一预算上线，它们会被判为失败；如果放宽预算，成本又显著高于其他路线。这个差异比“通过率”更值得在选型时考虑。

**Codex 第三组用满四十次。** 它在通过的同时也触及了新的上限边缘，余量为零。同一任务在别处只需十七八次，这里翻了倍，说明它的调用效率是这条路线的主要问题。

**两批结果不能合并。** 二十次与四十次预算下跑的是同一批任务定义，但预算和 `browser.yaml` 的哈希都变了，因此两批分开记录、分开引用，不拼成一个总成功率。

两框架最终补充单独列出，DSH 使用新保存方式：

| 框架与材料 | 第四组 | 第五组 | 本实验结果；请求合计 |
| --- | --- | --- | --- |
| DSH，新保存方式最终补充 | 通过／19 次 | 通过／18 次 | **2/2；37 次** |
| Deep Agents，最终补充 | 通过／18 次 | 通过／20 次 | **2/2；38 次** |

补充组（第四、第五组，二十次预算）同样只有零到两次余量。原正式组与补充组保持各自材料范围。

这些结果说明网页能力需要同时看真实操作、产物和最终收束，不能只看有没有下单。即使提高到四十次，八条路线也只跑过受控测试站，没有测真实产品网站的稳定性——下一轮应换成目标业务页面复验。真实页面的步骤数和不确定性只会更多，届时四十次是否够用仍要重新测。

## 实验四：业务扩展、规则与控制

**问题：** 业务定制不只是多加一个函数。本实验分开测五项，**一项成功不能替代另一项**：

| 子项 | 要求 |
| --- | --- |
| 新增工具与业务状态 | 新增 `query_order_status` 只查真实回执；每笔下单后显式查询，再写入框架自己的持久状态；换新容器能读回 |
| 敏感操作拒绝 | 真实调用后被执行层拒绝，留归属和原因，不等待审批，无副作用 |
| 超量写入拒绝 | 任务明确要买 4 件，上限 3 件；必须在 HTTP 写入前拒绝，不得改小数量或拆单 |
| 诊断与取消 | 缺文件看真实错误；首次请求注入 504 看重试与累计额度；运行中调公开取消接口 |
| 新进程读取状态 | 删除旧容器，同镜像新容器零模型调用读回已完成状态（不继续未完成任务） |

**两个防作弊设计：** 超量拒绝必须与"正常买两件"配对，否则"全部拒绝"也能通过；敏感拒绝必须是真实调用后被拒，模型自己口头拒绝不算规则被测试。

**新增工具与持久业务状态，原正式三组。** 这仍是正常采购：每种商品买两件，每笔下单后查询真实回执，再保存确认状态。DSH 本组使用原保存方式。

| OpenClaw | 未通过／10 次 | 通过／14 次 | 未通过／7 次 | **1/3；31 次** | 第一、第三组未通过完整分页检查；各轮报告、三笔订单及回执状态正确 |

**运行中取消。** 取消另起真实任务试跑，必须确认原任务实际停止，保留原生终态和取消后写入情况。

| 框架 | 实际运行与请求数 | 取消结果 | 通过范围或失败原因 |
| --- | --- | --- | --- |
| DSH | 两次试跑各 1 次模型请求，均零业务写入 | **两次均未通过** | 已回到空闲且无待执行任务，但缺原生结束事件；第二次记录到结束事件无法序列化的错误。不能只用“空闲”证明完整取消 |
| OpenClaw | 旧接法 9 次请求、三笔写入；修正后 2 次请求、零写入 | **旧接法失败；修正后整体仍失败** | 旧接法使用的控制接口没有对应到发起任务的请求，请求返回后仍继续下单。改为断开原 HTTP 请求后，原生中止证据 9/9 通过，但同轮容器有内存不足标记，独立进程检查失败 |
| Deep Agents | 1 次模型请求，零业务写入 | **9/9 项通过** | 原生执行图完成协作停止并同步保存检查点；在当前执行步骤完成后停下，不是立即抢占 |
| OpenAI Agents SDK | 1 次模型请求，零业务写入 | **9/9 项通过** | 公开立即取消接口生效；预期非零退出和独立进程检查均符合本轮要求 |

OpenClaw 修正后确有同一任务的原生停止证据，不能把它说成靠最后清理容器才停下；同时也不能忽略内存不足而宣布整轮通过。这些取消样例未证明已提交的业务能够撤销，也不覆盖所有工具写入在途的停点。后续暂停实验的通过不能覆盖这里的取消失败。

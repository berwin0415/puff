# 实验资源总预算怎样验收

本页用于 I25 的实施准备，**尚未完成真实多用户实验**。`runner/resource_budget.py` 及其正反校准已纳入 `i18-process-scope-check-001`，固定 bench 镜像 `ec10ed62…` 内全套614项通过；这只确认判定器，不是实例成本实测。

要比较的不是“一个容器给多少资源”，而是在同样的 6 GiB / 3 CPU 总额度下，保留更多用户状态是否必须增加常驻计算资源。两个 Worker、模型代理、工具服务、后端、Gateway、浏览器及同期验收容器都计入当时的总额度；已停止容器的配额不占运行额度，其状态文件和镜像占用另记。

## 检查实际配额

宿主为每个阶段保留一份预先确定的容器清单，列出完整 Docker ID、运行状态、内存和 CPU 配额；另保存通过实验归属标签发现的全部容器的 Docker 观测。验收在 Docker 内完成：

1. 两份清单逐项对应，漏掉 Worker、共享服务或短时验收容器都不能通过。
2. 每个容器都有有限配额，实际配额与声明一致；Docker 的 `0` 表示无限，不能当成零开销。
3. 汇总当时所有运行容器的配额，核对总内存和 CPU；不能把每个用户各有 2 GiB 当作同预算。
4. 核对活跃任务不超过两个。此项只是上限检查，不能据此证明两任务确实同时运行。

清单必须由可信编排保存，不能让候选自己报告，也不能看完实际状态后倒填预期。创建、删除或更换 Worker 时更新生命周期证据，并在新阶段开始前重新核对。运行期动态采样须覆盖同一归属范围，不能只采固定 Compose 服务而漏掉新 Worker。

## 这项检查不能代替什么

`allocation_verdict` 只检查某一阶段的完整容器清单和资源配额，不证明用户身份、任务成功、资源节省或并发重叠。I25 还要独立核对两个真实任务的原生开始/结束和重叠区间、最终业务结果、I24 作用域结果，以及全空闲、两任务运行、回收、再次唤醒的实际采样。

唤醒时间拆成请求接收、排队、Worker 就绪、首次有效动作；不能把排队导致的低内存当作同工作量的节省。状态文件大小、共享固定开销、额外模型调用和 Worker 退出影响单列。Docker 的 PIDs 包含线程，不能直接称为进程数。

每用户常驻仅是实验对照假设，不能从 Hogee 源码推定现网常驻或回收行为。2 / 5 / 10 表示保留的用户状态数量，始终固定两个真实活跃任务；某一档无法在总预算内启动，就记录实测上限及失败，不增加 Colima 配额。

## 统一适配器与 T1/T2

`adapters/openclaw/` 已接入 `openclaw agent exec --json`：

- `preflight()` 校验 pinned commit、CLI、package metadata 和 LICENSE；
- `build_config()` 生成 OpenAI-compatible provider 配置，API key 只引用
  `${MODEL_API_KEY}`；
- JSON envelope 映射为 `process_started`、`assistant_output`、`candidate_error`
  和 `process_exited`，并写入脱敏 manifest/events/envelope。

真实运行：

| 任务 | run_id | 结果 |
| --- | --- | --- |
| API 冒烟 | `98ccbdf5-1ea4-42fc-acc3-82cf32384ea5` | `OPENCLAW_API_OK` |
| T1 工具 | `3727278b-24f0-43e9-bcf6-0bf9f0f20731` | shell/curl 读取 Fixture，返回 `60` |

T2 浏览器此前被误判为“依赖扩展 relay”。OpenClaw 实际内置了托管
`openclaw` headless profile，extension relay 只用于接管已登录的用户 Chrome，
不是托管浏览器的前置条件。适配器可以生成该配置；agent 已能发起浏览器调用，但导航被策略阻断。

但 agent 驱动导航到 loopback fixture 时仍返回
`browser navigation blocked by policy`，即使同时设置
`browser.ssrfPolicy.dangerouslyAllowPrivateNetwork: true` 和
`allowedHostnames: ["127.0.0.1"]`；模型最终回退到 curl。因此 T2 仍未通过，
阻断点是浏览器导航/SSRF 策略，不是 relay。

## 当前结论

已验证 OpenClaw 的开源来源、依赖安装、构建、Gateway 基础运行、远程模型调用、
统一 adapter 和 T1 工具任务。T2 浏览器受扩展 relay 环境限制而阻断；暂停/恢复、
checkpoint、人工审批和 Runner 重启恢复尚未形成同口径证据。后续应验证 Gateway
会话恢复和自定义工具接入，再比较生命周期与多租户边界的补齐成本。
